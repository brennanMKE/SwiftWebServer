## Description

WebSockets were started before any parser or upgrade hook existed (ROADMAP §4). Build RFC 6455 on the `.tunnel` response body from #0080 so the same code later runs over HTTP/2 (#0067) and HTTP/3 (#0111).

## Scope

- `WebSockets` component: validates `GET`, `Upgrade: websocket`, `Connection: upgrade`, `Sec-WebSocket-Version: 13`, a 16-byte base64 `Sec-WebSocket-Key`; computes `Sec-WebSocket-Accept` (SHA-1 via CryptoKit `Insecure.SHA1` or a small local SHA-1, no dependency); subprotocol selection; returns `.tunnel` so HTTP/1.1 emits `101`.
- `426 Upgrade Required` with `Sec-WebSocket-Version: 13` for wrong versions; `400` for malformed handshakes.
- `WSFrameParser` value-type state machine over `ByteBuffer`: FIN/RSV/opcode, 7/16/64-bit lengths (minimal-length not required on read), mask required from clients, unmasking in place, control frames ≤ 125 bytes and not fragmented, RSV bits rejected unless an extension is negotiated, max frame size limit.
- Frame writer (server frames unmasked).

## Acceptance criteria

- RFC 6455 §1.3 handshake example produces the expected `Sec-WebSocket-Accept`.
- Parser tests: every frame split at every byte offset parses identically; unmasked client frame, oversized control frame, fragmented control frame and reserved opcodes are rejected with the correct close code.
- `curl -v --http1.1 -H 'Upgrade: websocket' -H 'Connection: Upgrade' -H 'Sec-WebSocket-Version: 13' -H 'Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==' http://localhost:<port>/ws` shows `101` and `Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=`.

## Root cause

WebSockets were started before any parser, keep-alive or upgrade hook existed (ROADMAP §4),
so there was nothing to build on. With `.tunnel` (#0080) and the middleware builder (#0083)
in place, RFC 6455 could be built as an optional component that touches neither `HTTPCore`
nor `HTTP1`.

## Fix

- `WebSocketHandshake` (`Sources/WebSockets/WebSocketHandshake.swift`): validates `GET`,
  `Upgrade: websocket`, the `upgrade` token in the `Connection` list,
  `Sec-WebSocket-Version: 13` (missing or other: `426` with `Sec-WebSocket-Version: 13`,
  `Upgrade` and `Connection`), and exactly one `Sec-WebSocket-Key` that is padded base64 of
  16 bytes (else `400`; a non-GET is `400` too). `Sec-WebSocket-Accept` is CryptoKit
  `Insecure.SHA1` (system framework, no package dependency) plus a local base64.
- `WSFrameParser` (`WSFrameParser.swift`): value-type, split-invariant parser with one
  `parse(_:payloadInto:)` entry point returning `.needMoreBytes`, `.header`,
  `.payload(count:frameEnd:)` or a sticky `.error(code)`. Payload is streamed into a sink (no
  whole-frame buffering); 7/16/64-bit lengths (non-minimal accepted, 64-bit MSB → 1002);
  masking required from clients (configurable for a client role); control frames ≤ 125 bytes
  and FIN set; reserved opcodes and RSV bits not allowed by a negotiated extension → 1002;
  payload over `maxFrameSize` → 1009, decided from the header alone. Checks that need only
  the first two bytes fail before the rest of the header arrives, with the same verdict at any
  split.
- `WSMasking` / `WSFrameWriter` (`WSFrame.swift`): unmasking XORs a 64-bit word at a time
  (mask rotated by the frame offset so splits keep the phase) while moving bytes out of the
  receive buffer; that copy happens anyway, so there is no separate in-place pass. The writer
  emits unmasked server frames with the shortest length encoding (masked frames for a client
  role and the tests).
- `WebSocketCloseCode` with the RFC 6455 §7.4 / IANA validity rules (1000–1003, 1007–1014,
  3000–4999 on the wire).
- The `.tunnel` side of the handshake (the `WebSocketUpgrade` component returning `101` and a
  `.tunnel` body) needs the session, so it landed with #0109 in `ea710e1`; the curl acceptance
  check is verified there and listed below.

## Gotchas

- `HTTPRequest` carries no HTTP version, so the component cannot tell HTTP/1.0 from HTTP/1.1.
  In practice the key/version checks reject non-WebSocket clients, but RFC 9110 says a server
  must ignore `Upgrade` on HTTP/1.0 and must not send 1xx to it. That belongs in the HTTP/1.1
  runner (or a version on `RequestContext`), not in this target; worth a follow-up issue.
- `#expect(validator.validate(...))` does not compile for a mutating call (the macro captures
  the value immutably); bind the result first.
- Building a test request with `String(decoding:)` around masked frame bytes corrupts them
  (U+FFFD replacement); keep frames as bytes.
