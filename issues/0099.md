## Description

HTTP/3 control and request stream logic must be testable in memory like HTTP/1.1 (ROADMAP §4).

## Scope

- `InMemoryMultiplexedTransport` in `HTTPTestSupport`: scripted inbound bidi and uni streams with RFC 9000 stream IDs, per-stream `InMemoryTransport`, FIN, reset with code, STOP_SENDING, connection close with application code, and a paired client mode.
- Deterministic ordering controls so tests can interleave streams precisely.

## Acceptance criteria

- Self-tests mirror the #0098 echo test (same assertions) in memory and run in `swift test`.

## Relation

- **Milestone:** M8 — QUIC transport (item 8.2)

## Root cause

HTTP/3 logic had no in-memory substrate: `MultiplexedTransport` (#0077) had only the planned NW implementation (#0098), so control and request stream code could not be tested without QUIC.

## Fix

Added `InMemoryMultiplexedTransport` (HTTPTestSupport), mimicking the NW QUIC behaviour recorded in `docs/spikes/quic-spike.md`:

- `makePair(client:server:)` and `scripted(_:side:finishesInbound:configuration:)` (scripted inbound streams; local opens capture sends and never block).
- RFC 9000 stream IDs (client bidi 0, 4…; server bidi 1, 5…; client uni 2, 6…; server uni 3, 7…). A stream reaches the peer when it is opened, so the order of opens is the order of arrival (deterministic interleaving).
- `inboundStreams` is a demand-driven `AsyncSequence` with one consumer. Pending streams are bounded by MAX_STREAMS.
- Each stream is a pair of `InMemoryTransport` endpoints: bounded backpressure, receive chunking, `play` with delays and errors, `sentBytes`, `failNextSend`.
- FIN via `send(_:endOfStream: true)`. `reset(applicationError:)` discards unread bytes; the peer's receive throws `connectionReset` and `receivedResetCode` reads the code (NW `streamApplicationErrorCode`). `stopSending(applicationError:)` refuses peer sends and is answered by RESET_STREAM with the same code (RFC 9000 §3.5). `close(.abort)` = reset + stop with code 0 (NW `forceCancel`). `injectPeerReset` / `injectPeerStopSending` work in both modes.
- `close(applicationError:)`: every stream, pending opener and inbound iterator ends. The closer gets `.closed` and the peer `.connectionReset`. Both codes are observable (`closeApplicationError`, `peerCloseApplicationError`). The first close wins. `fail(with:)` makes `inboundStreams` throw.
- MAX_STREAMS is cumulative and never auto-replenished (spike gotcha 5). Opens beyond it suspend FIFO per kind until the peer calls `raiseMaxStreams`; they are cancellable. Inspection: `blockedOpenCount`, `pendingInboundCount`, `openedStreams`, `maxStreams*`.

## Gotchas

- On connection close, the closing side's stream endpoints are closed *before* any pipe is reset. Otherwise a closer's pending receive can wake on the drained pipe and report `connectionReset` instead of `.closed`.
- Unlike NW (spike Q6), the peer can read the connection-close code here. Tests that assert it model the intended wire behaviour, which #0104 still has to verify on NW.
- In scripted mode, a locally opened bidi stream receives end of stream at once (no scripted peer).
- The connection keeps every stream it created until it is released, so it is meant for tests, not long-running loads.
- `#expect(try await ...)` inside task-group closures failed to type-check ("errors thrown from here are not handled"). Bind the value to a `let` first.
