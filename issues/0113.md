## Description

In `docs/SERVER-COMPARISON.md`, with a new connection per request (16 concurrent, `oha --disable-keepalive`), the new server reaches 2,266 req/s with a 6.4 ms p50. nginx reaches 21,344 req/s with a 0.59 ms p50. With keep-alive the new server is within 4% of nginx, so the cost is in accepting and setting up each connection, not in request handling.

## Steps to reproduce

1. `scripts/guarded.sh -t 2400 -- scripts/bench-compare.sh 10 /tmp/compare.md`
2. Compare the `close` rows.

## Expected behavior

New-connection throughput within 2× of nginx on the same machine.

## Actual behavior

About 10× slower, with a 6 ms median latency for a 626-byte response.

## Notes

- Suspects: `NWListener` → `NWConnection` → `start(queue:)` per connection, a new serial queue per connection, the readiness handshake before the first receive, the bounded accept queue in the TCP listener (#0078), and per-connection task-group child creation (#0079).
- Measure first: time from accept to first byte read, and allocations per connection. Compare per-connection queue against a shared queue pool; consider setting `NWListener.newConnectionLimit` and avoiding the extra hops.
- If Network.framework's per-connection cost cannot be cut enough, evaluate a BSD-socket + kqueue transport behind the same `ByteStreamTransport` protocol, for cleartext TCP only. It would be an optional adapter, with TLS and QUIC staying on Network.framework.
- Ephemeral-port exhaustion on loopback distorts closed-connection benchmarks. Measure with fewer total connections, for example `oha -n 20000`, or spread the client across several source addresses (127.0.0.2+).

## Root cause

Not our accept queue, task-group children or continuation hops. All of these together cost a
few microseconds (the accept loop takes a ready connection in about 3 µs). Network.framework
runs all connection work for the process on one serial queue, `com.apple.network.connections`,
and 86% of `sample` hits were there. Its listener creates an `nw_association` (with a path
evaluator, parameters, endpoints and a deactivation timer) for every distinct remote
endpoint and keeps it for about 60 s after the connection closes. `heap` showed 10,586
associations after about 10,600 connections, and our own live transports stayed at about the
number in flight. Each accept looks the endpoint up in a table that grows with recent peers
(`nw_context_copy_registered_endpoint` → `nw_hash_table_get_node` →
`nw_endpoint_is_equal`). Result: about 665 µs of CPU and 409 allocations per connection, a
2 ms p50 to `newConnectionHandler` and another 2 ms to `.ready`, all serialized on about one
core. The rate falls with every round of new clients (4.3k → 2.7k → 1.6k connections/s). None
of the public knobs changed it: a shared serial-queue pool, a private
`NWParameters.PrivacyContext`, `disableLogging()`, and periodic `flushCache()` all stayed within
noise.

## Fix

- New optional transport in NetworkTransport, for cleartext TCP only: `BSDSocketListener` and
  `BSDSocketTransport` (POSIX non-blocking sockets + kqueue, `BSDEventLoop`, `SocketCore`).
  System calls run directly on the calling task. A one-shot kqueue wait is armed only on
  `EAGAIN`, and its event resumes the task, which retries. Accept and receive stay
  demand-driven, with no read-ahead and the accept bound in the kernel's listen backlog. `send`
  returns when the kernel has accepted every byte, `endOfStream` is `shutdown(SHUT_WR)`, and
  `.abort` is `SO_LINGER` 0. Cancellation and close have the same semantics as `TCPTransport`.
  A descriptor is closed only when no system call is using it, so a descriptor number is never
  reused under a concurrent `read`.
- Configuration switch: `sws-bench serve --transport bsd|nw` (config key `"transport"`).
  **The default is `bsd`** because it wins clearly in both modes (below). TLS and QUIC stay on
  Network.framework, and `TCPListener` remains available and tested.
- Measurement: `sws-bench accept` (per-connection phase timeline, allocations per
  connection, `--pause` to observe NW's association aging) and `scripts/bench-accept.sh`
  (`oha --disable-keepalive -n 10000 -c 16` with a `TIME_WAIT` drain, interleaved with
  nginx, then keep-alive rounds). Only `@_spi(Benchmark)` timestamps were added to the NW
  adapter.

  (load average 10.2 → 10.9, 0 errors in every closed-connection run). Medians: new

  load 25–43 gave BSD 20,512 against nginx 23,679 (0.87×). Both runs are within the 2× target.

  including the 14 shared socket tests in `TCPTransportTests` now run against both adapters

## Gotchas

- Network.framework's accept cost depends on history: it grows with the number of distinct
  peers in roughly the last 60 s, so short benchmarks on a fresh process overstate it, and
  back-to-back rounds look worse each time.
- `heap` and `sample` need the bench binary's PID. `pgrep -x sws-bench` can match another
  agent's server, so match on the worktree path.
- With a stalled reader, the BSD transport accepts about 2.5 MiB (kernel socket buffers) before
  `send` stalls, against about 0.6 MiB for NW. Both are bounded.
- `BSDSocketTransport.close` is `close(2)`: unread input makes the kernel send RST, as with
  NW's `cancel()`. HTTP/1.1's lingering close (#0082) drains input first.
- `docs/SERVER-COMPARISON.md` still shows the NW numbers; re-run `bench-compare.sh`, which now
  uses the BSD default, at the milestone-end idle run.
