## Description

Complete RFC 6455 with a connection state machine and a message API, verified with Apple's own WebSocket client.

## Scope

- `WSConnection` state machine: open, closing (sent or received), closed; close handshake with code and reason validation, closing timeout, TCP close after the handshake.
- Message assembler for fragmented messages with a max message size (`1009`); interleaved control frames allowed; continuation without a start is `1002`.
- Streaming UTF-8 validator for text messages across fragment boundaries (`1007` on invalid).
- Automatic pong to ping, application ping API, idle ping/timeout optional.
- Handler API: `AsyncSequence` of messages in, async send out, with backpressure; built on `ByteStreamTransport` only, so it is transport-agnostic.
- Optional Autobahn run via the existing `scripts/run-autobahn-*.sh` scripts when Docker is available (not installed on this machine; not an exit criterion).

## Acceptance criteria

- `URLSessionWebSocketTask` integration tests in `swift test`: text echo, binary echo, a 1 MiB message, ping/pong, and client-initiated and server-initiated close with codes observed on both sides.
- In-memory tests: fragmented text with a multibyte character split across frames validates; invalid UTF-8 closes with 1007; oversized message closes with 1009.

## Root cause

Only the frame layer existed (#0108): there was no connection state, message assembly, UTF-8
validation, ping/pong or close handshake, no application API, and nothing that answered a
handshake with `101`.

## Fix

- `WSConnection` (`Sources/WebSockets/WSConnection.swift`): value-type state machine (open,
  closing, closed) with `process(_ input:) -> Action` for received bytes and
  `handle(_ event:) -> Action` for local events (application close, close timeout, end of
  stream); one action per call, no I/O. It owns the parser, the message being assembled and
  the control-frame buffer.
  - Fragmentation: continuation without a message, or text/binary inside one → 1002; control
    frames interleave freely; message size checked from frame headers before the payload is
    buffered → 1009.
  - Text is validated per received payload run, so a bad byte fails at once (1007) even
    mid-fragment, and a message that ends inside a code point is 1007.
  - Ping → `sendPong`; pong → `receivedPong`. Data and pings that arrive after our Close are
    discarded.
  - Close: a peer Close is checked (1-byte payload or a code not valid on the wire → 1002,
    non-UTF-8 reason → 1007), echoed with its code, and the server closes the TCP connection
    first (half-close, then wait for the peer's EOF or the close timeout). Our Close waits for
    the peer's; EOF without a Close reports 1006; the timeout closes the transport.
- `UTF8Validator` (`UTF8Validator.swift`): byte-range DFA (narrowed second-byte ranges after
  E0, ED, F0, F4) with an 8-byte ASCII fast path; fails on the first byte that cannot
  continue a valid sequence.
- `WebSocket` (`WebSocket.swift`): `messages` (`AsyncSequence` of `.text(String)` /
  `.binary(ByteBuffer)`), `send`, `send(text:)`, `send(binary:)`, `ping(_:)` (waits for the
  matching pong), `close(code:reason:)`, `closeCode`/`closeReason`/`failureCode`.
  `WebSocket.run(over:subprotocol:configuration:handler:)` is generic over
  `ByteStreamTransport` only, so RFC 8441 (#0067) and RFC 9220 (#0111) can call it on an
  extended CONNECT stream. The session is one task group: reader (receive → state machine
  under a `Mutex`, non-suspending), writer (single sender draining a `BoundedAsyncQueue`,
  drops frames after a Close), close timer, and the handler. Received messages go through a
  `BoundedAsyncQueue` (capacity 1 by default), so a slow reader suspends the reader task and
  no more bytes are read from the transport. A returning handler closes with 1000, a throwing
  one with 1011.
- `WebSocketUpgrade` (`WebSocketUpgrade.swift`): `HTTPMiddleware` registered through the
  builder. On its path it validates the handshake (`400`/`426`), runs the Origin hook (`403`),
  picks a subprotocol through a callback (ignored unless offered), and returns `101` with
  `Upgrade`, `Connection`, `Sec-WebSocket-Accept` and a `.tunnel` body that runs the session.
  With no path it only takes `Upgrade: websocket` requests; other requests go to `next`.
  Handlers get a `WebSocketRequest` snapshot (path, query, origin, offered subprotocols,
  headers, connection info), since the `HTTPRequest` is invalid after the handler returns.
- `sws-bench serve --websocket-echo PATH`: an echo endpoint in front of the usual handler;
  without the flag the chain has no WebSocket code at all.

## Gotchas

- `URLSessionWebSocketTask` only reads frames, pongs included, while a `receive()` is
  outstanding: `sendPing`'s completion never fires otherwise. Keep a receive pending while
  pinging (the test uses `async let`).
- `BoundedAsyncQueue.finish()` does not resume producers already suspended in `send`; to
  abandon the inbound queue when the handler returns, finish it and then drain with
  `tryNext()` so the reader is never stuck behind an application that stopped reading.
- The tunnel closure gets no shutdown signal, so a draining server cannot send 1001 to open
  WebSockets; they end when the HTTP/1.1 drain deadline cancels the connection task (the
  session handles cancellation cleanly). Passing the signal into `.tunnel` would allow a
  graceful 1001; a follow-up for HTTPCore/HTTP1.
- No HTTP version on `HTTPRequest` (see #0108 Gotchas).
- Pongs decided by the reader and an application Close decided at the same moment can reach
  the writer in either order; the writer drops anything after a Close, so nothing follows a
  Close on the wire.
- Type names nested in a generic function are not allowed (`enum Role` inside
  `run(over:...)`); it lives on `WebSocket`.
