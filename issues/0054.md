## Description

Respect the peer's send windows by suspending body writers instead of buffering.

## Scope

- Connection and per-stream send windows. A DATA frame is sized as the minimum of the chunk, the stream window, the connection window, and MAX_FRAME_SIZE.
- Writers `await` credit through continuations stored in the connection's `Mutex`-protected state (no actor) and resumed outside the lock. WINDOW_UPDATE and a SETTINGS INITIAL_WINDOW_SIZE delta (which can make windows negative, §6.9.2) resume them.
- Cancellation handlers remove waiters, and waiters on the same connection are resumed fairly.
- A WINDOW_UPDATE increment of 0 is a `PROTOCOL_ERROR`, and a window overflow above 2³¹−1 is a `FLOW_CONTROL_ERROR`.

## Acceptance criteria

- A test client advertises a 1-byte window and increments it slowly. The server delivers the file correctly without buffering more than one chunk.

## Root cause

Feature work. #0044 already sized DATA frames by both send windows and MAX_FRAME_SIZE, applied INITIAL_WINDOW_SIZE deltas (negative windows included) and rejected window overflow. But writers waited on a generation counter: every batch taken and every window change woke every waiting writer (#0044 Gotchas). That is a thundering herd, and not fair: whichever task ran first won, so a large response that kept coming back could starve the others.

## Fix

Fair waiting in `HTTP2SharedState`, all inside the connection `Mutex`, with continuations resumed outside it:

- **Tickets.** A writer that cannot send gets a ticket (`StreamStep.wait(ticket:)`), parks its continuation (`parkWaiter`), and retries with the same ticket.
- **Two waiting places.**
  - A writer whose own stream send window is ≤ 0 waits in `streamWaiters`. Only a WINDOW_UPDATE on that stream, an INITIAL_WINDOW_SIZE change that makes it positive, a reset of the stream, or the connection closing wakes it.
  - A writer that needs queue space or connection window, or finds another writer ahead, joins the back of `fairQueue`.
- **One turn at a time.** `grantNext` gives the turn to the first queued writer that can proceed now and wakes only it: a HEADERS writer needs queue space, a DATA writer queue space and connection window. It runs after every frame sent, every batch the writer takes, and every connection WINDOW_UPDATE. A writer that did not wait cannot overtake the one holding the turn.
- **Round robin.** A writer that sent a frame and returns for more while others wait goes to the back, so responses take turns frame by frame.
- **Cancellation.** A cancelled writer is removed and passes its turn on (`cancelWaiter`, from the cancellation handler and after the wait).
- **Wakeups.** A stream reset wakes that stream's writer wherever it waits, and its retry drops. The final GOAWAY and connection close wake every writer.
- Zero increments (`PROTOCOL_ERROR`, from the parser) and windows above 2³¹−1 (`FLOW_CONTROL_ERROR`, stream or connection) were already handled; they now have connection tests.

## Gotchas

- Turns are handed out one at a time, so a burst of window serves the waiters one wakeup after another rather than in parallel. A woken writer sends one frame and passes the turn on at once, so the hand-off costs one task switch per frame, and only while writers contend.
- `fairQueue` is an array (`firstIndex` and `remove(at:)`), which is fine for MAX_CONCURRENT_STREAMS of 100. A much larger limit would want a ring.
- A HEADERS writer behind a DATA writer that waits for connection window is not held up: `grantNext` skips to the first writer that can proceed.
