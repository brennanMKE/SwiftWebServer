## Description

Each client bidirectional stream carries one request (RFC 9114 §4.1). Map it to `HTTPRequest`, run the middleware chain, and write the response as HEADERS and DATA frames.

## Scope

- `H3RequestStream` state machine: HEADERS, DATA*, optional trailers HEADERS; frames out of order are `H3_FRAME_UNEXPECTED`; `content-length` checked against DATA total (`H3_MESSAGE_ERROR`).
- Shared pseudo-header validation in `HTTPCore` (`:method`, `:scheme`, `:authority`/`host`, `:path`, no connection-specific fields, lowercase names) used by both HTTP/3 and HTTP/2 (#0047).
- Request body is a demand-driven `HTTPRequestBody` over DATA frames; backpressure by not reading the QUIC stream.
- Each request stream handled as a child task of the connection's task group; no shared mutable state on the request path (static-table QPACK).
- Response: QPACK-encoded HEADERS, DATA frames (`.bytes`, `.file` read in bounded chunks, `.stream`), trailers; FIN after the last frame; HEAD/204/304 rules from #0081.

## Acceptance criteria

- `/opt/homebrew/opt/curl/bin/curl --http3-only -k https://localhost:8443/` returns the index page; `--parallel -Z` fetching 20 files over one connection succeeds; a 1 GiB file downloads with a matching checksum and flat server RSS.
- In-memory tests for every request-stream rule and a malformed-frame suite (bad order, oversized frame, bad pseudo-headers) asserting stream or connection errors with the RFC 9114 code.

## Root cause

Feature work: HTTP/3 had no request path. Nothing mapped a client bidirectional stream to an `HTTPRequest`, ran the handler, or wrote a response.

## Fix

- **`H3RequestStream`** (`Sources/HTTP3/H3RequestStream.swift`) is a pure state machine for HEADERS, then DATA*, then optional trailers, then FIN.
  - A frame out of order is the connection error `H3_FRAME_UNEXPECTED`.
  - A stream that ends before HEADERS is the stream error `H3_REQUEST_INCOMPLETE`.
  - DATA beyond `content-length`, or a FIN short of it, is `H3_MESSAGE_ERROR`.
- **Heads** (`H3Message.swift`) are decoded by `H3RequestHeadDecoder` with static-table `QPACKDecoder` into a per-stream `HTTPRequestStorage`. Each field is checked by HTTPCore's `PseudoHeaderValidator` (`:method`, `:scheme`, `:authority`/`host`, `:path`, lowercase names, no connection-specific fields, `te: trailers`). `:path` is split into path and query.
  - A malformed head resets the stream with `H3_MESSAGE_ERROR`, and the connection stays up.
  - A section over MAX_FIELD_SECTION_SIZE is answered `431`.
  - Any other QPACK failure closes the connection with `QPACK_DECOMPRESSION_FAILED`.
  - Trailers are decoded and validated (no pseudo-header fields).
- **Request body.** `main` gained `HTTPRequestBody`/`HTTPRequestBodySource` (#0081) during this work, so there is no h3-local body type and no TODO left to unify. `H3BodyChannel` is an `HTTPRequestBodySource`, and `request.body` is a normal `HTTPRequestBody` with `knownLength` and `trailers`.
  - A body reader task per stream (`H3RequestReader` + `pumpBody`) parses DATA into a `BoundedAsyncQueue` (capacity 4). It stops reading the QUIC stream while the queue is full, which is the backpressure.
  - Reads after the handler returns throw `.expired`, and concurrent reads throw `.concurrentRead`.
  - A malformed body is `.malformed`, a stream ending inside a frame is `.truncated`, and a peer reset is `TransportError.connectionReset`.
- **Responses** are written by `H3ConnectionDriver.write`. `H3ResponseHeadEncoder` writes `:status` first, lowercases names, drops connection-specific fields and adds `content-length` when the length is known.
  - `.bytes` goes out as HEADERS + DATA + FIN in one send.
  - `.file` is one DATA header followed by `sendFile` (bounded 64 KiB `pread` chunks).
  - `.stream` writes one DATA frame per `HTTPBodyWriter.write`.
  - HEAD, 204 and 304 carry no content.
  - `.tunnel` is answered `501` until #0111.
- **Concurrency.** `HTTP3.run` runs a discarding task group per connection with a child task per stream. Inside each request stream task, a task group runs the handler next to the body reader. A peer reset seen by the reader cancels the handler.
  - A handler that throws before anything was sent gets `500`.
  - A `.stream` body that fails after the head resets the stream with `H3_INTERNAL_ERROR`.
  - After the response, an unread body is drained to FIN.
  - Request streams share no mutable state. `H3Connection` sits in a `Mutex` with non-suspending critical sections.
- **HTTPCore.** `ResettableStream` adds `reset(applicationError:)` and `stopSending(applicationError:)`, the #0098 follow-up. `QUICStreamTransport` and `InMemoryMultiplexedTransport.Stream` already had the methods and now conform. `MultiplexedConnectionProtocol` is the `ConnectionProtocol` counterpart for multiplexed transports, and `HTTP3` conforms with ALPN `h3`.
- **`sws-bench serve --h3`** starts a `QUICListener` on 127.0.0.1 (port 0 by default). It loads the identity from a PKCS#12 file through `TLSIdentity` (in memory only; the default is `.test-identity/server.p12`) and serves main's `ServeHandler`: GET gets hello, POST is echoed, PUT gets the body length.

## Gotchas

- Network.framework has no standalone STOP_SENDING, so `stopSending` on a QUIC stream resets both directions. After writing a response the server therefore never sends STOP_SENDING to cut off an unread request body. It drains the body to FIN instead. A client that never sends FIN keeps that stream task alive until the connection ends (abuse limits are #0104).
- The body reader records why the body ended (`fail(_:)`) before the handler task is cancelled. `nextChunk` checks that reason before `Task.checkCancellation()`, so the handler sees `.malformed` or `connectionReset` rather than a bare `CancellationError`.
- When the body turns out malformed while the handler runs, the handler's error must not produce a `500`: `serve` resets the stream, and a racing `500 + FIN` could make the reset invisible to the client.
- A request stream reset before the server read its HEADERS is dropped silently, because the in-memory and QUIC transports discard unread bytes. Tests that reset a request wait until the handler has started.
- Swift's type checker times out on large inline `@Test(arguments:)` tuple literals. They are built as `static let` arrays.
- Not covered here: the acceptance items that need StaticFiles (#0084): serving the index page and a 1 GiB checksum download with flat RSS. File bodies already go out through bounded `sendFile` chunks (tested with 200 KiB). Response trailers are not supported (`HTTPResponse` has none). The peer's MAX_FIELD_SECTION_SIZE is not enforced on our response heads yet (#0102).
