## Description

`keepAliveTimeout` is parsed but ignored, so idle and slow-header connections live forever (#0012). Add per-phase deadlines and a graceful drain on shutdown.

## Scope

- `Deadline`-based timeouts in the HTTP/1.1 runner: header-read timeout (slowloris), keep-alive idle timeout, body-read inactivity timeout; values from configuration with documented defaults.
- Header or body timeout mid-request → `408 Request Timeout` + close; idle timeout between requests → silent close.
- Graceful drain: on `ServerLifecycle.draining`, idle connections close immediately, in-flight requests finish and their connection closes after the response (`Connection: close`), and anything left at the drain deadline is cancelled.
- Timeouts implemented as children of the connection's task group or a deadline checked by the runner, not unstructured tasks.

## Acceptance criteria

- In-memory tests with an injected clock: slow-header client gets 408 and is closed; idle keep-alive connection closed at the timeout; drain lets an in-flight streamed response finish and refuses new requests.
- Socket test: `nc localhost <port>` sending a partial request line is closed after the header timeout.
- SIGTERM during a large-file `curl` download completes the download and the process exits 0 within the drain deadline.

## Root cause

The HTTP/1.1 runner had no deadlines at all: a connection parked in `receive` stayed there
until the client sent something or the server's drain deadline cancelled it, so an idle or
slowloris client held a connection and its task indefinitely (#0012), and a draining server
waited the full drain timeout for idle keep-alive connections. The shutdown signal was read
once per batch, so an in-flight response did not say `close`. Error closes (413, 417, unread
`100-continue` bodies) half-closed and closed at once, so a client still sending could see a
reset instead of the response.

## Fix

- `HTTP1Timeouts` in `HTTP1Configuration` (defaults: header 10 s, idle 5 s, body 30 s, send
  30 s, linger 2 s; `nil` disables one) plus `maxLingerSize` (1 MiB).
- `HTTP1.run` supervises the loop in one task group per connection: the loop, one timer task
  and one shutdown waiter. No task per request. They share `HTTP1Watchdog`, one atomic word
  holding the loop's phase (idle, head, body, send, linger), its deadline in
  `mach_continuous_time` ticks, and an owned bit. The loop publishes each phase with a
  compare-and-swap; the timer sleeps until the deadline (re-checking at least every shortest
  limit) and claims the word with a compare-and-swap only if it is unchanged, so a loop that
  moved on is never interrupted. Every loop send is preceded by `enter(.send)`, so once the
  supervisor owns the connection the loop sends nothing more.
- Header (from the head's first byte, not renewed by progress) and body (inactivity) expiry:
  the supervisor sends `408` + `connection: close` with end of stream while the loop is still
  parked in `receive`. It does not cancel the receive first because cancelling a TCP receive
  cancels the whole `NWConnection`. It then lingers: the loop discards input until the client
  closes or the linger limit passes.
- Idle expiry closes silently (`CloseReason.timeout`); send expiry resets (`.abort`).
  Outputs over 1 MiB and files go out in 1 MiB slices, each under its own send limit, so the
  limit catches a client that stopped reading, not a slow download.
- Drain: the shutdown waiter claims a connection that is idle or mid-head and closes it at
  once. `ShutdownSignal.isTriggered` is now one sequentially consistent atomic load, cheap
  enough to check per request. The loop checks it after publishing its phase (pairs with the
  waiter, which sets the flag and then reads the phase), before each head (a pipelined request
  not yet started gets no response) and before each response (the in-flight response says
  `close`). `HTTP1Connection` closes on `.shutdown` in `readingHead` too.
- Lingering close: after a final response when request bytes may be unread (parse error,
  413/417, an unread or undrainable body, an unread `100-continue` body, dropped pipelined
  requests), the output is half-closed and input discarded for at most `linger` and
  `maxLingerSize`, ended early by the client's end of stream. A clean `Connection: close` with
  nothing buffered does not linger.
- Memory (#0080 gotcha): not a leak, see `docs/benchmarks/M3.3-timeouts.md`. `leaks` reports 0.
  The retained heap after close-mode runs is all Network.framework per-endpoint association
  and path state, which expires on its own. After 90 s idle the footprint went from 115 MiB to
  19.3 MiB. `ps` RSS stays high because freed pages are only marked reusable.

## Gotchas

- Cancelling a `TCPTransport` receive cancels the whole connection (Network.framework cannot
  cancel one receive). So a timeout that needs to answer cannot cancel the loop first: the `408`
  is sent concurrently with the loop's parked receive (one receive plus one send at a time is
  allowed), and the loop is cancelled only when the connection ends.
- The timer re-reads the phase word at least every shortest configured limit (2 s with the
  defaults, the linger), so a connection between requests wakes its timer about three times per
  idle period. Wakeups are per connection and per period, never per request.
- An idle connection closes after `idle` even before its first request (no `408`). The header
  limit starts at the first byte of a head.
- Sniffing in `ProtocolRegistry` (only when more than one cleartext protocol is registered) has
  no timeout yet; a client that connects and sends nothing waits there until the drain deadline.
  It belongs in HTTPServer (follow-up; left alone here because #0113 is changing the accept path).
- `.bytes` bodies over 1 MiB are copied slice by slice into a scratch buffer to send them under
  the send limit (ByteBuffer has no zero-copy sub-range).
- The 2 extra child tasks per connection add a few MiB during close-mode bursts and are part of
  per-connection setup cost; worth a look alongside #0113 if accept rate matters.
- `ConfigFile` and `sws-bench serve` do not expose the new limits yet; `HTTP1Configuration` is the
  only way to set them.
