## Description

The legacy receive loop keeps parsing after the response, never resets its buffer (#0007), falls through to parsing on receive errors (#0008), leaves the connection hanging when a response throws (#0009), and closes after one response. Implement the HTTP/1.1 connection as a pure state machine plus a thin async runner that is the hot loop in ROADMAP §5.3.

## Scope

- `HTTP1Connection` state machine: idle, readingHead, handling, readingBody, writing, closing, tunnelled; persistence per RFC 9112 §9.3 (`Connection: close`, HTTP/1.0 without keep-alive), `Connection` response header decided here (#0020 part).
- `HTTP1` conforms to `ConnectionProtocol`; its runner owns one receive buffer, the parser and the state machine as locals (no actor); one `await` per read and one per pipelined batch write.
- Pipelining: parse every complete head already buffered, respond in order, flush once per batch.
- Receive errors and EOF end the loop cleanly (#0008); a handler throw before the response starts becomes `500` + `Connection: close` (#0009); after headers are sent, the connection closes.
- `.tunnel` responses emit `101 Switching Protocols` and hand the transport to the closure (hook for #0108).
- Buffer compaction after each request so the buffer never grows across requests (#0007).

## Acceptance criteria

- In-memory tests: 100 keep-alive requests on one connection; 10 pipelined requests in one write answered in order with one flush; handler throw → 500 and close; receive error → loop exits, no response attempted; HTTP/1.0 without keep-alive closes.
- `curl -v http://localhost:<port>/a http://localhost:<port>/b` shows `Re-using existing connection`.
- `sws-bench` keep-alive load run with `oha -c 16` beats the legacy baseline from #0070 and allocations per request in our code are 0.

## Root cause

The legacy receive loop had no notion of a connection: it parsed whatever was buffered after each
response (#0007), fell through to parsing on receive errors (#0008), dropped handler errors in an
unstructured task (#0009), and closed after every response without saying so (#0020).

## Fix

- `HTTP1Connection` (`Sources/HTTP1/HTTP1Connection.swift`): a pure value-type state machine
  (idle, readingHead, handling, readingBody, writing, closing, tunnelled) with
  `mutating func handle(_:) -> Action`. It decides persistence per RFC 9112 §9.3 (`Connection:
  close`; HTTP/1.1 persistent by default; HTTP/1.0 only with `keep-alive`, and never persistent
  with an unknown-length body since it has no chunked coding) and the `connection` header the
  serializer writes.
- `HTTP1` (`Sources/HTTP1/HTTP1.swift`) conforms to `ConnectionProtocol` (ALPN `http/1.1`,
  request-line sniffing). Its driver keeps the request storage (whose buffer is the receive
  buffer), parser, serializer, output buffer and state machine as stored properties of one local
  value: per batch, one `receive`, every complete pipelined head handled in order into one output
  buffer, one `send`; consumed bytes are discarded after each batch so the buffer never grows
  across requests. `.file` bodies use `transport.sendFile` after the head is flushed.
- Errors: parse error → mapped status + `connection: close`; handler throw → 500 + close (earlier
  pipelined responses go first); receive/send error → loop ends, no response; EOF between
  requests or mid-head → quiet close. Error and closing responses are flushed with
  `endOfStream: true`.
- Hooks: request bodies get 413 (Content-Length) or 501 (chunked) and close until #0081
  (`HTTP1Connection.bodyNotSupportedStatus`); `.stream` responses are answered like a handler
  error until #0081; `.tunnel` flushes the head and hands the stream (replaying buffered bytes)
  to the closure (#0108); shutdown is checked once per batch and idle connections are cancelled
  at the drain deadline until #0082.
- `sws-bench serve` speaks HTTP/1.1 with a prebuilt hello response (`--body-size N` for static
  bytes); `sws-bench h1conn` measures the loop.

## Gotchas

- The type `HTTP1` shares its module's name, so `HTTP1.Something` resolves to the type, not the
  module; refer to other HTTP1 types unqualified.
- `HTTP1Parser` requires the buffer's reader index to stay put while a head is in progress, so
  compaction with a partial head buffered resets the parser and rescans that head once.
- The registry calls `run` through an opened existential, so the loop is not specialized for the
  transport and handler; witness-table calls cost a few ns per request.
- `ShutdownSignal.isTriggered` takes a shared lock; it is read once per batch, not per request.
- RSS reached 110 MiB after a close-mode run of about 14,000 connections (12.5 MiB after millions
  of keep-alive requests); worth checking with the timeout/drain work in #0082.
