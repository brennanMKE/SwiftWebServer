# 0055 — Enforce SETTINGS_MAX_CONCURRENT_STREAMS and header list size limits

## Description

Bound per-connection work using the limits the server advertises.

## Scope

- A HEADERS frame that would exceed MAX_CONCURRENT_STREAMS gets `RST_STREAM(REFUSED_STREAM)`, and its header block is still decoded (#0046).
- Header lists over MAX_HEADER_LIST_SIZE get a `431` response when possible, or otherwise a stream reset.
- Limits come from the `http2` config section.

## Acceptance criteria

- Tests cover stream 101 of 100 being refused while earlier streams complete, and an oversized header list.

## Relation

- **Milestone:** M13 — HTTP/2 flow control, limits and conformance (Track B)
- **Blocked by:** #0046, #0049, #0088, #0095
- **Blocks:** #0056

## Root cause

Feature work. The stream table already refused HEADERS past MAX_CONCURRENT_STREAMS (#0045), but nothing tested it end to end. Every other limit was missing or too blunt:

- **Our header list limit.** It was enforced only inside HPACK, so an oversized request head was a connection `COMPRESSION_ERROR` instead of a `431`.
- **The peer's MAX_HEADER_LIST_SIZE.** It was recorded but not enforced on response heads (#0044 Gotchas).
- **Request body size.** There was no limit (#0048 Gotchas).
- **Idle streams.** A stream error on an idle stream was answered with RST_STREAM, which RFC 9113 §6.4 forbids (#0050 Gotchas).

## Fix

- **Header list size (ours).**
  - `HTTP2RequestFieldSink` counts the list as §6.5.2 does: name + value + 32 per field.
  - Past `maxHeaderListSize` it stops storing and reports `fieldSectionTooLarge`. The stream is answered `431` without calling the handler. If a field before the limit was malformed, it is `RST_STREAM(PROTOCOL_ERROR)` instead.
  - HPACK and the block assembler accept up to `headerBlockLimit` (twice the advertised size), so such heads are still decoded and the dynamic table stays in step. Past it: `GOAWAY(ENHANCE_YOUR_CALM)` for the encoded block, `GOAWAY(COMPRESSION_ERROR)` for the decoded list.
  - Oversized trailers make the request malformed: `RST_STREAM(PROTOCOL_ERROR)`.
- **Header list size (the peer's).** `HTTP2SharedState.sendHeaders` computes the head's list size (`HTTP2ResponseHeadEncoder.listSize`, counting what would be sent). If it exceeds the peer's limit, a bare `:status 500` goes out with END_STREAM, and `write` sends no body.
- **Request body size.** New `HTTP2Configuration.maxRequestBodySize` (10 MiB, as in HTTP/3).
  - A larger `content-length` is answered `413` without the handler.
  - An undeclared body that grows past it fails the handler's read with `HTTPRequestBodyError.tooLarge`; a handler that throws it gets `413` instead of `500`.
  - Rejected streams (`431`, `413`) have no body. DATA still arriving is credited, and the stream is reset with `NO_ERROR` after the response (§8.1).
- **Idle streams.** `HTTP2StreamTable.isIdle`. A stream error on an idle stream (for example a PRIORITY frame that depends on itself) now closes the connection with that code.
- **MAX_CONCURRENT_STREAMS.** Unchanged, now covered by a connection test.

  - `streamErrorOnAnIdleStreamIsAConnectionError`, in the state machine and over a connection.

## Gotchas

- The HPACK decoder is the hard cap (twice the advertised limit); the advertised limit is enforced in the sinks. A head between the two costs decoding work but is never stored.
- A `431` is sent even when the required pseudo-headers come after the limit, because there is no request to validate any more.
- A bare `500` replaces the response; the handler's body is dropped, and `.file` bodies are closed as usual.
