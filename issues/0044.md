## Description

Build the `HTTP2Connection` runtime. A reader loop pulls frames from the `FrameParser` (#0035) and feeds a pure `HTTP2ConnectionStateMachine`. Connection state shared with stream tasks lives in a `Mutex` (Synchronization) with non-suspending critical sections, not an actor (ROADMAP §2). A single `FrameWriter` task drains an outbound queue.

## Scope

- `HTTP2ConnectionStateMachine` is a struct whose `mutating func handle(_ event:) -> Action` returns a single action (never `[Action]`), does no I/O and never awaits (CLAUDE.md).
- The `FrameWriter` is the only writer to the transport. HPACK encoding and frame enqueue happen in one `Mutex` critical section, so encoding happens in wire order and HEADERS + CONTINUATION frames are contiguous. Continuations are resumed outside the lock.
- The outbound queue is a `BoundedAsyncQueue` (#0073) that suspends producers when full; no `AsyncStream` for frame flow. Control-frame queue depth is tracked for #0056.
- The connection runs in `withThrowingDiscardingTaskGroup` with the writer and stream tasks as children. Reader end-of-input or error cancels the group.
- No Combine, and no unstructured `Task {}`.

## Acceptance criteria

- An in-memory transport test performs the preface and SETTINGS exchange and a clean close.
- A test proves that frames queued from many concurrent tasks never interleave inside a header block.

## Root cause

Feature work: frames, HPACK, streams, header blocks and the SETTINGS machine existed, but no runtime connected them to a transport.

## Fix

- **Driver** (`Sources/HTTP2/HTTP2.swift`, `HTTP2ConnectionDriver`). `HTTP2.run` serves one connection:
  - the **reader** is the connection's own task. It checks the preface and parses frames with `HTTP2FrameParser`. Every frame passes `HeaderBlockAssembler` first. Every complete block is HPACK-decoded: into an `HTTPRequestStorage` for dispatched streams, and into a discarding sink for refused, ignored and trailer blocks. Then the reader drives `HTTP2Connection`.
  - stream tasks, the settings timer and the shutdown watcher are children of one `withDiscardingTaskGroup`. The reader runs in that group's body. End of input, a transport error, or a connection error ends the reader, and the group is cancelled.
  - the **writer** is a sibling in an outer group. It outlives the streams so it can flush the final GOAWAY, and it then closes the transport with the queue's close reason. It is the only code that calls `send`.
  - there are no actors and no unstructured `Task {}`.
- **Shared state** (`HTTP2SharedState`) holds the machine, the HPACK encoder (`HTTP2ResponseHeadEncoder`) and the outbound queue in one `Mutex`. All of it is non-suspending.
  - A response head is HPACK-encoded and its HEADERS + CONTINUATION frames (split at the peer's MAX_FRAME_SIZE) are enqueued in one critical section.
  - `acknowledgeSettings` applies HEADER_TABLE_SIZE to the encoder and enqueues the ACK in the same critical section, in the same ordered lane.
  - Continuations to resume are collected as `HTTP2Wakeups` and resumed after the lock is released.
  - A stream is counted as active in the same critical section that decides to dispatch it, so a graceful drain never closes under it.
- **Outbound queue** (`HTTP2OutboundQueue`): two `ByteBuffer` lanes.
  - The *ordered* lane holds SETTINGS, SETTINGS ACK, HEADERS/CONTINUATION, DATA, RST_STREAM and GOAWAY in enqueue order.
  - The *priority* lane holds PING ACK and connection WINDOW_UPDATE.
  - The writer takes both and sends them with one `send` per drain. The first batch starts with our SETTINGS, which must be the first frame.
  - Stream writers (HEADERS, DATA) suspend while the ordered lane holds `outboundQueueSize` bytes (default 64 KiB). They wait on a generation counter, so no wakeup is lost, and cancellation removes the waiter.
  - Reply control frames never block the reader. More than `maxQueuedControlFrames` (default 1,000) queued and unwritten is `GOAWAY(ENHANCE_YOUR_CALM)`; this is the control-queue depth #0056 asked for.
- **Connection behaviour**:
  - PING gets a PING ACK with the same payload; an unsolicited PING ACK is ignored.
  - A connection error from the parser, assembler, HPACK, machine or flood limit gets one GOAWAY with its code. Its debug data is only the code name. The last-stream-ID is the highest stream processed. The connection then closes.
  - A server drain (`context.shutdown`) sends GOAWAY(NO_ERROR, last processed stream), serves the streams at or below it, and closes after the last one.
  - The settings timeout comes from #0043.
- **Minimal request path** for #0049 to build on (`Sources/HTTP2/HTTP2Message.swift`):
  - request heads are validated by `PseudoHeaderValidator`; a malformed head is RST_STREAM(PROTOCOL_ERROR);
  - one task per stream calls the handler;
  - response heads put `:status` first, use lowercase names, drop connection-specific fields, and add `content-length` when known; HEAD, 204 and 304 send END_STREAM on HEADERS;
  - `.bytes`, `.file` (`pread` chunks) and `.stream` bodies become DATA frames sized by both send windows and the peer's MAX_FRAME_SIZE; writers wait for WINDOW_UPDATE or a larger INITIAL_WINDOW_SIZE;
  - a handler error before HEADERS is a `500`; a body failure after HEADERS is RST_STREAM(INTERNAL_ERROR); `.tunnel` is answered `501` (#0067).
- **Not yet**:
  - request bodies (#0048): DATA is discarded and its connection credit returned once half the window is used; a stream still sending when its response ends is reset with NO_ERROR (§8.1);
  - cookie joining and `content-length` checks (#0047);
  - per-stream cancellation on RST_STREAM (#0051): the response is dropped, but the handler is not cancelled;
  - the PING round-trip on shutdown and idle timeouts (#0052);
  - stream receive windows (#0053);
  - fair window waiting (#0054): all waiters are woken and retry.

## Gotchas

- The outbound queue is not `BoundedAsyncQueue`. HPACK encoding and the enqueue must share one critical section, and `BoundedAsyncQueue.send` suspends, so it cannot run inside a `Mutex`. The queue lives inside the connection's `Mutex`. Producers check for space, encode and append synchronously, or wait on the generation counter and retry. It is bounded the same way.
- The priority lane may overtake the ordered lane, so only frames with no ordering constraint go there (PING ACK, connection WINDOW_UPDATE). RST_STREAM and the SETTINGS ACK must stay ordered behind the HEADERS they relate to. The first batch never lets the priority lane overtake, because our SETTINGS must lead.
- The writer closes the transport right after the final GOAWAY. There is no lingering close yet (#0052), so a peer whose unread data is still in flight may see a reset before it reads the GOAWAY.
- `waitForProgress` wakes every waiter on each drain and window change. That is correct but not fair; #0054 should replace it with per-stream waiters.
- Peer MAX_HEADER_LIST_SIZE is recorded but not yet enforced on response heads (#0055).
