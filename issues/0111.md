## Description

RFC 9220 bootstraps WebSockets over an HTTP/3 request stream using extended CONNECT. Reuse the `.tunnel` hook and #0109 unchanged. RFC 8441 over HTTP/2 stays in #0067.

## Scope

- Advertise `SETTINGS_ENABLE_CONNECT_PROTOCOL = 1` when the WebSockets component is registered (#0100).
- Accept `:method CONNECT` with `:protocol websocket`, `:scheme`, `:path`, `:authority`; respond `200` and keep the stream open; the stream becomes the `ByteStreamTransport` handed to `.tunnel`.
- Stream FIN and reset map to WebSocket close and abort.

## Acceptance criteria

- In-memory test over `InMemoryMultiplexedTransport`: extended CONNECT then a text echo and close handshake.
- If a client on this machine supports RFC 9220 (checked and recorded), an end-to-end echo; otherwise the resolution states that and relies on the in-memory test.

## Root cause

Not a defect: HTTP/3 answered every `.tunnel` response with `501`. The request decoder
dropped `:protocol` (so no handler could see an extended CONNECT), and nothing turned on
`SETTINGS_ENABLE_CONNECT_PROTOCOL` when a WebSocket component was registered.

## Fix

- `HTTPCore`:
  - `HTTPRequest.connectProtocol`: the `:protocol` value, empty otherwise; kept by `snapshot()`.
  - `ExtendedConnectProvider`, a marker protocol with `extendedConnectProtocols`.
  - `MiddlewareChainInspector.extendedConnectProtocols(in:)`.
- `HTTP3`:
  - `HTTP3.run` inspects the handler chain once per connection. With a provider in it,
    `enableConnectProtocol` is on and SETTINGS carries `SETTINGS_ENABLE_CONNECT_PROTOCOL = 1`.
  - `H3RequestHeadDecoder` keeps `:protocol` in the request. When we did not advertise the
    setting (RFC 8441 §3), `:protocol` is malformed (`H3_MESSAGE_ERROR`). The existing
    `PseudoHeaderValidator` requires `:scheme`, `:path` and `:authority` for an extended CONNECT.
  - A `2xx` with `.tunnel` for a CONNECT sends HEADERS without FIN, then runs the closure over
    `H3TunnelTransport`. Its `receive` returns the DATA payloads the body reader queues (with
    the same backpressure as a body); each `send` is one DATA frame through the response sink
    (send budget and send deadline); end of stream is FIN. The closure's `TunnelContext`
    carries the connection's drain signal (#0116). Request body limits do not apply to an
    extended CONNECT. `.tunnel` for any other request is still `501`.
  - Close and reset mapping:

    | Event | Tunnel side |
    |---|---|
    | peer FIN | receive returns 0 |
    | peer RESET_STREAM / STOP_SENDING | receive throws `connectionReset`; the tunnel is not cancelled |
    | `close(.normal)`, `close(.shutdown)` | FIN |
    | `close(.abort)`, `close(.timeout)`, `close(.protocolError)` | RESET_STREAM and STOP_SENDING `H3_REQUEST_CANCELLED` |

    With a running tunnel, a peer abort reaches the session through its receive instead of
    cancelling its task (`H3BodyChannel.beginTunnel`), so the WebSocket ends with 1006
    rather than mid-cancellation. The stream is then reset with `H3_REQUEST_CANCELLED`, as
    for any abandoned request.
- `WebSockets`: `WebSocketUpgrade` is an `ExtendedConnectProvider` (`websocket`).
  - On its path, `CONNECT` with `:protocol websocket` and `Sec-WebSocket-Version: 13`
    (`WebSocketHandshake.validateExtendedConnect`) is answered `200` with no
    `Upgrade`/`Connection`/`Sec-WebSocket-Accept`, but with the subprotocol and
    permessage-deflate headers, and runs the unchanged `WebSocket.run(over:)`.
  - A wrong version is `400` with `Sec-WebSocket-Version: 13`; HTTP/3 has no `Upgrade`, so no
    `426`. Another CONNECT is `400` (`Failure.notWebSocketConnect`).
- `Package.swift`: `HTTP3Tests` depends on `WebSockets` (one line).

## Gotchas

- The setting is decided per connection by walking the handler chain with dynamic casts:
  once per QUIC connection, never per request. Set `H3Configuration.enableConnectProtocol`
  to advertise it for a custom extended CONNECT handler that is not an
  `ExtendedConnectProvider`.
- The request stream's peer-abort watcher and body reader would normally cancel the
  handler's task. A WebSocket cancelled mid-session ends its `messages` before the reader
  records 1006, so the handler saw `closeCode == nil`. While a tunnel runs, aborts go through
  its receive instead.
- A client that sends data and then FIN without a Close frame races its own data. The server
  may see end of stream before the echo is sent, and `WebSocket.send` then throws `closed`. An
  echo handler that uses `try` ends on that error, not at the end of the loop.
- A client that resets a WebSocket stream counts toward `H3AbuseLimits` rapid-reset
  accounting, like any abandoned request. A normal close (Close frames, then FIN) does not.
- #0067 (RFC 8441 over HTTP/2) can reuse all of this: `WebSocketUpgrade` already answers
  extended CONNECT, and the HTTP/2 runner needs the same `connectProtocol` and
  `TunnelContext` plumbing.
