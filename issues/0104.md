## Description

Harden HTTP/3 the way #0051, #0052 and #0056 harden HTTP/2.

## Scope

- Cancellation bridging: peer reset or STOP_SENDING cancels the request's child task (handler sees `CancellationError`, files close); local cancellation or a throwing body resets the stream with `H3_REQUEST_CANCELLED` / `H3_INTERNAL_ERROR`.
- Graceful shutdown end to end with GOAWAY, drain deadline and QUIC close with `H3_NO_ERROR`.
- Abuse limits: rapid stream open/reset, unknown-frame and reserved-stream floods, oversized or slow field sections, QPACK encoder-stream floods, idle streams that never send HEADERS; each with a counter and threshold that closes with `H3_EXCESSIVE_LOAD`.

## Acceptance criteria

- One in-memory test per abuse pattern asserting the close code and bounded memory.
- A test resets a stream mid-download and asserts the handler task finished and the connection still serves another stream.

## Root cause

HTTP/3 had no limits on what a hostile client can make the server do for free (reset request streams as fast as credit returns, open reserved uni streams, repeat no-op QPACK instructions, flood control or unknown frames, stall reads), and a peer abort was only noticed by the next stream read or write: a handler still computing after the request ended was never cancelled, and a cancelled handler ended its stream with a bare FIN.

The flaky `goawayLetsTheInFlightRequestFinishAndRejectsNewStreams` was a test race, not a server bug: an in-memory stream reaches the server when it is opened, so after GOAWAY the server can reject it (RESET_STREAM + STOP_SENDING) before the client's HEADERS send runs, and that send then throws `connectionReset`. `H3TestClient.send` let the error escape instead of reading the rejection.

## Fix

- `H3AbuseLimits` (`H3Configuration.abuseLimits`), checked by `H3AbuseMonitor` under the connection lock, one fixed 10 s window per count: aborted requests (rapid reset, 100), ignored uni streams (16), QPACK instructions (1,000), control frames (1,000), unknown request-stream frames (1,000), each `H3_EXCESSIVE_LOAD`; `maxUnknownFrameLength` (16 KiB, `H3FrameParser`) `H3_EXCESSIVE_LOAD`; `maxConnectionSendBuffer` (4 MiB, `H3SendBudget`) plus `H3Timeouts.send` (30 s) reset a slow reader's streams with `H3_REQUEST_CANCELLED`; `maxIdleConnections` (1,000 per `HTTP3` value, `H3ConnectionTracker`) gracefully shuts down the longest-idle connection.
- Cancellation: new HTTPCore protocol `PeerAbortObserving` (`waitForPeerAbort()`), adopted by `QUICStreamTransport` (resumes on the stream failing, which NW does on a peer abort) and the in-memory stream. Each request runs a watcher next to the body reader and the handler; a peer abort cancels both. Requests the peer abandoned, or whose handler was cancelled or threw `CancellationError`, are reset with `H3_REQUEST_CANCELLED` (`H3Failure.requestCancelled`); a body writer failing after the head stays `H3_INTERNAL_ERROR`.
- `H3ConnectionTracker` debug counters: live connections, request streams, handlers, body channels.
- `H3TestClient.send` reads the server's reset code when its HEADERS send fails because the server already refused the stream.
- Spike Q6 answered: Network.framework sends no application CONNECTION_CLOSE; documented as a known limitation in `docs/notes/nw-transport.md`.

## Verification

- `H3AbuseLimitsTests` (11 tests, 13 cases): each limit closes with `H3_EXCESSIVE_LOAD` just past its threshold and not at it, the slow-reader streams are reset with `H3_REQUEST_CANCELLED` while per-stream bytes stay within the stream buffer and connection-wide stalled bytes within the budget, the idle eviction sends GOAWAY + `H3_NO_ERROR` to the oldest connection only.
- `H3CancellationTests` (6 tests, 7 cases): reset while the handler computes (CancellationError, stream reset `H3_REQUEST_CANCELLED`), reset mid-download (writer ends, next stream served), reset mid-upload, handler cancellation resets with `H3_REQUEST_CANCELLED`, throwing writer resets with `H3_INTERNAL_ERROR`, and 1,000 abandoned requests (half computing, half uploading): 1,000 handlers cancelled, and 0 live request streams, handlers and body channels afterwards.
- `H3QUICCancellationTests` (2): the same over real NW QUIC with a `QUICConnection` client (reset and forceCancel).
- `QUICCloseCodeTests` (4): curl through a UDP relay, server packets decrypted with curl's key log.
- Flaky test, 50 runs each under 12 × `yes` plus other agents: before 1/50 failed (`connectionReset` at 0.004 s; load average 14 rising to 94), after 0/50 (load average 18 rising to 115); the four touched HTTP/3 suites also passed 10/10 under the same load.
- Full `swift test -j 2`: all targets passed except two existing NW QUIC timing tests in `NetworkTransportTests` (`echoUniAndResetAgainstARawNWClient`, `connectionCloseFailsStreamsAndEndsInboundOnBothSides[quic]`) at load average about 70; both passed 8/8 when rerun at load 10–28.

## Gotchas

- Network.framework never puts our code on the wire: after the group is cancelled it sends only stream resets/STOP_SENDING (code 0) and a FIN on a server-initiated stream 1 it never opened; the peer closes itself, and the only server CONNECTION_CLOSE seen is transport NO_ERROR. Every `H3_EXCESSIVE_LOAD` and `H3_NO_ERROR` close looks like a plain teardown to an NW peer. Assert close codes over the in-memory transport.
- curl and NW negotiate TLS_AES_256_GCM_SHA384 on loopback (48-byte secrets, HKDF-SHA384); curl's connection IDs are 20 bytes, NW's 8.
- A peer abort fails an NW stream even with nothing pending (`.failed(ECONNRESET)`), which is what `waitForPeerAbort()` relies on. A raw NW receive after FIN completes at once with `ENOMSG`, so polling would not work.
- The in-memory pipe toward a peer is sized by the *receiver's* stream configuration, so per-stream send buffering in tests follows the client's `bufferCapacity`.
- NW's own per-stream send buffer (about 4 MiB) is still unbounded by the API; `maxConnectionSendBuffer` bounds only bytes inside our sends, and `timeouts.send` bounds how long a slow reader holds NW's buffers.
- `H3UniStreamType.reserved(n)` stores the raw type value, not N: a test that builds GREASE stream types must compute 0x21 + 0x1f·N itself.
- Swift Testing's `#expect(throws:)` printed a garbage value for an `HTTP3Error` thrown through `withUnsafeBytes` with typed throws; wrap the call in a `Result` instead.
- Each send now also takes the connection's send-budget lock and the watch's send-deadline lock (four extra uncontended lock operations per send). Not benchmarked (load average 15–90 during this work); measure with the M10 load numbers (#0106).
- `PeerAbortObserving` is a small addition to HTTPCore (outside the HTTP3/NetworkTransport scope), needed so both transports can adopt it.
