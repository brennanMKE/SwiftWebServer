## Description

`If-Modified-Since` never matches because of sub-second mtimes (#0017), `If-None-Match` ignores lists and wildcards and does not take precedence (#0019), and non-200 responses always get an HTML error body including 304 (#0018). Implement RFC 9110 §13.2.2 precondition evaluation and an error-page middleware that respects body rules.

## Scope

- Evaluation order: `If-Match`, `If-Unmodified-Since`, `If-None-Match`, `If-Modified-Since`, `If-Range`; `If-None-Match` lists, `*`, weak comparison for GET/HEAD; `If-Modified-Since` ignored when `If-None-Match` is present (#0019).
- Dates compared at whole-second precision with IMF-fixdate parsing by fixed offsets (#0017).
- `412 Precondition Failed` where required; `304` carries `ETag`, `Last-Modified`, `Cache-Control`, `Date` and no body.
- Error-page middleware: configured HTML pages for 4xx/5xx only, never for 1xx/204/304 or HEAD bodies (#0018 part).

## Acceptance criteria

- Tests reproduce #0017, #0018 and #0019 and pass, plus one test per RFC 9110 §13.2.2 step.
- `curl -I -H 'If-None-Match: "<etag>"'` returns 304 with no body; `curl -z <file>` returns 304 for an unmodified file.

## Root cause

The legacy server compared the whole `If-None-Match` value to one ETag, fell through to `If-Modified-Since` when it did not match, compared a sub-second mtime with a whole-second date (`modDate <= sinceDate` never true for an echoed `Last-Modified`), and `HTTPResponse.init` replaced every non-200 body with an HTML page, 304 included. The new stack's StaticFiles (#0084) had validators but no precondition handling and empty error bodies.

## Fix

- `ConditionalRequest` (StaticFiles, public, reusable by any handler): `evaluate(method:fields:etag:lastModified:representationExists:)` runs RFC 9110 §13.2.2 steps 1-4 (If-Match strong; If-Unmodified-Since only without If-Match; If-None-Match weak with lists over several fields, `*`, `W/`; If-Modified-Since only without If-None-Match and only for GET/HEAD) and returns `.proceed`, `.notModified` or `.preconditionFailed`. `ifRangeAllowsRange` is step 5 (strong tag or exact date). Invalid dates and date fields sent twice are ignored. Walks list elements in place; no allocation.
- `HTTPDate.parse`: IMF-fixdate, RFC 850 and asctime by fixed offsets, no Foundation; rejects impossible dates. Comparisons use the mtime truncated to seconds, the instant `Last-Modified` renders (#0017).
- `CachedFile` pre-renders a `304` (ETag, Last-Modified, Cache-Control, `.empty` body, no Content-Length; the connection adds Date). StaticFiles evaluates preconditions after its 400/403/404/405 checks and before Range; a 412 is a static response.
- `StaticFilesConfiguration.maxAge` renders `Cache-Control: public, max-age=N` (legacy `caching.maxAge`); `cacheControl` still wins.
- `ErrorPages` middleware: fills only empty-bodied 4xx/5xx responses without a Content-Length, never for HEAD, keeps the handler's fields, sets `Content-Type: text/html; charset=utf-8`. Default pages are generated once per registered status; `init(root:pages:defaultPages:)` loads files under a root at startup (realpath containment, errors for missing, outside-root or non-4xx/5xx entries).

## Gotchas

- `ConditionalRequest` and `HTTPDate` live in StaticFiles, not HTTPCore. Move them to HTTPCore if another component needs preconditions without depending on StaticFiles.
- `If-Range` with a date matches on equality only; RFC 9110 §13.1.5 also asks that the date be strong (Last-Modified at least a second before Date), which is not checked.
- RFC 850 two-digit years map to 1970-2069 instead of the RFC's "50 years in the future" rule.
- 404s from StaticFiles fall through to `next`, so `If-Match: *` on a missing file is not answered 412 here.
- ErrorPages gives HEAD error responses no Content-Length (they pass through untouched).
