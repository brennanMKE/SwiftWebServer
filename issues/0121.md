## Description

Add a `ReverseProxy` middleware component that forwards requests matching a **mount** (path prefix and/or host) to an upstream, using the client from #0120. Requests that don't match fall through to the next component, so a static site at `/` and an app at `/cgi-bin` work together.

The owner's use case: run app servers (for example Go `net/http`) on localhost, with this server as the public TLS endpoint serving HTTP/1.1, HTTP/2 and HTTP/3. A static website is served at `/`, and a path prefix such as `/api` (or `/cgi-bin`) is reverse-proxied to a web app. The reference upstream is the Go app in `Examples/go-api` (Go 1.27 is installed). This is what Apache `mod_proxy` (`ProxyPass` / `ProxyPassReverse`) does today.

## Scope

- Mounts:
  - A path prefix matched on segment boundaries, so `/cgi-bin` matches `/cgi-bin` and `/cgi-bin/x` but not `/cgi-binx`. Matching happens after percent-decoding, with the same traversal and normalization rules as StaticFiles, so `/%63gi-bin` and `/cgi-bin/../x` can't bypass a mount or the auth in front of it.
  - Optional host match, and composition with VirtualHosts.
  - Longest prefix wins. Mounts are compiled once at startup, with no allocation per match.
- Path mapping: `stripPrefix` (send `/cgi-bin/foo` as `/foo`), or keep the full path, plus an optional upstream base path (`http://127.0.0.1:9000/app`). The query string passes through unchanged.
- Request headers:
  - Remove hop-by-hop headers (`Connection` and the headers it names, `Keep-Alive`, `TE`, `Trailer`, `Transfer-Encoding`, `Upgrade` except for #0123, `Proxy-*`).
  - Set `X-Forwarded-For` (append), `X-Forwarded-Proto`, `X-Forwarded-Host` and `X-Forwarded-Prefix` (the mount path), and/or RFC 7239 `Forwarded`, as configured.
  - `preserveHost`: send the client's `Host`, or the upstream's.
  - Incoming `X-Forwarded-*` from untrusted clients is replaced, not appended, unless the peer is in a configured trusted-proxies list.
- HTTP/2 and HTTP/3 downstream: map pseudo-headers to an HTTP/1.1 request upstream. The response comes back over whichever protocol the client used.
- Response handling:
  - Remove hop-by-hop headers.
  - `rewriteLocation` (like `ProxyPassReverse`): rewrite absolute `Location`/`Content-Location` pointing at the upstream, and add the prefix back when it was stripped.
  - Optional cookie path rewriting.
  - Streamed body; 1xx (except 101) handled correctly.
- Composes with the other components: Auth in front, Compression and AccessLog around it. A proxied response with `Content-Encoding` is left alone by Compression.

## Acceptance criteria

- Tests for prefix matching on segment boundaries, encoded or traversal paths not bypassing a mount, strip vs keep, query pass-through, every forwarded header including the untrusted-client replacement, hop-by-hop removal both ways, Location rewriting, and requests arriving over h2 and h3 forwarded as HTTP/1.1.
- Integration test: StaticFiles at `/` and the proxy at `/api` on the same server. `curl /index.html` comes from disk and `curl /api/echo?x=1` comes from the upstream (the Go app `Examples/go-api` when `go` is installed, otherwise a Swift test upstream), with the expected forwarded headers echoed back.

## Root cause

The WIP component (8b197d8) always replaced incoming forwarded fields (no trusted-proxies
list), matched mounts by building and normalizing a `String` for every request (also for the
static files it passes through), filtered headers through lowercased `String`s, had no cookie
path rewriting, and had no tests over h2 or h3.

## Fix

- `ProxyMount.trustedProxies` (`IPAddressRange`: IPv4/IPv6 address or CIDR, IPv4 mapped,
  parsed with `inet_pton` into a `UInt128`; config `trustedProxies`). From a trusted peer
  `X-Forwarded-For` and `Forwarded` are appended to and `X-Forwarded-Proto`/`-Host` passed on;
  from anyone else all are replaced. `X-Forwarded-Prefix` is always the mount path.
- Request and response header filtering on field IDs and bytes: hop-by-hop names, `Proxy-*`
  and `Connection`-listed names (any case), pseudo-headers, `Host`, `Expect`.
- Mounts compile prefix and host bytes once. `lookup` matches a raw path that is already
  normalized (no `%`, NUL, dot segment or non-ASCII byte) on its bytes with no allocation; any
  other path takes the decode-and-normalize slow path, so encodings and traversal cannot
  bypass a mount. Host mounts compare `:authority`/`Host` bytes without the port.
- 1xx: interim responses other than 101 (`100 Continue`, `103 Early Hints`) are consumed by the
  upstream client and not relayed: the downstream protocols answer `Expect: 100-continue`
  themselves when the proxy reads the body and have no interim-response API, and early hints
  are advisory. `Expect` is not forwarded upstream. Documented in README and the client.
- `rewriteCookiePath`: with `stripPrefix` or an upstream base path, `Set-Cookie` `Path` is
  mapped into the client's path space (base removed, prefix added; outside the base: kept).

## Gotchas

- A matching request still allocates: the decoded path and upstream target `String`s
  (`UpstreamRequest` is `String`-based), the rewritten fields, and the forwarded values
  (`makeUpstreamRequest`: 7 allocations in release).
- `trustedProxies` is per mount, not server-wide (config lives in the `proxy` key).
- Cookie rewriting only touches `Path`, not `Domain`.
