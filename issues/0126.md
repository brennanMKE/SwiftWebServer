## Description

Found while writing the developer guides. The handler-chain builder examples in the doc comments of `Router.swift`, `Server.swift`, `Authenticator.swift`, `WebSocketUpgrade.swift` and in `docs/MIDDLEWARE.md` fail with "ambiguous use of 'buildBlock'" when the last element is `StaticFiles`, `Router` or `VirtualHosts`, because those types conform to both the middleware and the handler protocols. The guides work around it by passing the last element through a function returning `some HTTPHandler`.

## Scope

- Make the builder unambiguous (for example, a `buildFinalResult`/overload ranking, or separate terminal wrappers), so the natural form compiles.
- Fix the doc-comment examples and `docs/MIDDLEWARE.md`; drop the workaround from `docs/guide/` once it isn't needed.

## Acceptance criteria

- A compile test (a test target file) builds each documented chain shape, including each of the three types as the last element.

## Relation

- **Milestone:** M17 follow-ups (deployment readiness)
- **Blocked by:** none
- **Blocks:** none

## Root cause

`MiddlewareBuilder` had two overload families per block size: middlewares ending in an
`HTTPHandler` (`MiddlewareChain`) and middlewares only (`ComposedMiddleware`). A type that
conforms to both protocols matches both as the last argument, and neither overload is more
specialized than the other (`H: HTTPHandler` and `M: HTTPMiddleware` are unrelated), so the
call was ambiguous. `buildFinalResult`, `buildOptional` and `buildEither` had the same problem.

## Fix

- New overloads take a component constrained `HTTPHandler & HTTPMiddleware`: `buildBlock`
  with it last (1-10 elements), `buildOptional`, `buildEither` and `buildFinalResult`. A
  type satisfying both constraints can be passed to either older family but not vice versa,
  so overload ranking picks the new one. They build what the handler family builds, so the
  last component is the terminal handler (the old `terminal(_:)` workaround's meaning); in
  any other position it is matched only as a middleware, as before.
- `OptionalMiddleware` conforms to `HTTPHandler` when its wrapped type does (`404` when
  absent), and `EitherHandler` to `HTTPMiddleware` when both branches do, so `if`/`if-else`
  over dual types works last or in the middle.
- Doc comments (`VirtualHosts.swift` dropped `as some HTTPHandler`), `docs/MIDDLEWARE.md`,
  `docs/guide/`, `README.md` and `Examples/custom-server` no longer use the workaround.

## Verification

- `Tests/VirtualHostsTests/BuilderShapeTests.swift` (17 tests) compiles each documented chain
  (Server, Authenticator, WebSocketUpgrade, Router, VirtualHosts, VirtualHost chains, the
  custom-server example) with StaticFiles, Router and VirtualHosts last, alone, in the middle,
  ten elements deep, and under `if`/`if-else`, and pins the built types exactly.
- `swift build`, `scripts/guarded.sh -t 900 -- swift test -j 2`: 1624 tests passed (4 known
  issues, pre-existing HTTP/3 curl observations). `Examples/custom-server` builds.
- Hot path: no benchmark run. Chains that compiled before get the same overloads and types;
  dual-last chains now build `MiddlewareChain<…, StaticFiles>`, the same type the workaround's
  opaque `some HTTPHandler` produced. No new existentials or wrappers.

## Files changed

- `Sources/HTTPCore/MiddlewareBuilder.swift`: dual-type overloads, conditional conformances.
- `Package.swift`: `VirtualHostsTests` test dependencies (one line).
- `Tests/VirtualHostsTests/BuilderShapeTests.swift`: new.
- `Sources/VirtualHosts/VirtualHosts.swift`, `docs/MIDDLEWARE.md`,
  `docs/guide/choosing-components.md`, `docs/guide/dynamic-sites.md`, `README.md`,
  `Examples/custom-server/Sources/MySite/MySite.swift`: workaround removed.

## Gotchas

- `ConfigFile` still has its own `handler(_:) -> some HTTPHandler` helper; it is harmless and
  was left alone (another worker owns that target).
- An `if` without `else` over a dual type is an `OptionalMiddleware`; as the last element it
  answers `404` when absent, in the middle it passes requests on.
