## Description

Implement the stream lifecycle from RFC 9113 §5.1.

## Scope

- States: idle, reserved (local), open, half-closed (local), half-closed (remote), and closed. Transitions happen on HEADERS, DATA, END_STREAM, and RST_STREAM in both directions.
- Client-initiated streams must use odd, monotonically increasing ids (§5.1.1). A reused or lower id is a `PROTOCOL_ERROR`.
- Receiving implicitly closes idle streams with lower ids.
- Frames on closed streams follow §5.1: STREAM_CLOSED stream errors, a grace window for frames that were in flight after a reset the server sent, and ignoring WINDOW_UPDATE and RST_STREAM there.
- Frames other than HEADERS and PRIORITY on an idle stream are connection `PROTOCOL_ERROR`s.

## Acceptance criteria

- Table-driven tests enumerate state × frame × direction and assert the resulting state or error.

## Root cause

Feature work: the HTTP2 target had frames, errors and stream identifiers (#0034, #0036) but no stream lifecycle or identifier bookkeeping.

## Fix

- `HTTP2Stream`: a value-type state machine, `mutating func handle(_ event: Event) -> Action`, covering every RFC 9113 §5.1 state. It takes frames received and sent (HEADERS as a complete block, DATA, PRIORITY, RST_STREAM, WINDOW_UPDATE, PUSH_PROMISE on the promised stream) and returns one action: `proceed`, `ignore`, `streamError(code)` or `connectionError(code)`. A stream error has already moved the stream to `closed(.resetSent)`. `closed` carries a reason, because the rules for late frames differ:
  - `resetSent`: everything the peer had in flight is ignored.
  - `resetReceived`: late DATA/HEADERS is a stream `STREAM_CLOSED` error, answered once and then ignored.
  - `endStream`: late DATA/HEADERS is a connection `STREAM_CLOSED` error.
  - WINDOW_UPDATE and RST_STREAM are always ignored, so RST_STREAM is never answered with RST_STREAM. PRIORITY is accepted in every state.
  - Reserved states follow §5.1 for both directions (connection `PROTOCOL_ERROR` for forbidden received frames), though a server without push never enters them.
  - Sending a frame the state forbids is `INTERNAL_ERROR`. Sending on a closed stream is `ignore`, because a response can race the peer's reset.
  - A second received HEADERS without END_STREAM is a stream `PROTOCOL_ERROR` (§8.1: trailers end the stream).
- `HTTP2StreamTable`: the server's identifier rules.
  - Client streams are odd and increasing. Reusing a lower identifier is a connection `PROTOCOL_ERROR`, and opening a stream implicitly closes the idle ones below it.
  - HEADERS on an even stream, stream 0 or PUSH_PROMISE is a connection `PROTOCOL_ERROR`, as is anything but HEADERS/PRIORITY on an idle stream. PRIORITY does not open a stream or use up its identifier.
  - HEADERS beyond SETTINGS_MAX_CONCURRENT_STREAMS is refused with `REFUSED_STREAM`. The identifier is used up and the frames the client already sent on it are ignored.
  - `goawaySent(lastStreamID:)` sets a bound that can only be lowered, ignores frames above it, and closes active streams above it.
  - Storage: one open-addressed table (Fibonacci hash, linear probing, backward-shift deletion, at most half full) holds both live and recently closed streams. Its size is fixed at init from `maxConcurrentStreams + recentlyClosedCapacity`. A fixed ring evicts closed streams oldest first. A stream at or below the highest ID that is not in the table is treated strictly (it is either long closed or was never opened): HEADERS → connection `PROTOCOL_ERROR`, DATA → stream `STREAM_CLOSED`, WINDOW_UPDATE/RST_STREAM ignored.

## Gotchas

- The closed-stream "grace window" is count-based, not time-based (the machine has no clock): a closed stream is remembered until `recentlyClosedCapacity` newer streams have closed. A connection that wants a time limit can lower the capacity or evict on a timer later.
- HPACK must still decode header blocks the table answers with `ignore` or a stream error (refused streams, streams above GOAWAY), and received DATA it ignores still counts toward connection flow control. That is the connection's job (#0046, #0053).
- After a `streamError` the stream is already `closed(.resetSent)`. Do not feed the RST_STREAM back in as a sent frame; it would be ignored anyway.
