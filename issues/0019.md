# 0019 — If-None-Match ignores lists and wildcards and does not take precedence over If-Modified-Since

| | |
|---|---|
| **Status** | open |
| **Module** | Semantics |
| **Platform** | macOS |
| **First seen** | 2026-09-12 |

## Description

The `If-None-Match` handling (`HTTPServer.swift:229-243`) compares the whole header against one ETag after trimming quotes. It does not handle a list (`W/"a", W/"b"`) or `*`. When `If-None-Match` is present but does not match, the code falls through to the `If-Modified-Since` check, but RFC 9110 §13.1.3 requires `If-Modified-Since` to be ignored whenever `If-None-Match` is present. Once #0017 is fixed, a stale ETag plus a recent date will wrongly return 304.

## Steps to reproduce

1. `curl -si http://localhost:8080/index.html -H 'If-None-Match: W/"stale", <current etag>'` returns 200, but it should return 304.

## Expected behavior

Weak comparison against each entity tag in the list, `*` matches any existing file, and `If-Modified-Since` is evaluated only when `If-None-Match` is absent.

## Actual behavior

Only an exact single-value match works, and the evaluation order is wrong.

## Notes

This is the precondition order from RFC 9110 §13.2.2. `If-Match` and `If-Unmodified-Since` are not supported, which is acceptable for GET/HEAD-only serving.
