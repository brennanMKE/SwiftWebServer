## Description

The legacy server ignores request bodies, sends a body on HEAD (#0016), replaces 304 bodies with an HTML error page (#0018) and has no size limit on bodies (#0011). Add demand-driven request bodies and streaming responses with the correct body rules.

## Scope

- `HTTPRequestBody`: `AsyncSequence` of `ByteBuffer` whose `next()` performs the read; `.empty` costs nothing. `Content-Length` bodies and a `ChunkedDecoder` state machine (chunk extensions ignored, trailers parsed and bounded).
- Unread body bytes are drained (up to a limit) or the connection is closed before the next request.
- `Expect: 100-continue`: `100 Continue` sent only when the handler starts reading the body; `417` for unknown expectations.
- Body size limit → `413 Content Too Large` and close (#0011 part).
- `HTTPResponseBody` `.bytes`, `.file(FileRegion)` via `sendFile`, and `.stream(length:writer)` with chunked encoding when length is unknown; writer backpressure through `send` completion.
- HEAD: headers as for GET including `Content-Length`, no body bytes (#0016); 1xx, 204 and 304 never carry a body or chunked framing (#0018 part).
- Streaming-body parts of #0030.

## Acceptance criteria

- In-memory tests: chunked body split at every byte offset decodes identically; trailers exposed; oversized body → 413 and close; `Expect: 100-continue` sends 100 only when the body is read; HEAD response byte-compared with GET minus body; 304 and 204 contain no body.
- `curl -T` of a 50 MB file to an echo-length handler reports the right length with server RSS flat (bounded buffer).

## Root cause

The legacy server never read request bodies, had no size limit (#0011), always appended the body
(HEAD included, #0016) and replaced non-200 bodies with an HTML page (#0018, 304 included). The
new stack (#0080) answered any request with content with 413/501 and close, and `.stream`
responses like a handler error, as hooks for this issue.

## Fix

- `HTTPRequestBody` (`Sources/HTTPCore/HTTPRequestBody.swift`, moved out of `HTTPMessage.swift`):
  `.empty` (free) or a stream over an `HTTPRequestBodySource`, whose `nextChunk(request:)` performs
  the read. Adds `knownLength`, `trailers`, `collect(upTo:)`, `HTTPRequestBodyError` (`tooLarge`,
  `malformed`, `truncated`, `expired`, `concurrentRead`) and `HTTPBodyWriterError`.
- `ChunkedDecoder` (`Sources/HTTP1/ChunkedDecoder.swift`): pure, span-driven, split-invariant
  state machine. Returns data ranges inside the input (no copy), validates and ignores chunk
  extensions, validates trailer lines (no obs-fold) and hands their raw bytes out; limits for
  chunk size, extension length, trailer bytes and fields; strict CRLF (bare LF, CR without LF,
  missing CRLF after data are errors); bad hex and 64-bit overflow rejected.
- `HTTP1RequestBodyReader` (`Sources/HTTP1/HTTP1RequestBodyReader.swift`): one per connection,
  created on the first body, borrowing the runner's transport and receive buffer while the
  handler runs. Bytes that arrived with the head come from the receive buffer; then one receive
  per `next()`. Content-Length reads never ask for more than the body owes; chunked bodies receive
  into the reader's own buffer and return any bytes past the last chunk to the receive buffer when
  the request ends. Chunks are one reused buffer of at most `receiveSize` bytes. `100 Continue` is
  sent on the first read that must receive (skipped if body bytes already arrived). Bodies expire
  when the handler returns (generation id).
- `HTTP1Connection`: `bodyNotSupportedStatus` is gone. `maxBodySize` gives 413 before the handler
  for a larger Content-Length; `Expect` other than `100-continue` gives 417 (ignored on HTTP/1.0);
  new events `bodyFailed` (413/400 + close), `bodyUnread(drainable:)` → `readingBody` +
  `drainBody`, `bodyDrained(complete:)`, `responseBodyFailed` (abort); `Exchange` carries
  `hasBody`/`expectsContinue`; response contexts carry the request version.
- `HTTP1` runner: flushes earlier pipelined responses before a `100-continue` request; after the
  handler, drains an unfinished body up to `maxDrainSize` (default 64 KiB) or marks the response
  `close` (also for a malformed body or a `100-continue` body never asked for). `.stream` bodies
  are sent by `HTTP1ResponseBodyWriter` after the head is flushed: one `send` per write
  (backpressure), Content-Length with an over/under-length check, chunked for unknown length,
  close-delimited for HTTP/1.0 (new `HTTP1BodyFraming.closeDelimited`); a writer that throws or
  mismatches aborts the connection. HEAD/204/304 run no writer and send no file; the serializer's
  header rules from #0076 apply.
- `HTTP1Configuration`: `maxBodySize` (default 10 MiB), `maxDrainSize`, `chunkedLimits`.
- `sws-bench serve`: `ServeHandler` echoes `POST` bodies and answers `PUT` with the body length;
  `--max-body-size`. `HelloHandler` stays suspension-free for `h1conn`.

## Gotchas

- Request bodies are readable only while `handle` runs (as the ROADMAP's request lifetime says):
  a `.stream` writer cannot read the request body, so a streaming echo is not possible yet.
- The body source is an existential (`any HTTPRequestBodySource`, one witness call per chunk), a
  second exception beside `.stream` bodies to the no-existentials rule; `.empty` never touches it.
- Unread bodies are drained before the response is written, so the `connection` header is final
  when serialized. A chunked rest beyond the drain limit closes the connection.
- With `Expect: 100-continue` and a handler that does not read, the response says `close` and the
  connection closes without reading; a client that already sent the body may see a reset if the
  kernel discards unread bytes (no lingering close yet; #0082).
- HEAD/304 with `.empty` or an unknown-length stream carry no `content-length` (the length is not
  known without running the writer); a handler can set it explicitly (#0076 rules).
- `h1conn` pipelined is about 8% slower than on `main` (larger `HTTPRequest`, `Expect` summary,
  bigger exchange state); still 0 allocations. Worth re-checking at the milestone gate.
- `Array.span` needs macOS 26: tests go through `ByteBuffer.withReadableSpan`.
