## Description

The package has one library target, a stub WebSocket test-suite target and no test target, so nothing can be verified and parallel worktrees would all have to edit `Package.swift`. Restructure the package once so every roadmap target from ROADMAP §5.1 exists, the legacy server keeps building and shipping until M4, and `swift test` runs real tests.

## Scope

- Move `SwiftWebServerCore` sources into a `Legacy` target; the `SwiftWebServer` executable keeps depending on it until #0086.
- Declare every §5.1 target with a stub source file: `HTTPCore`, `HTTP1`, `HTTPServer`, `NetworkTransport`, `HeaderCompression`, `HPACK`, `HTTP2`, `QPACK`, `HTTP3`, `WebSockets`, `StaticFiles`, `Compression`, `VirtualHosts`, `Auth`, `AccessLog`, `Router`, `ConfigFile`, `sws-bench` (executable) and `HTTPTestSupport`. Dependencies follow §5.1: `HTTPCore` imports neither Network nor Foundation; only `NetworkTransport` and `ConfigFile` import those frameworks.
- One Swift Testing test target per source target plus `IntegrationTests` and a `LegacyTests` target, each with at least one real test (not a placeholder `#expect(true)`); `LegacyTests` covers the legacy parser so the legacy bugs have a home until parity.
- Delete `SwiftWebSocketsTestSuite` and `File.swift` stubs (ROADMAP §3).
- Bump `swift-tools-version` to the lowest version that supports package traits (6.1) and set Swift 6 language mode, strict concurrency and `.macOS(.v15)` for every target.
- Check whether `Span`/`RawSpan` are available for the macOS 15 deployment target with the installed toolchain (Swift 6.4.2) and record the answer in `docs/ROADMAP.md` §7 notes so #0073 knows whether to use them or fall back to `UnsafeRawBufferPointer`.
- Declare package traits for `HTTP2`, `HTTP3` and `WebSockets` so the CLI can compile them out (they may be no-ops until those tracks land).

## Acceptance criteria

- `swift build` and `swift test` succeed; the test output lists test names from every test target and a passing summary.
- `ROOT_PATH=$PWD/Root swift run SwiftWebServer` still serves `curl -v http://localhost:8080/` from the `Legacy` target.
- `grep -r 'import Network\|import Foundation' Sources/HTTPCore` returns nothing.
- The `Span` availability result is written down with the exact compiler error or success observed.

## Root cause

The single `SwiftWebServerCore` target mixed every concern, so parallel milestone work would have collided in one module and in `Package.swift`.

## Fix

Legacy code moved to a `Legacy` target that backs the unchanged executable. Every roadmap target is declared from one table in `Package.swift`, with a placeholder type and a Swift Testing target each. Tools-version is 6.4, with HTTP2/HTTP3/WebSockets traits declared. Span findings are in `docs/notes/span-availability.md`.

## Verification

`swift build`, `swift build -c release`, and `swift test` on merged `main` (8a938a2): 49 tests across 20 test targets passed, including 8 real LegacyTests covering the parser and config. The legacy server answered `curl /` with 200.

## Files changed

- `Package.swift`: table-driven target list, traits, upcoming features
- `Sources/Legacy/*`: moved from `Sources/SwiftWebServerCore`
- `Sources/<Target>/*Module.swift`: placeholders for every roadmap target
- `Tests/*`: one test target per library, plus `IntegrationTests` and `LegacyTests`
- `docs/notes/span-availability.md`, `Tests/HTTPCoreTests/SpanAvailabilityTests.swift`: Span/InlineArray findings

## Gotchas

On macOS 15, `Span`, `RawSpan` and `MutableSpan` work when built from unsafe buffer pointers. `Array.span` and `InlineArray` need macOS 26. Returning a span from a function needs the experimental `Lifetimes` feature. `InternalImportsByDefault` and `ExistentialAny` are off for Legacy.
