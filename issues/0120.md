## Description

There is no client side for talking to an upstream (backend) HTTP server. A reverse proxy needs an HTTP/1.1 client with a pool of keep-alive connections to upstreams on loopback TCP and on Unix domain sockets.

The owner's use case: run app servers (for example Go `net/http`) on localhost, with this server as the public TLS endpoint serving HTTP/1.1, HTTP/2 and HTTP/3. A static website is served at `/`, and a path prefix such as `/api` (or `/cgi-bin`) is reverse-proxied to a web app. The reference upstream is the Go app in `Examples/go-api` (Go 1.27 is installed). This is what Apache `mod_proxy` (`ProxyPass` / `ProxyPassReverse`) does today.

## Scope

- New `Proxy` target. The upstream client is built on the existing transports: a BSD-socket TCP connect, plus a new Unix-domain-socket connect in `NetworkTransport` that shares the kqueue event loop.
- Reuse the `HTTP1Serializer` to write requests and the parser machinery to read responses. Add response-side parsing (status line, headers, Content-Length, chunked and close-delimited bodies), as a sibling of `HTTP1Parser` that is split-invariant and has limits.
- Connection pool per upstream:
  - A bounded number of idle keep-alive connections.
  - A max number of connections, with the waiting queue bounded too.
  - Idle eviction.
  - Discard any connection the upstream closed or answered with `Connection: close`.
  - Never reuse a connection after a partial or failed exchange.
- Streaming both ways with backpressure. The request body is pulled from `HTTPRequestBody` as the upstream accepts it. The response body is handed to the downstream writer as `.stream`, so nothing is buffered whole.
- No allocation per request on the steady-state keep-alive path apart from what the response body needs.

## Acceptance criteria

- Unit tests against an in-memory upstream: keep-alive reuse, chunked and Content-Length responses, a close-delimited response, a malformed response, and an upstream close mid-body.
- Integration tests with a real upstream on 127.0.0.1:0 and on a Unix socket in `$TMPDIR`. The upstream is a small server in the test target (or `sws-bench serve`).
- `sws-bench micro`: added proxy overhead per request with a warm pool.

## Root cause

The WIP client (07dcdf6, e3116cc, 51993cd) pooled idle connections but had no limit on open
connections, no wait queue, no idle eviction, and reused a pooled connection without checking
it, so a POST could go out on a connection the upstream had already closed (502). Request
heads were built with `String` interpolation and lowercased names, response heads parsed via
per-field `String`s, the body reader was an actor and an empty body released its connection
from an unstructured `Task`.

## Fix

- `UpstreamPools` (Mutex, non-suspending sections): per address, `maxConnections` slots
  (idle + checked out + connecting), a bounded FIFO wait queue with a timeout
  (`UpstreamError.poolExhausted`, mapped to `503` by `ReverseProxy`, not counted against
  upstream health, retried on the next upstream for idempotent methods), `maxIdle` LIFO idle
  list, `idleTimeout` checked at checkout plus a periodic sweep (`ReverseProxy.run` as a
  `ServerComponent`, every half idle timeout within 1-30 s; closes all idle connections when
  cancelled). Releases hand connections or slots to waiters directly.
- `BSDSocketTransport.isIdleAndOpen`: one `recv(MSG_PEEK | MSG_DONTWAIT)` before reuse (and in
  the sweep); a FIN, reset or stray byte discards the connection.
- `UpstreamPoolPolicy` travels with each request (`UpstreamPolicy.pool` ->
  `UpstreamSendOptions.pool`), so mounts configure it: `proxy[].pool` `{maxConnections,
  maxIdle, queue, queueTimeout, idleTimeout}`.
- `writeHead` writes the request head from bytes (field IDs and canonical names, no
  lowercasing, `append(decimal:)`/`append(hex:)` framing) into a per-connection reused buffer;
  chunked request bodies framed in the same buffer. `parseHead` parses in place over a `Span`.
  The receive buffer is reused. `BodyReader` is a class with a busy flag instead of an actor;
  an empty body releases inline; a response dropped unread gives its slot back from `deinit`.
- `sws-bench micro --filter Proxy` and `sws-bench proxy` (overhead over a warm pool, in-process
  loopback upstream, load average printed). Results: `docs/benchmarks/M17-proxy.md`.

## Gotchas

- The steady-state path is not allocation-free yet: with the default timeouts each wait for
  the response head races the receive against a sleep in a task group (`withUpstreamTimeout`),
  about 17 allocations and 8-10 us per request. Follow-up: a deadline on the kqueue wait
  (`EVFILT_TIMER` armed with the read) in `NetworkTransport`. With timeouts off the client
  makes 10 allocations per request (response fields, body reader and its closures, body chunk).
- The liveness peek narrows but cannot close the race with an upstream that closes just after
  the check; the #0122 stale retry still covers bodiless idempotent requests.
- Pools are per upstream address; mounts sharing an address share a pool, and each request's
  own `pool` policy is applied to it.
- `ReverseProxy.run` now always runs (the idle sweep) until cancelled.
- The #0120 and #0121 code commits share files (`Upstream.swift`, `ConfigFile+Proxy.swift`,
  `ReverseProxy.swift`); build them as a pair.
