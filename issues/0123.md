## Description

A Go app behind the proxy that serves WebSockets needs the upgrade passed through end to end.

## Scope

- On HTTP/1.1 downstream: forward `Upgrade: websocket` and `Connection: upgrade` to the upstream. On `101`, splice the two byte streams both ways using the `.tunnel` hook and `TunnelContext`, with backpressure and half-close handling. Close both sides together.
- On HTTP/2 (RFC 8441) and HTTP/3 (RFC 9220) downstream: map extended CONNECT to an HTTP/1.1 `Upgrade: websocket` request upstream, with a generated `Sec-WebSocket-Key`. Check `Sec-WebSocket-Accept`, then splice the stream.
- Per-mount opt-in, plus idle timeout and graceful shutdown (#0116 semantics: the tunnel ends on drain).
- Other upgrade tokens are refused unless explicitly allowed.

## Acceptance criteria

- A `URLSessionWebSocketTask` echo through the proxy to a test upstream WebSocket server over HTTP/1.1.
- In-repo h2 and h3 WebSocket clients echo through the proxy.
- A close from either end propagates. A large message hits backpressure.

## Root cause

`ReverseProxy` (#0121) treated `Upgrade` and `Connection` as hop-by-hop and always used the pooled request/response client, so an upgrade never reached the upstream and there was no path from an upstream `101` to the `.tunnel` hook. Extended CONNECT (h2/h3) had no mapping at all, and the proxy was not an `ExtendedConnectProvider`, so h2/h3 did not advertise `SETTINGS_ENABLE_CONNECT_PROTOCOL`.

## Fix

- New `Sources/Proxy/ReverseProxy+Upgrade.swift`; `ReverseProxy.swift` only gains a `tunnel: ProxyTunnelConfiguration` property and a one-call hook (`proxyUpgradeIfRequested`) before the normal forward.
- HTTP/1.1: with `ProxyMount.websocket` on, `Connection: upgrade` + `Upgrade: websocket` is forwarded (plus any token in `ProxyTunnelConfiguration.allowedUpgradeProtocols`; other tokens are still stripped). The request goes on a dedicated BSD-socket connection that never enters the pool. `101` → `101` with `Upgrade`/`Connection` re-added and a `.tunnel` body; any other answer is relayed through `mapResponse` and the connection closed afterwards.
- HTTP/2 / HTTP/3: extended CONNECT `:protocol websocket` → `GET` with `Upgrade: websocket`, `Connection: Upgrade` and a generated `Sec-WebSocket-Key`; the upstream `101` must carry the matching `Sec-WebSocket-Accept` (else `502`), then `200` + `.tunnel` (accept header dropped). A `2xx` without switching is `502`; extended CONNECT on a mount without `websocket` is `501`. `ReverseProxy` conforms to `ExtendedConnectProvider` (`["websocket"]` when any mount opts in).
- Splice (`UpstreamTunnel.splice`): one task per direction in a task group, each receive waits for the previous send to be accepted (backpressure); EOF is forwarded as a half-close; bytes the upstream sent after its `101` head are replayed first. Both sides close together when both directions ended, on any error (abort), after `idleTimeout` (default 300 s), `halfCloseTimeout` (30 s) after one direction ended, or when `TunnelContext.shutdown` triggers (drain). Handshake bounded by `handshakeTimeout` (30 s; `504` on timeout, `502` on connect failure).

## Gotchas

- On drain the tunnel closes both TCP/stream sides; being a byte-level splice it does not inject a WebSocket Close 1001 (the upstream app sees EOF / 1006).
- `ConfigFile`'s `proxy[].timeouts.idle` is not yet mapped onto `ReverseProxy.tunnel.idleTimeout`; #0122/#0124 should wire it.
- Possible existing bug (not touched): `ReverseProxy.makeUpstreamRequest` already prepends `target.basePath`, and `UpstreamHTTP1Client.serializeHead` prepends it again, so a target with a base path would get it twice on the pooled path. The upgrade path's own serializer does not re-prepend.
- The h2/h3 end-to-end tests live in HTTP2Tests/HTTP3Tests to reuse their in-repo clients, hence the extra test edges.
