## Description

Define how the proxy behaves when an upstream is down, slow or misbehaving.

## Scope

- Timeouts per mount: connect, time to the response head, idle between body reads, and total.
- Error mapping: connect refused or failed gives `502 Bad Gateway`. A timeout before the head gives `504 Gateway Timeout`. A malformed upstream response gives `502`. A failure after the response head was sent aborts the downstream stream: reset on h2/h3, close on h1. Error responses go through ErrorPages.
- Retries: only for idempotent methods with no request body consumed, and only on connect failure or a stale pooled connection that failed before any byte was sent. The retry count is bounded.
- Multiple upstreams per mount: round-robin or least-connections. Passive health tracking marks an upstream down after N consecutive failures, for a cool-down period. An optional active health check (GET a path at an interval) runs as a `ServerComponent`.
- Client disconnect cancels the upstream request and doesn't return that connection to the pool.
- Upstream backpressure: a slow client slows the upstream read, with no unbounded buffering.

## Acceptance criteria

- Tests for each timeout giving the right status, 502 on refused connections, 504 on a slow head, abort mid-body on h1/h2/h3, the retry rules (non-idempotent requests never retried), the failover order, passive and active health, client cancel propagation, and memory staying bounded with a slow client.

## Root cause

The #0120/#0121 proxy had no per-mount policy: the `timeouts` config key was parsed but never
reached the client, only the first upstream was used, and the client retried any bodiless
request (POST included) after a stale pooled connection. Separately, both
`ReverseProxy.makeUpstreamRequest` and `UpstreamHTTP1Client.serializeHead` prepended
`target.basePath`, so `http://host:port/app` upstreams saw `/app/app/...`.

## Fix

- `UpstreamPolicy` on `ProxyMount` (`policy`, additive): `UpstreamTimeouts` (connect 10 s,
  response 60 s, idle 60 s, total off), `retries` (1), `UpstreamHealthPolicy` (3 failures,
  10 s cool-down, optional active check path/interval), `tunnelIdleTimeout`.
- `UpstreamClient.send(_:body:to:options:)` (default implementation ignores options). The pooled
  client races each transport wait (connect, every head read, every body read) against
  `Task.sleep` in a task group (`withUpstreamTimeout`); the cancelled wait closes the socket so
  the connection is never pooled. A connection produced after losing the connect race is closed.
- Error mapping in `ReverseProxy+Forwarding.swift`: `connectTimeout`/`timeout` → 504, everything
  else → 502, returned as status-only responses so ErrorPages renders them. After the head, the
  body stream throws, which closes h1 and resets h2/h3 through the existing writer-failure paths.
- Retries: only idempotent methods, only after a connect failure (next upstream in rotation,
  at most `retries` extra attempts); a stale pooled connection (EOF/reset before any response
  byte) is resent once only for bodiless idempotent requests. POST/PATCH are never retried.
- `UpstreamBalancer` (Mutex): round-robin over healthy upstreams; N consecutive failures mark an
  upstream down for the cool-down; all down → try all. `ReverseProxy` is a `ServerComponent`
  that runs active `GET` checks (status < 500 = up) when a mount sets `health.path`.
- Client cancel: cancellation surfaces in the transport wait, the connection is closed (not
  pooled) and `CancellationError` is rethrown. Backpressure is the existing pull loop: one 16 KiB
  read per downstream write.
- Config: `timeouts.total`, `retries`, `health {failures, cooldown, path, interval}`; an explicit
  `timeouts.idle` also sets the mount's WebSocket/Upgrade tunnel idle timeout (#0123).
- basePath: the proxy alone prepends it; `serializeHead` sends `request.target` as-is.

## Gotchas

- macOS answers a loopback SYN to a full accept queue with RST, not a drop, so a real hanging
  connect cannot be produced on 127.0.0.1; `connectTimeoutGives504` uses the internal
  `beforeConnect` seam. Never use a LAN black-hole address (Local Network prompt).
- h2/h3 mid-body abort is the generic writer-failure path (`H2ResponseTests.bodyFailureAfterHeadersIsInternalError`,
  H3 `.responseFailed` → reset); the proxy-specific test covers h1 only.
- A non-idempotent request on a stale pooled connection fails with 502 rather than being resent.
  A cheap liveness probe before reusing an idle connection would avoid most of these.
- Upgrade requests use `peek()` (no rotation advance), so tunnels go to the upstream the next
  normal request would use.
- The request-body upload phase is not bounded by these timeouts (the downstream body timeout
  covers it); `response` is measured from the end of the request.
