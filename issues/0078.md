## Description

The legacy `ConnectionStream` pumps `receive` callbacks into an unbounded `AsyncStream` and creates a new stream and `Task` per `values` access (#0028); the state handler is installed after `start` (#0010). Implement `ByteStreamTransport` over `NWConnection` so bytes are read only when asked for.

## Scope

- `TCPTransport: ByteStreamTransport` wrapping `NWConnection`: `stateUpdateHandler` and `viabilityUpdateHandler` installed before `start(queue:)` (#0010); one `receive(minimumIncompleteLength:maximumLength:)` per `receive(into:)` call, copied into the caller's `ByteBuffer`; `send` completion resumes the continuation; cancellation cancels the connection.
- `TCPListener` over `NWListener` with port 0 support and the bound port reported after `.ready`.
- `DispatchQueue` use confined to this target (CLAUDE.md).
- Measure the known floor (ROADMAP §7): allocations and ns per receive/send round trip; try a task-executor preference backed by the connection's queue and keep it only if `sws-bench` shows a win.

## Acceptance criteria

- Socket tests bind port 0 and exchange data with `/usr/bin/curl` and with an `NWConnection` client; a client that sends 100 MB while the server reads slowly leaves server RSS bounded (no eager pump).
- A test asserts a connection that fails before `.ready` reports the failure (handler installed before start).
- `sws-bench transport` records per-read and per-write overhead in `docs/benchmarks/`.

## Root cause

The legacy `ConnectionStream` pumped `receive` callbacks into an unbounded `AsyncStream` (#0028) and installed the state handler after `start` (#0010). There was no transport behind the new `ByteStreamTransport` protocol.

## Fix

- `TCPTransport: ByteStreamTransport` over `NWConnection`:
  - The state and viability handlers are installed before `start(queue:)`. Each connection runs on its own serial queue.
  - Each `receive(into:maxLength:)` issues exactly one `receive(minimumIncompleteLength: 1, maximumLength:)` and appends the `Data` straight into the caller's buffer. EOF is sticky.
  - `send` uses `isComplete: true` and resumes on `.contentProcessed`. `endOfStream` sends `.finalMessage`, a half-close.
  - `close` calls `cancel()` for a graceful close, or `forceCancel()` (an RST) for `.abort`.
  - Continuations are `UnsafeContinuation`s in a `Mutex`, taken out before resuming, so each is resumed exactly once.
  - Task cancellation throws `CancellationError` and cancels the connection.
  - `TCPTransport.connect(host:port:)` treats `.waiting` as a failure.
- `TCPListener` over `NWListener`:
  - Binds with `requiredLocalEndpoint` (default 127.0.0.1, port 0). `start()` returns the bound port after `.ready`.
  - `connections` is a demand-driven `AsyncSequence` of ready transports, with a bounded pending-accept queue. Over-limit connections are cancelled and counted (`rejectedConnectionCount`).
- `TCPConfiguration` holds `noDelay`, keep-alive, connect timeout and address reuse. `NWError` maps to `TransportError`, and `ConnectionInfo` carries both addresses.
- Measurement: `TransportBench` (exposed only, per the orchestrator) and `AllocationCounter.countAsync`. The task-executor-preference experiment uses an opt-in `TCPTransport.taskExecutor`. Results are in `docs/notes/nw-transport.md`; the orchestrator asked for them there rather than in `docs/benchmarks/`.

## Gotchas

- A refused connect leaves the `NWConnection` in `.waiting(ECONNREFUSED)` forever unless the client treats waiting as a failure.
- `forceCancel()` on TCP sends an RST, and the peer gets `ECONNRESET`. `cancel()` is graceful and delivers every byte that `.contentProcessed` already confirmed.
- The per-receive NW floor is about 6.5 µs and 12 allocations, so read large and parse many requests per read.
- The task-executor preference gave about 10–15% on per-call ns but cost 2 more allocations per call, with no latency change. It stays opt-in until it is measured on an idle machine.
- `Mutex` cannot be captured by value in a closure. Capture its owner.
