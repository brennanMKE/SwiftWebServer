## Description

HTTP/3 frames (RFC 9114 §7) are type/length pairs of QUIC variable-length integers (RFC 9000 §16). Implement the varint and frame parsers as pure value-type state machines.

## Scope

- `VarintParser` and varint writer (1/2/4/8-byte forms, minimal encoding on write, accept non-minimal on read).
- `H3FrameParser` state machine fed from `ByteBuffer`: DATA, HEADERS, CANCEL_PUSH, SETTINGS, PUSH_PROMISE, GOAWAY, MAX_PUSH_ID; unknown and reserved (0x1f·N+0x21) types skipped; HTTP/2-only types (0x02, 0x06, 0x08, 0x09) rejected with `H3_FRAME_UNEXPECTED`.
- Per-type length limits; DATA payload delivered as a byte range without copying; frame length bounded by configuration (`H3_FRAME_ERROR` / `H3_EXCESSIVE_LOAD`).
- `H3ErrorCode` with all RFC 9114 §8.1 codes.

## Acceptance criteria

- Round-trip tests for every frame type; RFC 9000 Appendix A.1 varint examples; every frame fed one byte at a time produces identical output to a whole-buffer feed.
- `sws-bench h3frames` shows 0 allocations per frame header parse.

## Root cause

This is new work, not a bug fix. HTTP/3 needs QUIC varints and a frame codec before the control and request streams (#0100, #0101) can be built, and the `HTTP3` target was an empty placeholder.

## Fix

- `QUICVarint` encodes the minimal 1/2/4/8-byte form and has `encode(_:length:into:)` for a fixed width. Encoding a value of 2^62 or more throws `QUICVarintError.valueOutOfRange` before it writes anything. `decode` accepts non-minimal forms and returns `.value(_, consumed:)` or `.needsMoreData`. `VarintParser` keeps a partial integer across chunks.
- `H3FrameParser` is a value type. `mutating func parse(_ input: UnsafeRawBufferPointer) throws(HTTP3Error) -> Output` returns one `Event` and the number of bytes consumed; `.needsMoreData` always consumes the rest of the input. A DATA frame produces `.dataHeader(length:)` and then `.data(Range)` slices of the caller's input, so its payload is never buffered. HEADERS, PUSH_PROMISE, SETTINGS, CANCEL_PUSH, GOAWAY and MAX_PUSH_ID are reported when complete: as `.input(range)` with no copy when the payload is contiguous, otherwise as `.buffered(range)` from an internal buffer that keeps its capacity. `withPayload(_:in:_:)` reads either form. `finish()` throws `H3_FRAME_ERROR` if the stream ends mid-frame.
- `Configuration` sets `streamKind` (`.request`/`.control`), `role` (`.server`/`.client`), `maxFieldSectionLength` (64 KiB) and `maxSettingsLength` (4 KiB). The parser rejects these frames with `H3_FRAME_UNEXPECTED`: HTTP/2-only types (0x02, 0x06, 0x08, 0x09); PUSH_PROMISE received by a server; control-only frames on a request stream; DATA, HEADERS or PUSH_PROMISE on a control stream; a second SETTINGS; and MAX_PUSH_ID received by a client. A control stream whose first frame is not SETTINGS is `H3_MISSING_SETTINGS`. HEADERS, PUSH_PROMISE or SETTINGS over the limit is `H3_EXCESSIVE_LOAD`, checked from the length before any payload arrives. A single-varint frame of length 0 or more than 8, or with trailing or truncated bytes, is `H3_FRAME_ERROR`. Reserved and unknown frames are skipped as they arrive, at any length.
- `H3Settings` parses QPACK max table capacity, max field section size, QPACK blocked streams, `ENABLE_CONNECT_PROTOCOL` and `H3_DATAGRAM`, and ignores unknown and reserved ids. Duplicates (found by rescanning the bounded payload, with no set), HTTP/2 ids 0x02–0x05 and boolean values other than 0/1 are `H3_SETTINGS_ERROR`; a truncated pair is `H3_FRAME_ERROR`. The encoder writes known settings plus an optional GREASE pair.
- `H3FrameEncoder` writes every frame type to any `ByteSink`, plus generic and reserved frames and a DATA header on its own, so the body can be written without a copy.
- `H3UniStreamType` covers control, push, QPACK encoder, QPACK decoder, reserved and unknown stream types (`isKnown` is false for the last two). `UniStreamClassifier` reads the leading stream-type varint incrementally.
- `HTTP3Error: UInt64` has all 17 RFC 9114 §8.1 codes with their wire values and RFC names, plus `isReserved(_:)`. `H3ErrorCode` is a typealias for it.
- Input is `UnsafeRawBufferPointer` and output is `HeaderCompression.ByteSink`. HTTP3 sees `ByteSink` transitively through QPACK, so no `Package.swift` change was needed for it. The code does not use `ByteBuffer`.

- `scripts/guarded.sh -t 900 -- swift build`: build complete.
- `scripts/guarded.sh -t 900 -- swift test`: every Swift Testing run passed. HTTP3Tests ran 50 tests in 7 suites: `QUICVarintTests`, `H3FrameRoundTripTests`, `H3FrameErrorTests`, `H3SettingsTests`, `H3StreamTypeTests`, `HTTP3ErrorTests` and `HTTP3ModuleTests`. They include `rfc9000AppendixA1Decodes` (all five A.1 samples, including the non-minimal `0x4025`, fed at every chunk size), `rfc9000AppendixA1EncodesMinimally` and `rejectsValuesOf2To62AndAbove`. There are round trips for DATA, HEADERS, SETTINGS (with GREASE), CANCEL_PUSH, GOAWAY, MAX_PUSH_ID, PUSH_PROMISE (client role), reserved and unknown frames, and non-minimal header varints. Each round trip is checked for split invariance: whole buffer, one byte at a time, and two chunks cut at every offset. Each error case listed above has its own test, and so does each split position of a stream that ends mid-frame.
- `swift run -c release sws-bench`, run with a temporary uncommitted call in `main`: `h3frames.parse.whole` took 11.75 ns/frame and `h3frames.parse.chunked37` took 88.88 ns/frame, over a 1,000-frame request stream (HEADERS, 3×256-byte DATA and a reserved frame, repeated).

## Gotchas

- The issue's acceptance criterion of "0 allocations per frame header parse" is met by construction: the whole-buffer path never touches the internal buffer, and events are enums of ranges and integers. No allocation counter exists yet to measure it. The chunked path allocates once per parser, when the first HEADERS frame is split across chunks.
- Without `FullTypedThrows`, a plain `do { try parser.parse(…) } catch` binds `error` as `any Error`. Use `do throws(HTTP3Error)` to keep the type. As in #0095, closures passed to `withUnsafeBytes` are written untyped (`throws`) or return a `Result`.
- Frame-sequence rules inside a request stream (DATA before HEADERS, trailers) and the GOAWAY ID checks (`H3_ID_ERROR`) are left to #0100/#0101. The parser only enforces which frames may appear on which kind of stream.
- The RFC requires that a control stream start with SETTINGS, so even a reserved frame sent first is `H3_MISSING_SETTINGS`.
