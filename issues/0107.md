## Description

Optional: honour the `priority` header and PRIORITY_UPDATE frames (type 0xF0700) on the control stream to order response data. The HTTP/2 half stays in #0065.

## Scope

- Shared `priority` structured-field parser (urgency 0–7, incremental) in `HTTPCore`, reused by #0065.
- PRIORITY_UPDATE for request streams validated on the control stream (`H3_ID_ERROR` for bad IDs).
- Scheduling by urgency then round-robin among incremental streams, implemented as a send-order hint since QUIC scheduling is owned by Network.framework; document the limits of what can be controlled.

## Acceptance criteria

- Unit tests for the parser and for scheduling order with mixed urgencies.
- The resolution states how much control NW QUIC gives (measured, not assumed).

- **Milestone:** M10 — HTTP/3 hardening (optional)

## Root cause

HTTP/3 skipped PRIORITY_UPDATE as an unknown frame type and ignored the `priority` field; the connection send budget (#0104) served waiting sends strictly first come, first served.

## Fix

- Shared parser: `HTTPCore/HTTPPriority.swift`, landed with #0065 (5667613).
- `H3FrameType.priorityUpdateRequest` (0xF0700) and `.priorityUpdatePush` (0xF0701). `H3FrameParser` buffers them on the control stream (an element-ID varint, then at most `maxPriorityUpdateLength` = 1,024 bytes: empty is H3_FRAME_ERROR, longer is H3_EXCESSIVE_LOAD) and reports `.priorityUpdate(push:id:field:)`; on a request stream they are H3_FRAME_UNEXPECTED (RFC 9218 §7.2).
- `readControlStream`: a request-stream ID that is not client-initiated bidirectional (`id % 4 != 0`), or a push ID with no or a lower MAX_PUSH_ID (we never push), closes the connection with H3_ID_ERROR. PRIORITY_UPDATE counts toward `maxControlFramesPerWindow` like every control frame (#0104 flood limit).
- `H3Priorities` (new `H3Priorities.swift`): per-connection table of `H3StreamPriority` cells (atomic urgency/incremental). `respond` opens a cell from the request's `priority` field (an earlier PRIORITY_UPDATE wins) and closes it when the response ends. Updates for open streams apply at once; updates for streams above the highest served are kept (at most `maxConcurrentRequestStreams`), others ignored. A handler's `priority` response field is merged in `write`/`runTunnel` (RFC 9218 §5).
- `H3SendBudget`: waiters carry their stream's cell. `release` serves the waiter with the lowest scheduling key (urgency, non-incremental before incremental, non-incremental by stream ID, incremental first come first served so repeated sends interleave), and every 16th grant goes to the oldest waiter (no starvation). `H3ResponseSink` passes the stream's cell to `acquire`.

## How much control Network.framework QUIC gives (measured)

`H3QUICPriorityTests` over real loopback QUIC: two streamed 8 MiB downloads, `u=7` requested before `u=0`, with the send budget contended (64 KiB) and at its 4 MiB default. In all 3 + 3 runs (and again in the full suite) both downloads finished within 0.5 ms of each other, in either order (e.g. 64 KiB budget: `/high` 77.4 / `/low` 77.5 ms; `/low` 69.2 / `/high` 69.4 ms). **On an uncongested link the ordering does not reach the wire**: a send completes once Network.framework buffers it, so the budget rarely holds a stream back, and NW QUIC interleaves the streams' packets itself. `NWProtocolQUIC` exposes no per-stream priority. The budget ordering is a send-order hint that matters only when the budget is truly exhausted (a client that stops reading). Making an urgent HTTP/3 response finish first would need pacing response sends in the server, a possible follow-up.

## Verification

- `swift test -j 2 --filter H3PriorityTests`: 9 tests (11 cases) — PRIORITY_UPDATE parsing at every split; H3_FRAME_UNEXPECTED on a request stream; H3_FRAME_ERROR and H3_EXCESSIVE_LOAD; table updates before open (wins over the request field), after open, the response field merge, after close ignored, invalid ignored, early buffer bounded; budget serves `u=0`, `u=1`, `u=3`, `u=6` in that order; incremental streams alternate; the oldest low-priority waiter gets the 16th grant; in-memory h3 connection accepts updates before and after a stream opens; H3_ID_ERROR for IDs 1 and 2 and for a push without MAX_PUSH_ID; H3_FRAME_UNEXPECTED for PRIORITY_UPDATE on a request stream.

## Gotchas

- QUIC request streams can arrive out of order: a PRIORITY_UPDATE for a stream below the highest one served that has not arrived yet is treated as closed and ignored.
- With `maxConnectionSendBuffer = nil` there is no budget and so no ordering at all.
