## Description

Implement `MultiplexedTransport` (ROADMAP §5.2) on Network.framework QUIC using exactly the API shape validated by the spike (#0071).

## Scope

- `QUICListener`: `NWListener` with `NWProtocolQUIC.Options` (ALPN `h3`, identity from #0087) and `newConnectionGroupHandler`; one `NWConnectionGroup` per QUIC connection.
- `inboundStreams` is a demand-driven `AsyncSequence` fed by `group.newConnectionHandler`, bounded (no unbounded buffering); each stream is a `ByteStreamTransport & StreamIdentified` exposing stream ID and direction.
- `openUnidirectionalStream()` via `NWConnection(from:using:)` with `direction = .unidirectional`.
- FIN mapped to `receive` returning 0 and to `send(_:endOfStream: true)`; stream reset/STOP_SENDING and connection close with an application error code as determined by the spike.
- `QUICConnectionState` and `QUICStreamState` value types mirror NW state updates into events.

## Acceptance criteria

- Echo test against an NW QUIC client in the same process: bidirectional echo, server-opened uni stream, FIN in both directions, reset with an error code observed by the peer, and connection close with an application code.
- A client that opens 1,000 streams does not grow server memory beyond the configured stream limit × buffer size.

## Notes

From the QUIC spike (#0071, docs/spikes/quic-spike.md): set a client group's `newConnectionHandler` before `start`; every send must use `isComplete: true`; replenish MAX_STREAMS by raising `groupMetadata.localMaxStreamsBidirectional`; `group.cancel()` waits for all streams to end, so cancel streams first; route by each stream's `negotiatedALPN`; NW buffers about 2–6 MiB per stream before send completions stall, so bound sends ourselves. Load identities with `kSecImportToMemoryOnly` only.


## Root cause

New work: NetworkTransport had only the TCP adapter, so no `MultiplexedTransport` ran over real QUIC.

## Fix

- `QUICListener` is an `NWListener` with `NWProtocolQUIC.Options` (ALPN from `QUICConfiguration`, default `h3`) and an in-memory `TLSIdentity` (#0072, used here because #0087 is not done). It binds `requiredLocalEndpoint` (127.0.0.1, port 0 by default) and uses `newConnectionGroupHandler`. Its `connections` sequence is demand-driven and bounded by `pendingConnectionLimit`, and it hands a connection over once the connection is usable (group ready or a stream ready, spike gotcha 7).
- `QUICConnection: MultiplexedTransport` wraps one `NWConnectionGroup`, and one serial queue runs the group and all its streams. A client connects with `connect(host:port:configuration:)`: certificate pinning, a connect timeout, and `newConnectionHandler` installed before `start`.
  - Inbound streams are started at once and handed over through a demand-driven `inboundStreams`. The queue is bounded by `pendingStreamLimit`; streams beyond it are reset with `rejectedStreamErrorCode`.
  - `openUnidirectionalStream` / `openBidirectionalStream` use `NWConnection(from:using:)` and retry while it returns nil.
  - MAX_STREAMS: each finished peer stream raises `localMaxStreamsBidirectional`/`Unidirectional` to initial + finished.
  - `close(applicationError:)` sets the group `applicationError`, resets every ready stream (`forceCancel`), cancels never-ready ones, then cancels the group.
- `QUICStreamTransport: ByteStreamTransport & StreamIdentified` (not `QUICStream`, which collides with macOS 26's Network module):
  - One NW receive per `receive`.
  - Sends are split into `sendChunkSize` (64 KiB) chunks. Each chunk waits for `.contentProcessed`, and every send uses `isComplete: true`.
  - FIN is `.finalMessage`.
  - `reset(applicationError:)` sets `streamApplicationErrorCode` and then cancels. The peer's code is captured into `receivedResetCode` when a receive fails with a reset.
- `QUICConnectionState` and `QUICStreamState` are pure value-type state machines that mirror group and stream events into single actions.
- Tests: `MultiplexedTransportConformanceTests` runs the same 9 scenarios against the QUIC adapter and `InMemoryMultiplexedTransport` (#0099). `QUICTransportTests` holds the QUIC-only cases. `NetworkTransportTests` gains `HTTPTestSupport` as a test dependency (a one-line `Package.swift` change).

## Gotchas

- Assigning `NWProtocolQUIC.Metadata.applicationError = ApplicationError(code:)` with a nil `reason` crashes with SIGSEGV. Always pass a reason.
- A plain `cancel()` of streams during connection close sometimes reached the peer as FIN, which can make a truncated response look complete. Use `forceCancel()`.
- Setting `streamApplicationErrorCode` on every stream just before cancelling them and the group made a spurious server-initiated stream (ID 1) appear at the NW client. A single-stream `reset` does not do this.
- A client whose verify block rejects the certificate never gets a TLS error. Its group stays `waiting(ENETDOWN)` (the server group fails with `EINVAL`), so `connect` needs its timeout.
- A dropped `QUICStreamTransport` cancels its stream, which hands credit back to the peer. Tests that assert "no credit granted" must keep the client streams alive.
- NW's per-stream send buffer (about 4 MiB here) cannot be bounded through the public API. The adapter only bounds its own copies (one chunk).
- The STOP_SENDING code cannot be sent separately: `stopSending` is a whole-stream reset. In memory, the receive side stays open after a local reset; on NW it does not. The `MultiplexedTransport.Stream` protocol has no reset or STOP_SENDING requirement, so #0100 can only abort generically through `close(.abort)`, and may want a small `HTTPCore` protocol for reset codes.
- Following up on spike Q6: whether the connection close code is on the wire is still unverified (#0104).
