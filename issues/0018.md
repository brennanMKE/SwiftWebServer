# 0018 — Non-200 responses always replace the body with an HTML error page, including 304

| | |
|---|---|
| **Status** | open |
| **Module** | Semantics |
| **Platform** | macOS |
| **First seen** | 2026-09-12 |

## Description

`HTTPResponse.init` (`HTTPResponse.swift:8-16`) discards the caller's body and substitutes the HTML status page for every status other than `.ok`. 304 responses therefore carry a body, which RFC 9110 §15.4.5 forbids, and no future status (201, 206, 301, and so on) can carry a real body. Verified on 2026-09-12: a 304 came back with `Content-Length: 357` and an HTML page.

## Steps to reproduce

1. `ET=$(curl -sI http://localhost:8080/index.html | grep -i etag | cut -d' ' -f2- | tr -d '\r')`
2. `curl -si http://localhost:8080/index.html -H "If-None-Match: $ET"`

## Expected behavior

`304 Not Modified` with no body and no `Content-Length` for a body.

## Actual behavior

304 with a 357-byte HTML page.

## Notes

Make the error page an explicit choice (for example, `HTTPResponse.errorPage(status:)`). Never attach a body to 1xx, 204, or 304 responses. Error pages should have `Content-Type: text/html; charset=utf-8`, which is currently missing.
