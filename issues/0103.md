## Description

Clients discover HTTP/3 through `Alt-Svc` on HTTP/1.1 or HTTP/2 responses over TLS (RFC 7838, ROADMAP §6).

## Scope

- Middleware contributed by the HTTP3 component adding `Alt-Svc: h3=":<port>"; ma=<seconds>` to responses on TLS listeners only; pre-rendered once at startup.
- Not added on cleartext listeners or on HTTP/3 responses themselves.
- UDP listener bound on the same port number as the TCP TLS listener by default (spike question 10).

## Acceptance criteria

- `curl -k -I https://localhost:8443/` shows the `Alt-Svc` header; `curl -I http://localhost:8080/` does not.
- `/opt/homebrew/opt/curl/bin/curl -k --http3 --alt-svc altsvc.txt` makes a second request over HTTP/3 (verified with `-w '%{http_version}'` = 3).

## Root cause

Nothing advertised HTTP/3: clients reaching the TLS listener had no way to learn that the
same origin also speaks h3 over UDP (RFC 7838, RFC 9114 §3.1.1).

## Fix

- `AltSvc` (`Sources/HTTP3/AltSvc.swift`), an `HTTPMiddleware` from the HTTP3 component, adds
  `Alt-Svc: h3=":<port>"; ma=<seconds>` to every response (error pages included) whose
  connection is TLS and did not negotiate `h3`: HTTPS (HTTP/1.1, later HTTP/2) yes, cleartext
  and HTTP/3 no. The value is rendered once into bytes and published through an
  `AtomicLazyReference`, so a response costs one atomic load, the TLS/ALPN test, and a copy of
  about 25 bytes into the head. `init(port:maxAge:)` renders at once; `init(maxAge:)` plus
  `advertise(port:)` renders once the UDP listener is bound (port 0 in tests).
- `HTTP3.run` fills in `negotiatedALPN = "h3"` when the transport could not read it back, so the
  middleware can always recognise HTTP/3 requests.
- The executable registers `AltSvc` in front of the chain only when `http3` is enabled (a
  separate `serve` instantiation, so without HTTP/3 the chain has no Alt-Svc step at all), and
  calls `advertise(port:)` with the bound QUIC port before printing the `listening` lines.
  `ma` is `http3.altSvcMaxAge` (default 86400). The UDP listener is on the TLS port number by
  default (#0089, spike question 10).

## Verification

- `scripts/guarded.sh -t 900 -- swift test -j 2 --filter "ListenersProcessTests|AltSvcTests|MixedListenersTests"`, then the full run
  `scripts/guarded.sh -t 1500 -- swift test -j 2`: 1,020 tests, 0 failures; `HTTP3Tests`
  alone: 140 tests passed.
- `Tests/HTTP3Tests/AltSvcTests.swift`: `rendersTheRFC7838Value`, `addedOnTLSResponsesOnly`
  (TLS, TLS without ALPN and h2 get it; cleartext and h3 do not; the response passes through),
  `advertisesNothingUntilThePortIsKnownThenTheFirstPortWins`, `appliesOnlyToTLSWithoutH3`.
- `Tests/IntegrationTests/ListenersProcessTests.swift`, the real binary on port 0:
  `altSvcOnHTTPSOnlyAndCurlUpgradesToHTTP3` (`curl -k -i https://` shows
  `alt-svc: h3=":<udp port>"; ma=600`, also on a 404; `curl -i http://` and
  `curl --http3-only` responses have none; Homebrew `curl -k --alt-svc <cache>` twice reports
  `%{http_version}` `1.1` then `3`), and `noAltSvcWithoutHTTP3`.
- Manually with a port-0 copy of `Root/http-config.tls.json`: the HTTPS head carried
  `alt-svc: h3=":52720"; ma=86400`, cleartext and HTTP/3 heads did not, and the curl alt-svc
  cache file recorded `h1 127.0.0.1 52721 h3 127.0.0.1 52721`.

## Gotchas

- The acceptance criteria's `localhost:8443` / `:8080` are port 0 in the tests (AGENTS.md);
  `Root/http-config.tls.json` keeps 8080/8443 for manual runs.
- curl's alt-svc cache needs the same host name on both requests, and its first request still
  goes over TCP: `--alt-svc` alone (no `--http3`) is enough with Homebrew curl 8.23.
- With port 0 a request can reach the TLS listener between binding and `advertise(port:)`;
  such a response has no `Alt-Svc`. The window closes before the `listening` lines are printed.
- The middleware appends without checking for an existing `Alt-Svc`, so a handler that sets
  its own gets two. No handler in the shipped chain sets one.
