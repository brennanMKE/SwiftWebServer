# 0051 — Bridge RST_STREAM in both directions to task cancellation

| | |
|---|---|
| **Status** | resolved |

## Description

Stream resets and Swift task cancellation must map onto each other.

## Scope

- An inbound `RST_STREAM` cancels that stream's child task. The handler sees `CancellationError`, the file handle closes, and buffered DATA is discarded with its connection-level window credit returned.
- A stream task that is cancelled locally, or whose response body throws, sends `RST_STREAM(CANCEL)` or `RST_STREAM(INTERNAL_ERROR)`.
- Flow-control waiters for a reset stream are resumed with an error through `withTaskCancellationHandler`.
- `RST_STREAM` on an idle stream is a connection `PROTOCOL_ERROR`.

## Acceptance criteria

- A test resets a stream mid-download and asserts that the handler task finishes, the file handle closes, and the connection keeps serving other streams.

## Relation

- **Milestone:** M12 — HTTP/2 connections and streams (Track B)
- **Blocked by:** #0049, #0088, #0095
- **Blocks:** #0052, #0053

## Root cause

Feature work. A peer RST_STREAM stopped the response (#0044) but did not cancel the handler: it kept running to completion. A stream task could not be cancelled on its own, because it was a child of the connection's single discarding group.

## Fix

- **`HTTP2StreamTask`** (`Sources/HTTP2/HTTP2StreamTask.swift`): each stream task (`runStream`) runs `serve` as the only child of a small discarding group, then waits on the task object.
  - `finish()` (the handler and response are done) ends the group normally. `cancel()` cancels the group, so the handler sees `CancellationError`.
  - A cancelled connection still reaches the handler through the task tree.
  - This costs one extra child task per stream.
- **Shared state.** `HTTP2SharedState.tasks` holds each dispatched stream's task. It is registered in the same critical section as the body, before the reader reads anything after the HEADERS, and removed in `streamEnded`.
  - A received `RST_STREAM`, or any `.resetStream` the state machine produces (a stream error the reader found: `content-length`, flow control, invalid trailers), queues the task and the body in `HTTP2Wakeups`. They are ended outside the lock, body first, so a handler reading the body sees `connectionReset` (or `malformed`) rather than a bare cancellation.
  - Buffered DATA is dropped and its connection credit returned (#0048).
- **Waiters.** Flow-control and queue waiters already resumed on cancellation through `withTaskCancellationHandler`, and the peer's reset wakes them (`.windowChanged`). The next attempt sees the closed stream.
- **Resets from the handler side** (`serve`):
  - a handler that was cancelled, or throws `CancellationError`, sends `RST_STREAM(CANCEL)`. So does a response cut short by cancellation;
  - other handler errors are still a `500` before HEADERS and `RST_STREAM(INTERNAL_ERROR)` after them (#0049);
  - the state machine drops a reset on a stream that is already closed, so a stream the peer reset gets nothing back;
  - the response is released before the stream ends, which closes a `.file` body's descriptor.
- RST_STREAM on an idle stream was already a connection `PROTOCOL_ERROR` (`HTTP2StreamTable`, #0045); it now has a connection-level test.
- **Debug counter.** `HTTP2ConnectionDriver.liveStreamTasks` (an atomic) counts the stream tasks running.

## Verification

- `scripts/guarded.sh -t 900 -- swift test -j 2 --filter HTTP2Tests`: 189 tests passed, 5 runs in a row. New in `H2ResetTests` (8 tests):
  - `peerResetCancelsTheHandler`: a handler sleeping 60 s sees `CancellationError`. No HEADERS, DATA or RST_STREAM goes out on the reset stream. The next stream is served, and no task, body or active-stream count is left;
  - `resetMidDownloadClosesTheFile`: a 1 MiB `.file` response stalls at the 65,535-byte window. After the client's RST_STREAM the task ends and the descriptor is closed: `fstat` fails, or the number now names another inode. The connection serves the next stream;
  - `resetMidStreamingBodyStopsTheWriter`: a `.stream` writer waiting for window throws;
  - `resetReturnsTheCreditOfBufferedData`: 48,000 buffered bytes come back as `WINDOW_UPDATE(0, 48000)` after the reset;
  - `resetOnAnIdleStreamIsAConnectionProtocolError`;
  - `handlerCancellationSendsCancel`: `RST_STREAM(CANCEL)`;
  - `serverResetCancelsTheHandler`: a body longer than `content-length` is `RST_STREAM(PROTOCOL_ERROR)` and cancels the sleeping handler;
  - `thousandResetsLeakNothing`: 1,000 streams (half with a request body) are opened and reset by the client in batches of 50. After a PING round trip, `liveStreamTasks`, `tasks`, `bodies`, the active-stream count and the stream table's active count are all 0. No RST_STREAM or GOAWAY is sent, and the next request is served.
- `H2CurlTests.curlTimeoutMidDownloadCleansUp`: two endless downloads with `curl --http2-prior-knowledge --max-time 1` end with exit code 28. Every `.stream` writer on the server stops within 5 s, and a new request gets `quick`.

## Gotchas

- `streams.cancelAll()` at the end of the connection also makes every running handler reset its stream with CANCEL. Those frames go to the writer, which may still flush them to a peer that has gone. That is harmless, and it is right for #0052's drain timeout.
- Rapid-reset abuse (CVE-2023-44487) is not limited here; that is #0056. A reset costs a task creation and a cancellation.
- `liveStreamTasks` is always compiled in (one relaxed atomic add and subtract per stream), so release-mode tests can use it too.
