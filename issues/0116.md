## Description

Follow-up from the #0109 Gotchas. The `.tunnel` closure gets no shutdown signal, so a draining server cannot tell open WebSockets to close. They end only when the drain deadline cancels the connection task, and clients see an abrupt end (1006) instead of a close handshake with 1001 Going Away (RFC 6455 §7.4.1).

## Expected behavior

When the server starts draining, every open WebSocket session sends Close 1001, completes the close handshake, and its connection ends before the drain deadline.

## Scope

- Pass the connection's `ShutdownSignal` into the `.tunnel` closure (a small context value next to the transport), from HTTP/1.1 and from HTTP/3 (#0111).
- `WebSocket.run(over:)` takes an optional shutdown signal and starts the close handshake with 1001 when it triggers.
- Test: in-memory and with `URLSessionWebSocketTask`, triggering the server's shutdown makes the client see 1001 and the server finish well before its drain deadline.

## Root cause

`HTTPResponseBody.tunnel` handed its closure only the byte stream. The connection's
`ShutdownSignal` stayed inside the HTTP/1.1 runner, which by design does not interrupt a tunnel
when draining, so a WebSocket session had no way to learn that the server was going away. It
ran until the server's drain deadline cancelled the connection task, and the client saw the
TCP connection drop (1006).

## Fix

- `HTTPCore`: `.tunnel` closures now take `(any ByteStreamTransport, TunnelContext)`.
  `TunnelContext` carries `shutdown: ShutdownSignal`, the connection's drain signal.
- `HTTP1`: `startTunnel` passes `TunnelContext(shutdown: context.shutdown)` (with or without
  replayed bytes). HTTP/3 passes its connection's signal the same way (#0111).
- `WebSockets`: `WebSocket.run(over:subprotocol:configuration:compression:shutdown:handler:)`
  takes an optional signal; a child task of the session waits on it and starts the close
  handshake with 1001 Going Away. It does not count toward the session's end (like the close
  timer) and is cancelled with the session. `WebSocketUpgrade` passes `tunnel.shutdown`.
- Existing `.tunnel { stream in ... }` call sites (three tests) take the second argument.

## Gotchas

- Changing the `.tunnel` closure type is source-breaking for every producer of a tunnel. HTTP/2
  only matches `.tunnel` without binding it, so it compiled unchanged; when #0067 runs tunnels
  over HTTP/2 it must pass `TunnelContext(shutdown: context.shutdown)` too.
- The HTTP/1.1 supervisor does not take over a tunnelled connection on shutdown
  (`takeOverIfBetweenRequests` is false in the `.done` phase), which is what lets the session
  finish its close handshake; the drain deadline still cancels a peer that never answers
  (after the session's own 5 s close timeout at most).
- `async let` values cannot be captured by `#expect(throws:)`; await them into a local first.
