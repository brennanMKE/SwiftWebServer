## Description

`TCPTransport.send(_:endOfStream: true)` on a TLS connection (Network.framework, `NWProtocolTLS` over TCP) does not reach the peer as end of stream: the peer never reads EOF while the connection stays open. So neither HTTP/1.1 nor HTTP/2 over TLS can half-close cleanly, and lingering close over TLS only ends through its quiet timeout. Found during #0061 (see its Gotchas).

## Steps to reproduce

1. Start a `TCPListener` with a `TLSConfiguration` on 127.0.0.1 port 0.
2. Connect a TLS client (raw `NWConnection` with TLS, or `openssl s_client`).
3. On the server side, `send(bytes, endOfStream: true)` and keep the connection open.
4. On the client, read until EOF.

## Expected behavior

The client reads the bytes, then EOF (TLS close_notify and/or TCP FIN), and can still send if TLS half-close is supported. If Network.framework cannot half-close TLS, that is documented and `close(.normal)` is the fastest correct full close.

## Actual behavior

The client reads the bytes and then waits; EOF only arrives when the server cancels the connection.

## Notes

- `TCPTransport.send` maps `endOfStream` to `NWConnection.ContentContext.finalMessage`. Over cleartext TCP that is a FIN (half-close), see `docs/notes/nw-transport.md`.
- Investigate `.finalMessage` vs. a custom context with `isFinal`, whether NW sends close_notify and FIN on a final-message send over TLS, and whether only `cancel()` does it.

## Root cause

Network.framework cannot half-close a TLS connection. On a TLS `NWConnection`, a final-message send (`.finalMessage` with data, `nil` content with `.finalMessage`, or a custom `ContentContext(identifier:isFinal: true)`) puts nothing on the wire: neither close_notify nor a TCP FIN. Observed on macOS 27.0 with TLS 1.3 and 1.2, using a raw NW TLS client (its next receive stays pending; it can still send and the server still receives) and `/usr/bin/openssl s_client` (prints neither `closed` nor `read:errno=0`). Only `cancel()` ends the stream for the peer: it sends close_notify and a FIN (`s_client` prints `closed`; an NW client's receive completes with `isComplete` within milliseconds). There is no public NW API to send close_notify or shut down TCP writes under TLS, so this cannot be fixed in the adapter.

## Fix

Documented as a known limitation, and made the full close the explicit answer:

- `TCPTransport` docs describe the TLS behaviour; new `TCPTransport.supportsHalfClose` is `false` for a TLS connection (generic code can check `info.isSecure`). `send(_:endOfStream: true)` over TLS still shuts down the local write side (later sends throw `outputShutdown`, receiving continues).
- `close(.normal)` (`cancel()`) already is the fastest correct full close over TLS: it returns in under 0.2 ms even with unread data queued, delivers every accepted byte, then close_notify and FIN. No code change was needed there; new tests pin it down.
- A lingering close over TLS cannot rely on the peer reacting to the half-close; it ends when the peer closes or by its own (quiet) timeout, then `close(.normal)`. Recorded in `docs/notes/nw-transport.md` ("No half-close over TLS").

## Gotchas

- Every receive on a TLS `NWConnection` reports `context.isFinal == true`, with or without a final message from the peer, so that flag says nothing about end of stream; only `isComplete` does.
- LibreSSL `s_client` fails with `poll error` when stdin is `/dev/null` (what `ChildProcess` uses). `sleep N | openssl …` under `sh -c` orphans the `sleep` when the child is killed; the test opens a FIFO read-write as stdin (`0<>fifo`) and `exec`s openssl, so there is one process and no EOF on stdin.
- `s_client` output distinguishes the endings: `closed` is close_notify, `read:errno=0` a FIN without close_notify, `read:errno=54` a reset.
- Follow-up for HTTP/1.1 and HTTP/2 owners (outside this issue's scope): over TLS the half-close before a lingering close is a no-op on the wire, so a short quiet timeout before `close(.normal)` is what ends the linger.
