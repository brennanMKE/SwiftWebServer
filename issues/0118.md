# 0118 — TLS transport never signals end of stream to the peer

| | |
|---|---|
| **Status** | open |
| **Module** | NetworkTransport |
| **Platform** | macOS |
| **First seen** | 2026-11-11 |

## Description

`TCPTransport.send(_:endOfStream: true)` on a TLS connection (Network.framework, `NWProtocolTLS` over TCP) does not reach the peer as end of stream: the peer never reads EOF while the connection stays open. So neither HTTP/1.1 nor HTTP/2 over TLS can half-close cleanly, and lingering close over TLS only ends through its quiet timeout. Found during #0061 (see its Gotchas).

## Steps to reproduce

1. Start a `TCPListener` with a `TLSConfiguration` on 127.0.0.1 port 0.
2. Connect a TLS client (raw `NWConnection` with TLS, or `openssl s_client`).
3. On the server side, `send(bytes, endOfStream: true)` and keep the connection open.
4. On the client, read until EOF.

## Expected behavior

The client reads the bytes, then EOF (TLS close_notify and/or TCP FIN), and can still send if TLS half-close is supported. If Network.framework cannot half-close TLS, that is documented and `close(.normal)` is the fastest correct full close.

## Actual behavior

The client reads the bytes and then waits; EOF only arrives when the server cancels the connection.

## Notes

- `TCPTransport.send` maps `endOfStream` to `NWConnection.ContentContext.finalMessage`. Over cleartext TCP that is a FIN (half-close), see `docs/notes/nw-transport.md`.
- Investigate `.finalMessage` vs. a custom context with `isFinal`, whether NW sends close_notify and FIN on a final-message send over TLS, and whether only `cancel()` does it.
