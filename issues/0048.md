## Description

A request's `HTTPRequestBody` (#0081) for HTTP/2 is an AsyncSequence whose iterator pulls DATA payloads buffered by the connection for that stream.

## Scope

- DATA on a stream that is not open or half-closed (local) is a `STREAM_CLOSED` error. END_STREAM finishes the sequence.
- The sum of DATA lengths is checked against `content-length` (stream `PROTOCOL_ERROR` on mismatch).
- Trailers from #0046 are exposed after the body ends.
- Padding bytes count toward flow control but are not delivered.
- Iterator `next()` is the pull signal that returns flow-control credit (implemented in #0053).
- Cancellation of the consuming task is handled cleanly.

## Acceptance criteria

- Tests stream a multi-frame body to a handler that reads slowly, cover a content-length mismatch, and cover trailers.

## Relation

- **Milestone:** M12 — HTTP/2 connections and streams (Track B)

## Root cause

Feature work: the connection core (#0044) discarded DATA and returned its connection credit as soon as it arrived. Handlers saw an empty body, and the server never sent a stream WINDOW_UPDATE, so a client stalled after 65,535 bytes of body on any stream.

## Fix

- **`HTTP2BodyChannel`** (`Sources/HTTP2/HTTP2BodyChannel.swift`) is the `HTTPRequestBodySource` of a request whose HEADERS do not end the stream. It holds one `ByteBuffer`.
  - The reader appends DATA payloads, with padding already removed by the parser. `next()` hands the handler everything buffered as one chunk.
  - END_STREAM ends the body. A trailer section, decoded with `HTTP2TrailerFieldSink` (#0047), is available afterwards through `HTTPRequestBody.trailers`.
- **Bound and backpressure.** The reader cannot pause one stream without pausing all of them, so flow control is the bound:
  - Credit goes back only when `next()` takes bytes (`HTTP2ReceiveCredit.bodyConsumed`). This is the pull signal #0053 builds on.
  - Stream credit is sent once half the stream window was consumed, and only while the peer may still send. Connection credit is batched at half the connection window, as before.
  - A handler that does not read stalls only its own stream, at the window.
  - DATA past the stream window (the larger of 65,535 and our INITIAL_WINDOW_SIZE, since the peer may use the default until it acknowledges our SETTINGS) is a stream `FLOW_CONTROL_ERROR`. The buffer is therefore never larger than one window.
- **State machine** (`HTTP2Connection`):
  - `.data` now carries the payload length. The stream table's `proceed` becomes `.acceptData`, and only the padding is credited at once.
  - Ignored, refused and errored DATA is credited at once, so it still counts toward connection flow control (#0045 Gotchas).
  - The new `.bodyConsumed` event returns connection credit, plus stream credit when the stream is still open for the peer.
  - Trailers are `.acceptTrailers`.
  - `.sendWindowUpdate` can carry a connection and a stream increment. Both go in the priority lane.
- **Errors.** Each failure reaches the handler after the bytes already buffered:
  - a DATA total above or below `content-length` (§8.1.1), or invalid trailers, is `HTTPRequestBodyError.malformed` and `RST_STREAM(PROTOCOL_ERROR)`;
  - a stream reset by either side is `TransportError.connectionReset`; buffered bytes are dropped and their connection credit returned;
  - the end of the connection is `TransportError.closed`;
  - after the handler returned, reads throw `expired`. Unread and later DATA is discarded and credited at once;
  - a cancelled read throws `CancellationError`, unless the body already failed.
- DATA on a half-closed (remote) or closed stream is still `STREAM_CLOSED` (#0045).
- Bodies live in `HTTP2SharedState.bodies`. The reader completes them. A reset, the end of the handler, or the end of the connection removes them, so a reset stream leaves nothing behind. A failed body is ended outside the lock (through `HTTP2Wakeups`).
- The handler now gets `context.requestContext`, so connection-scoped values set by observers reach HTTP/2 requests too.

## Gotchas

- #0053 still owns the inbound window policy: the acceptance tests for stalls and timely updates, connection-window accounting of buffered bytes against SETTINGS changes, and any auto-tuning. The hook is `HTTP2BodyChannel.nextChunk`, through `HTTP2ReceiveCredit.bodyConsumed`. Stream credit is batched in the channel and connection credit in the machine.
- The stream-window check uses the larger of 65,535 and the advertised INITIAL_WINDOW_SIZE. It is exact once the peer acknowledged our SETTINGS. Before that, a smaller advertised window is not enforced.
- `next()` returns the whole buffer and starts a new one, so each handed-out chunk is a fresh allocation. The handler owns the chunk.
- There is no request-body size limit (`413`) for HTTP/2 yet. HTTP/3 has `maxRequestBodySize`; HTTP/2 relies on the window and the handler (`HTTPRequestBody.collect(upTo:)`).
