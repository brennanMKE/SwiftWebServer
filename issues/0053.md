# 0053 — Implement inbound flow control that sends WINDOW_UPDATE as the handler consumes body data

## Description

Enforce the receive windows the server advertises (RFC 9113 §5.2 and §6.9), and return credit only as data is consumed, so buffered request bytes are always bounded by the window.

## Scope

- Connection and stream receive windows start at `SETTINGS_INITIAL_WINDOW_SIZE`. The connection window is raised after the preface.
- DATA beyond the window is a connection `FLOW_CONTROL_ERROR` (or a stream error for the stream window).
- The body iterator's `next()` returns credit. `WINDOW_UPDATE` is batched once consumed credit reaches half the window.
- Credit for data that is discarded (reset streams, padding) is returned to the connection window.

## Acceptance criteria

- A test with a handler that never reads verifies the client stalls at the window size and server memory stays bounded.
- A test with a handler that reads verifies timely WINDOW_UPDATEs.

## Root cause

Feature work. #0048 left the inbound window policy half done (#0048 Gotchas): connection credit was batched in the state machine, but stream credit was batched in the body channel against a fixed window of `max(65,535, advertised)`. A smaller advertised INITIAL_WINDOW_SIZE was never enforced, padding was not charged to the stream window, and the stream window did not follow our SETTINGS once acknowledged.

## Fix

- **`HTTP2ReceiveWindow`** (new, `HTTP2FlowControl.swift`): a value type for one receive window. `receive` charges a frame and reports overflow. `credit` batches consumed bytes and returns a WINDOW_UPDATE increment once half the window is pending. `resize` applies a new initial window, which may make it negative.
- **`HTTP2Connection`** owns every receive window: the connection's, and one per stream whose peer may still send. The stream window is created at dispatch when HEADERS does not end the stream, and removed at END_STREAM, trailers, a reset in either direction, the final GOAWAY or a connection error.
  - DATA past a stream window: `RST_STREAM(FLOW_CONTROL_ERROR)`, and the frame's connection credit is returned. DATA past the connection window: `GOAWAY(FLOW_CONTROL_ERROR)`.
  - Padding counts against both windows. It is credited to the connection at once and to the stream with the next stream update.
  - `bodyConsumed(streamID:length:)` (formerly with a `streamIncrement`) credits both windows. Each emits a WINDOW_UPDATE once half its window is pending, never per DATA frame. No stream credit is sent once the peer ended the stream.
  - Stream windows start at `max(65,535, advertised)` until our SETTINGS are acknowledged, because the peer may apply them before we see the ACK. At the ACK they move to the advertised `initialWindowSize` exactly, open streams included (§6.9.2).
- **`HTTP2BodyChannel`** no longer tracks windows. `next()` reports each chunk's length as consumed, and discarded bytes (failed, reset or expired bodies) are reported the same way.
- The connection window (`connectionWindowSize`, 1 MiB) stays larger than the stream window (`initialWindowSize`, 65,535), so several streams can upload at once.

## Verification

- `scripts/guarded.sh -t 600 -- swift test -j 2 --filter HTTP2Tests`: 212 tests passed. New in `H2InboundFlowTests` (13 tests):
  - state machine: `receiveWindowBatchesCreditAtHalfTheWindow`, `dataBeyondAStreamWindowResetsOnlyThatStream`, `dataBeyondTheConnectionWindowIsAConnectionError`, `consumedBytesReturnStreamAndConnectionCreditAtHalfAWindow`, `paddingIsCreditedToTheStreamWithTheNextUpdate`, `noStreamCreditAfterEndStream`, `acknowledgedInitialWindowSizeAppliesExactly`.
  - connections: `clientStallsAtTheWindowWhenTheHandlerDoesNotRead` (the client stops at 65,535 bytes, no stream WINDOW_UPDATE, the server buffers exactly one window), `readingHandlerGetsTimelyBatchedUpdates` (a 1 MiB upload through 64 KiB windows completes, with every stream increment at least half a window), `windowAccountingAcrossManyStreams` (20 streams × 50,000 bytes are charged to the connection window until read, and every consumed byte is credited exactly once), `smallerAdvertisedWindowIsEnforced`.
  - The existing #0048 body tests (`dataBeyondTheStreamWindowIsAFlowControlError`, `unreadBodyGetsNoStreamCredit`, `paddingIsNotDelivered`) still pass.

## Gotchas

- Padding stream credit is deferred to the next stream update rather than sent at once, so a stream that only ever sends padding never gets stream credit back. Such a peer gains nothing (no payload is delivered) and is reset when its response ends.
- There is no auto-tuning: the windows are fixed by `initialWindowSize` and `connectionWindowSize`.
