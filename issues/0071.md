## Description

HTTP/3's largest unknown is whether `NWProtocolQUIC` with `NWListener.newConnectionGroupHandler` gives a server everything RFC 9114 needs. Answer that in a one-day spike before any Track A code is written. The output is a report, not production code.

## Scope

- A throwaway spike (under `docs/spikes/quic/` or a scratch executable not wired into the package) using Option A from ROADMAP §6: `NWProtocolQUIC`, one `NWConnectionGroup` per QUIC connection, `group.newConnectionHandler` for inbound streams, `NWConnection(from:using:)` with `direction = .unidirectional` for server streams.
- Answer each question with observed evidence (log excerpts, commands run): (1) the listener accepts `/opt/homebrew/opt/curl/bin/curl --http3-only -k` and an NW QUIC client; (2) inbound stream direction and stream ID are readable; (3) the server can open three unidirectional streams; (4) FIN maps both ways (`isComplete` on receive, `.finalMessage` on send); (5) reset and STOP_SENDING codes are readable and settable; (6) the connection closes with an application error code; (7) backpressure works by not calling `receive`, with send completion as the flow signal; (8) 0-RTT behaviour; (9) per-stream memory and setup cost; (10) TCP and UDP listeners on the same port; (11) client tooling: Homebrew curl HTTP/3 and `URLSession` with `assumesHTTP3Capable` plus a trust override for the test identity.
- Write `docs/spikes/quic-spike.md` with the answers, the Swift API calls used, surprises, and a go/no-go.
- Gate (ROADMAP §6): if any of questions 1–7 fails, the report says so, Track A pauses, Track B is promoted, and Option B goes to the owner.

## Gotchas

**Gate decision (orchestrator): conditional GO.** Questions 1–5, 7, 10 and 11 work. For question 6, close works but the application error code on CONNECTION_CLOSE could not be observed; it is a diagnostic detail that does not block HTTP/3 serving and is now verified under #0104. Question 8: no 0-RTT or resumption, which is safe by default. Cost is about 590 allocations and 0.4–0.8 ms per stream inside NW, the floor for #0105.

- Set a client group's `newConnectionHandler` before `start`, or the group never starts.
- Every send needs `isComplete: true` on its context; `.defaultMessage` with `isComplete: false` blocks later sends.
- MAX_STREAMS is not replenished automatically; raise `groupMetadata.localMaxStreamsBidirectional` as streams finish.
- `group.cancel()` doesn't close while any stream is alive, including the never-started stream ID 0 the NW client opens.
- Route by each stream's `negotiatedALPN`; URLSession streams can arrive while the group is still `waiting`.
- The first run imported the identity into the login keychain; load it only with `kSecImportToMemoryOnly`.
