## Description

Features must be opt-in components that cost nothing when absent (ROADMAP §1.1). `docs/MIDDLEWARE.md` stopped at "the interface needs to be defined" and #0031 proposed one handler. Build the middleware chain as a nested generic from a result builder, plus the per-request context and server-level component registration.

## Scope

- `@MiddlewareBuilder` producing a nested generic chain ending in a handler; `if`/`if-else` support for configuration-driven components; static dispatch through the chain (no existentials).
- `RequestContext`: connection info, request start time, a small typed storage for components (e.g. auth principal, virtual host), and a per-connection metrics shard.
- `ServerComponent.run(server:)` registration for components with background work (e.g. metrics scraping); components started inside the server task group.
- Wire `enableCompression`/`enableETags`-style flags to component registration (#0024 part).
- `HTTPHandler` dispatch from parts of #0031.

## Acceptance criteria

- Tests: a chain of three middlewares runs in order and can short-circuit; a conditional component absent from the chain is not called.
- `sws-bench` shows no measurable difference (< 2%) between an empty chain and a chain with a disabled conditional component.

## Root cause

There was no way to compose optional features: `Server` took one handler, `RequestContext`
held only the connection info, and nothing ran background work for a component.

## Fix

- `MiddlewareBuilder` (`Sources/HTTPCore/MiddlewareBuilder.swift`): fixed-arity `buildBlock`
  overloads (up to 10 elements) nest middlewares to the right in front of the handler
  (`MiddlewareChain<A, MiddlewareChain<B, H>>`), so a request only borrows stored values;
  `OptionalMiddleware` for `if`, `EitherMiddleware`/`EitherHandler` for `if`/`else`,
  `ComposedMiddleware` for handler-less blocks, `NotFoundHandler` as the default terminal,
  `PassthroughMiddleware` for `{}`. All `@inlinable`. The result is wrapped in
  `CompiledChain`, a closure created by the inlinable `buildFinalResult` where the chain is
  written, because the protocol runners are reached through `any ConnectionProtocol` and run
  unspecialized; inside the closure the whole chain inlines. A lone handler is returned as is.
- `RequestContext` (`RequestContext.swift`): `connection`, `startTime: MonotonicInstant?`
  (raw `mach_continuous_time` ticks; stamped only when a `RequestStartTimeConsumer` is in the
  chain, via `ConnectionContext.recordsRequestStartTime`), and typed values through
  `RequestContextKey` stored in an immutable linked list that allocates only when a component
  sets a value.
- `ServerComponent`, `ServerHandle`, `MiddlewareChainContainer`, `MiddlewareChainInspector`
  (`ServerComponent.swift`): the server finds components in `components:` and in the chain
  (absent `if` components are not found), runs them as child tasks after binding, cancels
  them after the last connection closes, and rethrows a component failure from `run()` after
  draining.
- `Server`: builder initializer `Server(configuration:listeners:protocols:components:) { … }`;
  `handler:` unchanged (plus an optional `components:`).
- HTTP/1.1 runner stamps its stored context in place only when asked; HTTP/3 likewise.
- `HTTPHandler`/`HTTPMiddleware` signatures unchanged.

## Gotchas

- With `buildPartialBlock` present, `buildBlock` overloads are ignored. A left fold makes every
  `ComposedMiddleware` build `MiddlewareChain(inner, next)` per request, copying the rest of the
  chain (retains/releases per layer). Hence fixed-arity right-nested `buildBlock`s; more than 10
  elements need an `if true { … }` group (which is a `ComposedMiddleware`).
- An unspecialized chain is expensive (generic async call per layer plus value-witness copies);
  marking chain methods `@inlinable` alone does not help because the runners are unspecialized.
  Only code compiled in the module that names the concrete types is specialized, hence the
  closure in `CompiledChain`. A capture-less closure (root passed as an argument) avoids a
  partial-apply forwarder hop.
- Copying `RequestContext` per request and mutating it behind a branch cost 7–12 ns in the
  HTTP/1.1 loop even when the branch was not taken; stamping the driver's stored context in
  place removed it. `ContinuousClock.now` is ~33 ns; `mach_continuous_time` ~4 ns.
- Not done here: the per-connection metrics shard (belongs with AccessLog/metrics, #0090) and
  wiring config-file flags to components (`ConfigFile`, #0086); the builder's `if` is the hook
  for both. Removing the last `CompiledChain` hop needs runners specialized on the handler type.
