## Description

Encode response header fields (RFC 7541 §6) for use by the connection's single frame writer.

## Scope

- Indexing strategy: an exact static or dynamic match uses the indexed form. A name match uses a literal with incremental indexing for cacheable fields.
- Never-indexed representation for `authorization`, `cookie`, `set-cookie`, and fields the caller marks sensitive.
- Huffman coding when shorter.
- The encoder honors the peer's `SETTINGS_HEADER_TABLE_SIZE` by emitting a size update at the start of the next block after a change.

## Acceptance criteria

- Encoder output decodes to the same fields through #0040, including the dynamic table state.
- Appendix C.5 and C.6 response examples encode byte-for-byte when using the RFC's indexing choices.

## Root cause

Feature work: HPACK could decode (#0040) but not encode.

## Fix

- `HPACKEncoder` is a value type with no I/O that writes into any `ByteSink`. A block is `beginHeaderBlock(into:)`, which emits any pending size updates, followed by one `encode(name:value:indexing:into:)` per field.
- Indexing: an exact static match is used first, then an exact dynamic match, as the indexed form. Otherwise the name comes from the static table (preferred, as in RFC C.5.2) or the dynamic table.
- `HPACKIndexingPolicy.automatic` sends `authorization`, `cookie`, `set-cookie` and `proxy-authorization` never-indexed. It does not index volatile names (`:path`, `content-length`, `etag`, conditionals, …) or entries over 3/4 of the table, and indexes everything else incrementally. `.incremental`, `.withoutIndexing` and `.neverIndexed` override that per field; `.neverIndexed` is how a caller marks any field sensitive.
- Huffman follows `StringLiteral.HuffmanPolicy`, by default `.whenShorter`.
- `setPeerMaxTableSize` clamps the new size to the encoder's capacity and shrinks the table immediately. The next block starts with the smallest size set since the last block, then the final size (RFC 7541 §4.2). An encoder whose capacity is below the peer's initial 4,096 announces its size in the first block.
- `Sources/sws-bench/HPACKBench.swift` measures steady-state encode and decode of an 11-field browser request. It is not registered in the harness. `Package.swift` adds `HPACK` to the SWSBench dependencies (one line).
- 0deaa9a updates the `HPACKError` doc now that #0036 is on `main`: `HTTP2` maps any `HPACKError` to `HTTP2Error.connection(.compressionError, reason:)`. HPACK cannot depend on HTTP2.

## Gotchas

- The RFC's C.6.2 Huffman-codes "307" although Huffman is no shorter (3 bytes either way), so a byte-exact C.6 needs `.always`. C.4 matches `.whenShorter`.
- RFC C.5.3 and C.6.3 index `set-cookie`; this encoder never does on its own, so the tests pass `.incremental` for that field.
- `ByteBuffer` does not conform to `ByteSink` yet. HTTPCore cannot depend on HeaderCompression, and a retroactive conformance in HPACK would clash with QPACK. The frame writer (#0044) needs to settle where that conformance lives.
