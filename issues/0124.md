## Description

Expose the reverse proxy through `http-config.json` so the shipped binary can replace an Apache `mod_proxy` front end, for example a static website at `/` with `/cgi-bin` (or `/api`) proxied to a Go app on localhost.

## Scope

- A `proxy` config key: a list of mounts, each with:
  - `path` (prefix, default `/`), optional `host`/`hosts`
  - `upstream` or `upstreams` (`http://127.0.0.1:9000[/base]` or `unix:/path/to.sock`)
  - `stripPrefix`, `preserveHost`, `forwardedHeaders` (`x-forwarded` | `forwarded` | `both` | `none`), `trustedProxies`
  - `rewriteLocation`, `websocket`, `timeouts`, `retries`, `healthCheck`, and `maxConnections` and pool settings
- Ordering in the chain: Auth, then the proxy mounts, then StaticFiles/ErrorPages. Mounts take precedence for their prefix and everything else falls through to the static site. Works per virtual host (`hosts[].proxy`).
- The example config already exists: `Root/http-config.proxy.json` serves static `Root/Public` at `/` and proxies `/api` to the Go app `Examples/go-api` on `127.0.0.1:9000` (`stripPrefix: false`, since the Go app serves `/api/...` itself). Until this milestone lands, the server warns that `proxy` is an unknown key and ignores it. Make the config work as written, or adjust it and the docs together. A README section "Reverse proxy (replacing Apache mod_proxy)" maps `ProxyPass`/`ProxyPassReverse`/`ProxyPreserveHost` and `RequestHeader set X-Forwarded-Proto` to the equivalent keys.
- Upstream for docs and tests: `Examples/go-api`, a stdlib-only Go REST API (`/api/health`, `/api/items` CRUD, and `/api/echo`, which returns the request as the app saw it, including the forwarded headers). Integration tests build it with `go build` when `go` is on PATH and skip otherwise, keeping a Swift test upstream for the unit tests. It also listens on a Unix socket (`-unix PATH`) to test that path.

## Acceptance criteria

- The real binary from the example config: `curl -k https://…/` serves the static index, `curl -k https://…/api/items` (GET/POST/PUT/DELETE) reaches the Go app over h1, h2 and h3, `/api/echo` shows `X-Forwarded-For/Proto/Host` set correctly, and a WebSocket upgrade through a mount works (Swift test upstream). A config error naming the bad key exits 1.
- Benchmark in `docs/benchmarks/M17-proxy.md`: proxied hello-world keep-alive throughput and the added p50/p99 latency compared with hitting the upstream directly, alongside Apache `mod_proxy` (`/usr/sbin/httpd` with `ProxyPass`, loopback only) and nginx `proxy_pass` on the same upstream.

## Root cause

The `proxy` key, `ReverseProxy` and the chain wiring had landed (`a95e37f`), but the issue
still lacked per-virtual-host mounts (`hosts[].proxy`), real-binary acceptance over TLS for h1,
h2 and h3, and the benchmark. Working on them found two real bugs:

- Over HTTP/3, proxied requests had no `X-Forwarded-For`: server-side QUIC connections were
  created with `remote: nil`, and the peer address was only merged in from streams after the
  `ConnectionContext` had been copied for the connection.
- `pool.maxIdle` above 16 was silently ignored: the config built `UpstreamHTTP1Client()` with
  its default `maxIdlePerTarget` (16), which caps every mount's policy. With more than 16
  concurrent proxied requests the extra upstream connections were closed after each exchange,
  which at 64 connections filled the loopback port range with TIME_WAIT sockets and produced
  502s.

## Fix

- `hosts[].proxy` (same form as `proxy`): each site's chain is its own `ReverseProxy`, then the
  server-level mounts (`NestedReverseProxy`), then its files, so a site's mount wins for that
  site. The server-level proxy is registered once at the top (`ProxyMountsLifecycle`, a chain
  container) so its health checks and idle sweep run once; all mounts share one client.
- `QUICListener.accept` passes the group's peer (`NWMultiplexGroup.members.first`) to
  `QUICConnection`.
- The shared client's `maxIdlePerTarget` is the largest configured `pool.maxIdle` (at least 16).
- `http3.qpackMaxTableCapacity` / `qpackBlockedStreams` (default 0) are parsed and passed to
  `H3Configuration` (#0106).
- README: "Reverse proxy (replacing Apache mod_proxy)" with a directive-to-key table, `hosts[].proxy`
  and the QPACK keys. `scripts/bench-proxy.sh` and the results in `docs/benchmarks/M17-proxy.md`
  and `docs/SERVER-COMPARISON.md`.

## Gotchas

- With the default `pool.maxIdle` (16), more than 16 concurrent proxied requests still churn
  upstream connections; on loopback that exhausts ephemeral ports within seconds and breaks
  whatever runs next (Apache's and nginx's rows in the first run failed from the SWS run's
  TIME_WAIT). Set `maxIdle` to the expected concurrency, like nginx's `keepalive`. Consider a
  larger default.
- Apache mod_proxy needs `DefaultRuntimeDir`/`Mutex file:` pointing at a writable directory
  when run as a user, or it fails creating the proxy mutex in `/private/var/run`.
- The NetworkTransport change is outside the issue's targets but was required for correct
  `X-Forwarded-For` over h3.
- Follow-up: the per-read timeout race (8–10 µs, ~17 allocations per request) explains most of
  the 10–20% gap to Apache/nginx under concurrency.
