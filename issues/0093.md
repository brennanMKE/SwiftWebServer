## Description

Provide opt-in authentication for selected path prefixes.

## Scope

- Basic auth against a configured credential file (hashed passwords, constant-time compare) and static bearer tokens.
- `401` with `WWW-Authenticate` on missing or bad credentials; principal stored in `RequestContext`.
- Never logs credentials; `authorization` marked sensitive so HPACK/QPACK use never-indexed literals.

## Acceptance criteria

- Tests for valid, invalid and missing credentials and constant-time comparison helper.
- `curl -u user:pass` succeeds and `curl` without credentials gets 401 on a protected path.
- `sws-bench` shows no change (< 2%) with the component unregistered.

## Root cause

New component: the `Auth` target was a placeholder namespace. Also the legacy TODO "HMAC validation for JWT tokens".

## Fix

- `Authenticator` (middleware) holds `AuthPolicy`s: path prefixes, realm, and the accepted schemes. The first policy covering the path decides; other paths pass through after one prefix check. Prefixes match whole segments of the percent-decoded path, case-insensitively, skipping empty and `.` segments, and any `..` segment counts as covered (errs toward protecting: `/ADMIN`, `/%61dmin`, `//admin`, `/x/../admin` are all covered). Prefixes live in one flat `ScopeTable`.
- Basic: `CredentialStore` of `user:$pbkdf2-sha256$<iterations>$<salt>$<key>` lines (PBKDF2-HMAC-SHA256 via CommonCrypto `CCKeyDerivationPBKDF`, default 600,000 iterations, 16-byte salt). Plaintext lines are refused. The derived key is compared with `ConstantTime.equals`; unknown users run PBKDF2 against a dummy hash. Verified header values are cached (256 slots, 5 minutes) under a per-process random HMAC key, so repeat requests cost one HMAC.
- Bearer JWT: `JWTVerifier` pins `alg` to `HS256` (`none`, `HS384/512`, `RS/ES/PS*`, wrong case and headers with `crit` are refused before any key is used), selects keys by `kid` (or the key without an id), requires keys ≥ 32 bytes, checks the signature (constant time) before reading claims, then `exp` (required unless turned off), `nbf` (both with leeway), `iss` and `aud` (string or array). Duplicate members, wrong claim types and tokens over 8 KiB are malformed. Base64url and JSON are decoded in stack buffers by a byte-level scanner; `sub` is the only `String`.
- Static bearer tokens (`BearerToken`) are stored as SHA-256 digests and compared against every configured digest.
- Failures: `401` with one `WWW-Authenticate` per accepted scheme (`Basic realm="…", charset="UTF-8"`; `Bearer realm="…"`, plus `error="invalid_token"` for a refused token) and `Cache-Control: no-store`. `FailureLimiter`: a fixed power-of-two table of per-peer buckets (failures in a window; colliding peers share a count); a blocked peer gets `429` with `Retry-After` before any hashing. Missing credentials and other schemes are not counted.
- On success the `Principal` (name, scheme, JWT claims) is set as `context.principal`. `auth.protect(handler)` returns `Authenticated<H>` for single routes (e.g. `GET("/me", handler: auth.protect(…))` on the Router); the authenticator in front of a Router covers whole prefixes.
- HMAC and SHA-256 on the request path use CommonCrypto one-shot calls (`CCHmac`, `CC_SHA256`) instead of CryptoKit, which allocated 2-9 blocks per request (see Gotchas). No keychain anywhere: secrets come from the config or environment.
- ConfigFile: `"auth": [{"paths", "realm", "basic": {"file" | "users" | "usersEnv"} or a file name, "jwt": {"keys": [{"id", "secret" | "secretEnv"}], "issuer", "audience", "leeway", "requireExp"}, "tokens": [{"name", "sha256"}]}]` (or one object); registered after `ErrorPages`, in front of the files or `VirtualHosts`. `makeHandler(environment:)` takes the environment (the executable passes its own).
- `sws-bench hash-password --user NAME [--iterations N]` (password on stdin) and `scripts/hash-password.sh USER` (prompts without echo) print a credential line.
- `sws-bench micro --filter Auth`.

## Gotchas

- CryptoKit's `HMAC<SHA256>.authenticationCode` and `SHA256.hash` allocate per call (JWT verify was 1.6 µs with 9 allocations, the Basic cache hit 1.2 µs with 8). CommonCrypto's `CCHmac`/`CC_SHA256` into stack buffers allocate nothing and halve the time, so the brief's "CryptoKit" became CommonCrypto (also a system library, no keychain). The test suite still signs tokens with CryptoKit, which cross-checks the two.
- PBKDF2 is deliberately expensive (about 85 ms of CPU per uncached Basic check at 600,000 iterations). The verified-value cache and the failure limiter keep that off the common path; tests use 1,000 iterations.
- Scope matching must not trust the raw path: StaticFiles decodes `%XX` once and the default macOS file system is case-insensitive, so `/%61dmin` and `/ADMIN` reach `/admin`. Prefixes are therefore compared decoded and case-insensitively, and `..` anywhere puts a request in scope.
- The first scope check iterated `[AuthPolicy]`, copying a struct of ten references per policy (127 ns pass-through); the flat `ScopeTable` brought it to about 37 ns.
- `Span` cannot be stored in an escapable struct, so the JSON scanner works on `UnsafeBufferPointer` over the stack buffers.
- `"\r\n"` is one `Character` in Swift: credential lines split on `isNewline`, not `"\n"`.
- `authorization` was already a sensitive (never-indexed) name in the HPACK encoder; nothing in Auth logs credentials. The QPACK encoder was not checked (outside this issue's targets).
- The `<2%` "unregistered" criterion holds by construction (no change outside Auth, ConfigFile wiring, sws-bench); `h1conn` was not rerun because other agents were building.
