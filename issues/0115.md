# 0115 — Two QUIC transport tests fail intermittently under heavy load

| | |
|---|---|
| **Status** | open |
| **Module** | NetworkTransport / Tests |
| **Platform** | macOS |
| **First seen** | 2026-11-11 |

## Description

Two tests in `NetworkTransportTests` fail intermittently when the load average is above about 40 and pass on rerun:

- `QUICTransportTests.echoUniAndResetAgainstARawNWClient`: `secondPeer.receivedResetCode == 0x10b` fails (wrong or missing reset code). Seen in the #0104 agent's full run (load about 70) and in the orchestrator's run after merging M12 (load about 50, commit 2833f15).
- `MultiplexedTransportConformanceTests.connectionCloseFailsStreamsAndEndsInboundOnBothSides` (quic case): a stream still arrives after close. Seen in the #0104 run and the M12 agent's full run (load about 41).

They passed 5 of 5 in focused reruns at load about 49, and 8 of 8 at load 10–28.

## Expected behavior

Deterministic under any load: timing-dependent expectations wait for the event with a deadline rather than racing it.

## Notes

- `docs/notes/nw-transport.md`: Network.framework sends stream resets and STOP_SENDING with code 0 during close, plus a FIN on a server stream 1 it never opened (#0104 Q6 finding). The reset-code expectation may race NW's own code-0 reset of the same stream.
- A stream "arriving after close" may be NW's phantom stream 1 seen in #0098/#0104. If so, the transport should filter streams that arrive after close began, or the test should account for it.
- Reproduce with `scripts/guarded.sh -t 600 -- swift test -j 2 --filter NetworkTransportTests` in a loop under `yes > /dev/null` × 12 load.
