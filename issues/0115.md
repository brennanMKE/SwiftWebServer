## Description

Two tests in `NetworkTransportTests` fail intermittently when the load average is above about 40 and pass on rerun:

- `QUICTransportTests.echoUniAndResetAgainstARawNWClient`: `secondPeer.receivedResetCode == 0x10b` fails (wrong or missing reset code). Seen in the #0104 agent's full run (load about 70) and in the orchestrator's run after merging M12 (load about 50, commit 2833f15).
- `MultiplexedTransportConformanceTests.connectionCloseFailsStreamsAndEndsInboundOnBothSides` (quic case): a stream still arrives after close. Seen in the #0104 run and the M12 agent's full run (load about 41).

They passed 5 of 5 in focused reruns at load about 49, and 8 of 8 at load 10–28.

## Expected behavior

Deterministic under any load: timing-dependent expectations wait for the event with a deadline rather than racing it.

## Notes

- `docs/notes/nw-transport.md`: Network.framework sends stream resets and STOP_SENDING with code 0 during close, plus a FIN on a server stream 1 it never opened (#0104 Q6 finding). The reset-code expectation may race NW's own code-0 reset of the same stream.
- A stream "arriving after close" may be NW's phantom stream 1 seen in #0098/#0104. If so, the transport should filter streams that arrive after close began, or the test should account for it.
- Reproduce with `scripts/guarded.sh -t 600 -- swift test -j 2 --filter NetworkTransportTests` in a loop under `yes > /dev/null` × 12 load.

## Root cause

- **`echoUniAndResetAgainstARawNWClient` (reset code): a transport bug.** A peer reset moves the stream `NWConnection` to `.failed(ECONNRESET)` on its own (nw-transport observation 6). `QUICStreamTransport` read the peer's code only in a failing receive's completion. When the state change landed between two receives, the next receive failed from the stored failure and the code was never read, so `receivedResetCode` stayed `nil`. HTTP/3 would see a reset with no code.
- **`connectionCloseFailsStreamsAndEndsInboundOnBothSides` (quic): a test race.** The failure was `next == nil` on the client after the server closed. Network.framework's close always sends STOP_SENDING and a FIN on server-initiated bidirectional stream 1, which the server never opened. A raw NW client received that stream after 15 of 15 closes, also without setting `applicationError` and without reading the group metadata. A `QUICConnection` client usually fails its group (`EINVAL`) first and drops it. Under load, in about 1 of 150 closes, it became ready first (ID 1, no data, then `.failed(ENOTCONN)` with no code) and was handed to `inboundStreams`. The client had not begun a close, so the transport kept its contract. When the stream becomes ready, it looks like a real server-opened stream 1. Only clients see it, and HTTP/3 here is server-only.

## Fix

- `QUICStreamTransport.Core` reads `streamApplicationErrorCode` in its `.failed(ECONNRESET)` handler. It records the code as the RESET_STREAM code while this end still receives, else as the STOP_SENDING code. The first code wins, and our own echoed code is ignored.
- The conformance close test drains the client's inbound streams until iteration ends, with a 10 s deadline. For QUIC it allows at most one extra stream. That stream must be ID 1 and dead (FIN with no data, or `connectionReset`). In memory it still requires none.
- New `QUICTransportTests.peerResetCodeIsCapturedWhenTheStreamFailsBeforeAReceive` forces the late ordering by waiting for the peer abort before receiving.

## Gotchas

- The phantom stream 1 reaches an NW peer on every close, not only sometimes. Whether a `QUICConnection` client hands it over depends only on whether the stream becomes ready before the group fails.
- When the phantom fails it reports `ENOTCONN` with no code, not a reset. `TransportError` maps it to `connectionReset`.
- The `QUICCloseCodeTests` known issues print as `✘ ... recorded an issue` lines. Exclude `known issue` when you grep logs for failures.
