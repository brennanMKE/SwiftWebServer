## Description

Found while writing the developer guides. The executable handles SIGINT/SIGTERM with a graceful drain, but SIGHUP isn't handled, so the default action terminates the process mid-request. Front ends like Apache and nginx reload their config (and reopen log files) on SIGHUP, and the access log (#0125) has no rotation, so a reopen hook matters for long-running deployments (for example the LaunchAgents in `Examples/parallax-gordon`).

## Scope

- Handle SIGHUP: at least reopen the access log file (for newsyslog/logrotate-style rotation).
- Optionally reload `http-config.json`: parse and validate the new file; on success swap the handler chain for new requests while in-flight ones finish on the old one; on failure log the error and keep running. Listener address/port/TLS changes may require a restart; document which keys reload.
- No `DispatchQueue` outside the existing signal-source exception.

## Acceptance criteria

- Integration test with the real binary: rename the access log, send SIGHUP, the next request lands in a new file; a config change (for example a new proxy mount) takes effect without dropping an in-flight request; an invalid config on reload keeps the old one.

## Root cause

The executable installed DispatchSource handlers for SIGINT and SIGTERM only, so SIGHUP kept its default action (terminate, no drain). The handler chain was a fixed generic value handed to `Server` at startup, and the server discovers components and connection observers in it once, so there was no way to swap it; `AccessLog` opened its file once in its writer.

## Fix

- `ReloadableHandler<H>` (ConfigFile, new file): one handler that is also `ConnectionObserver`, `ServerComponent` and `RequestStartTimeConsumer`, holding generations of the chain. `replace(with:)` makes a new chain current; each connection is opened and closed with the observers of the generation current when it opened; each request runs on the generation current when it starts. A generation's components (log writer, proxy pools) run as children of `run(server:)` and are cancelled once it is not current and every connection opened while it or an older one was current has closed.
- Request path: the connection's generation from its `RequestContext` (non-generic key) followed through write-once successor links (`Atomic<Unmanaged<…>?>`, one acquiring load). No lock, no allocation. Requests without connection state take a `Mutex`.
- `AccessLog.reopen()`: bumps an atomic and wakes the writer with an empty batch; the writer reopens a file destination by its path before the next write (on failure keeps the old descriptor and counts a write error).
- `ServerMain`: a SIGHUP DispatchSource on the existing signal queue (serial, so reloads never overlap; ignored unless running). It loads the settings again (same file and CLI overrides), validates and builds the chain; on success reopens the old chains' logs and swaps; restart-only changes (`host`, `port`, `transport`, `tls`, `http2`, `http3`, `maxConnections`, `drainTimeout`, `timeouts`, `maxBodySize`, via `ServerSettings.restartOnlyChanges`) are reported as `needs a restart, ignored`. On failure: `reload failed, keeping the running configuration: …`, logs reopened.
- Docs: `docs/guide/running-on-a-mac.md` (rotation recipe, reload table), README, `--help`.

## Verification

- `ReloadIntegrationTests` (real binary, 127.0.0.1 port 0): rename the access log + SIGHUP → next request in a new file, old lines in the renamed one; again with an unparsable config → log still reopened. A 6 MiB download at 2 MB/s across a reload completes byte-identical while a new `/api` proxy mount starts working; a `host` change is reported as needing a restart; invalid JSON and a missing root keep the running config.
- `ReloadableHandlerTests`: swap order, observers per connection, old chain's component stopped only after its connection closed.
- `swift test -j 2`: 1632 tests, all pass except one unrelated flaky `TLSTransportTests.opensslSeesCloseNotifyOnlyOnClose` (passes on rerun).
- `sws-bench h1conn` (release, load avg 6.5–7): keepalive empty 270.8 / reloadable 281.7 ns/req; pipelined16 empty 195.1 / reloadable 216.0; dispatch empty 42.5 / reloadable 50.9 / reloadable-locked 49.0; 0 allocs/req everywhere.

## Gotchas

- Generic types on the request path cost metadata lookups: a context key nested in the generic handler and `AtomicLazyReference<Generation<H>>` each added ~90–100 ns per request. The key and the successor link are non-generic (`ReloadGenerationKey`, `ReloadGenerationLink`), and the specialized `Generation` is recovered with `unsafeDowncast`; hence one `ReloadableHandler` per chain.
- Requests on a keep-alive connection opened before a reload use the new chain, but the access log's per-connection buffer belongs to the old chain, so the new chain's log records them through its shared (locked) buffer until the connection closes.
- Access log metrics restart from zero after a reload (new chain, new counters). A new access log path is checked by `makeAccessLog` before the swap, so a reload cannot shut the server down through the writer's open error.
- TLS identity, listeners and protocol settings are not reloaded; changing them needs a restart.
