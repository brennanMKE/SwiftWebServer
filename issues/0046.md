## Description

A header block is one HEADERS (or PUSH_PROMISE) frame followed by zero or more CONTINUATION frames on the same stream, ending with END_HEADERS (§4.3, §6.10).

## Scope

- While a block is open, any frame other than CONTINUATION on the same stream is a connection `PROTOCOL_ERROR`.
- Accumulated block size is capped at `SETTINGS_MAX_HEADER_LIST_SIZE` before HPACK decoding (CONTINUATION flood defense, see #0056).
- The assembled block is decoded once, in order, and every block is decoded (even for refused or reset streams) to keep HPACK state in sync.
- Trailers: a second HEADERS block with END_STREAM.

## Acceptance criteria

- Tests cover a block split into many CONTINUATIONs, an interleaved frame (error), an oversized block (error), and a block on a refused stream that still updates the dynamic table.

## Root cause

Feature work: the frame parser (#0034) reports HEADERS, PUSH_PROMISE and CONTINUATION payloads as opaque fragments and leaves their sequencing and assembly to the layer above. That layer did not exist.

## Fix

- `HeaderBlockAssembler`: a value-type state machine, `mutating func handle(_ event: Event) -> Action`. Events are `headers`, `pushPromise`, `continuation` (each with its padding-free fragment as an `UnsafeRawBufferPointer` from `HTTP2FrameParser.withPayload`) and `otherFrame(type, streamID)`. Actions are `proceed`, `needsContinuation`, `decode(HeaderBlock)` and `connectionError(code)`.
  - Sequencing (§6.10): while a block is open, any frame other than CONTINUATION on the same stream is a connection `PROTOCOL_ERROR`. That includes unknown types, HEADERS, PUSH_PROMISE, and CONTINUATION on another stream. A CONTINUATION with no open block is also a `PROTOCOL_ERROR`. After a connection error the assembler stays failed.
  - Zero-copy single frame: a block that ends in its HEADERS frame is reported with `isAssembled == false` and decoded straight from that frame's fragment. A split block is copied into one `[UInt8]` buffer. The buffer reserves `maxBlockSize` the first time it is needed and is reused with `removeAll(keepingCapacity:)`.
  - CONTINUATION flood defence (VU#421644, docs/HTTP2.md, #0056): `maxBlockSize` (default 16,384 = SETTINGS_MAX_HEADER_LIST_SIZE) caps the encoded bytes, and `maxContinuationFrames` (default 32) caps CONTINUATIONs per block. Both are checked on every frame, so the frame that crosses a limit fails immediately with a connection `ENHANCE_YOUR_CALM` and the buffer is released.
  - HPACK hand-off: `decode(_:fragment:with:into:)` passes the complete block to `HPACKDecoder.decode` as a `Span`. Any `HPACKError` becomes a connection `COMPRESSION_ERROR` through the new `HTTP2Error.init(_: HPACKError)`. The caller decodes every block, including blocks on refused, reset or GOAWAY-ignored streams, so the dynamic table stays in step.
  - Trailers: `HeaderBlock.kind` is `.headers` for a stream's first block and `.trailers` for a HEADERS block on a stream at or below `highestHeadersStreamID`. Client streams increase, and `HTTP2StreamTable` (#0045) rejects HEADERS on streams that cannot carry one. That table also rejects a second block without END_STREAM, with a stream `PROTOCOL_ERROR`. PUSH_PROMISE blocks are `.pushPromise(promisedStreamID:)`.

## Gotchas

- Oversized or over-count blocks are connection `ENHANCE_YOUR_CALM`, following #0056. RFC 9113 §4.3 would also allow `COMPRESSION_ERROR` for a block the receiver declines to decompress. Either way it must be a connection error, because a block that is not decoded desynchronises HPACK.
- `maxBlockSize` caps encoded bytes. `HPACKDecoder.maxHeaderListSize` separately caps the decoded list (name + value + 32 per field), which defends against HPACK bombs.
- `HeaderBlock.isAssembled == false` means the bytes live only in the current frame's fragment. Call `decode` inside the same `withPayload` scope as `handle`.
- `Array.span` needs macOS 26, so the assembled buffer is exposed through `withUnsafeBufferPointer { $0.span }`.
- Trailer recognition assumes server role and that `HTTP2StreamTable` vetted the HEADERS frame. A client receiving 1xx responses would need per-stream counting instead.
