## Description

Follow-up from the #0108 Gotchas. `HTTPRequest` carries no HTTP version, so `WebSocketUpgrade` cannot tell an HTTP/1.0 request from an HTTP/1.1 one. RFC 9110 §7.8 says a server must ignore `Upgrade` in an HTTP/1.0 request, and RFC 9110 §15.2 says it must not send a 1xx response to an HTTP/1.0 client; RFC 6455 §4.1 requires HTTP/1.1 or later for the opening handshake. Today a well-formed handshake sent as `HTTP/1.0` gets `101`.

## Expected behavior

The request (or its context) exposes the HTTP version. `WebSocketUpgrade` ignores `Upgrade: websocket` on HTTP/1.0: with no path the request goes to the next handler, and on the component's path it is answered `400` without switching protocols.

## Scope

- An `HTTPVersion` value on `HTTPRequest`, set by the HTTP/1.1 runner from the request line (and by HTTP/3; HTTP/2 when its runner is next touched).
- `WebSocketHandshake.validate` rejects HTTP/1.0.
- Tests: the HTTP/1.1 parser reports both versions on the request; an HTTP/1.0 handshake through `HTTP1().run` gets `400`, not `101`.

## Root cause

The HTTP/1.1 parser records the request line's version in `HTTP1RequestHead.version`, but
`HTTP1RequestHead.request(in:)` dropped it when building the protocol-independent
`HTTPRequest`, which had no version field. Components therefore could not apply the rules
that depend on it, and `WebSocketUpgrade` answered a valid handshake sent as `HTTP/1.0`
with `101`.

## Fix

- `HTTPCore`: `HTTPVersion` (`major`, `minor`; `.http1_0`, `.http1_1`, `.http2`, `.http3`;
  `Comparable`, `HTTP/1.1` / `HTTP/3` descriptions) and `HTTPRequest.version`, an `init`
  parameter defaulting to `.http1_1`; `snapshot()` keeps it. Two bytes in the request value,
  no allocation.
- `HTTP1`: `request(in:)` sets `.http1_0` or `.http1_1` from the request line.
- `HTTP3`: requests carry `.http3` (#0111 relies on it). HTTP/2 does not set it yet and
  reports the default (`.http1_1`); see Gotchas.
- `WebSockets`: `WebSocketHandshake.isUpgradeRequest` is false for HTTP/1.0 (the `Upgrade`
  field is ignored, RFC 9110 §7.8), so a component with no path passes the request on;
  `validate` throws the new `Failure.unsupportedHTTPVersion` (`400`) before any other check, so
  a component with a path answers `400` and never `101`.

## Verification

- `HTTP1ParserTests.requestCarriesTheHTTPVersion` (new): an `HTTP/1.0` request line gives
  `request.version == .http1_0` (and on its snapshot); `parsesIntoRequestStorage` checks
  `.http1_1`; description and ordering of `HTTPVersion`.
- `WebSocketUpgradeTests.http10HandshakeIsRejected` (new): the RFC 6455 handshake sent as
  `HTTP/1.0` through `HTTP1().run` gets `400` with no `Sec-WebSocket-Accept` on the
  component's path, and `404` from the next handler with a path-less component.
- `H3WebSocketTests.requestsSeeHTTP3AndTheConnectProtocol` (#0111): HTTP/3 requests report
  `.http3`.

## Gotchas

- HTTP/2 requests report `HTTPVersion.http1_1` until the HTTP/2 runner passes
  `version: .http2` when it builds `HTTPRequest` (a one-line change in `Sources/HTTP2`, left
  alone here because another agent owned that target). Nothing depends on it yet: the
  HTTP/1.0 check only compares against `.http1_0`.
- The version is on the request rather than `RequestContext`, because it is a property of
  each request line (a connection can carry `HTTP/1.0` and `HTTP/1.1` requests).
