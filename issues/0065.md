# 0065 — Support RFC 9218 extensible priorities for response scheduling

## Description

Use the `priority` request header and PRIORITY_UPDATE frames (type 0x10) to order which streams' DATA the writer sends first.

## Scope

- Parse the `priority` structured field (urgency 0–7, incremental).
- Handle PRIORITY_UPDATE on stream 0 with validation.
- Frame writer scheduling: lower urgency first, round-robin among incremental streams, while respecting flow control.

## Acceptance criteria

- Scheduling order tests with mixed urgencies.

## Relation

- **Milestone:** M13 — HTTP/2 flow control, limits and conformance (Track B), optional
- **Partly superseded by:** #0107 (HTTP/3 priorities and the shared `priority` field parser)
- **Remaining here:** PRIORITY_UPDATE and scheduling for HTTP/2.
- **Blocked by:** #0054

## Root cause

HTTP/2 sent SETTINGS_NO_RFC7540_PRIORITIES=1 (#0050) but offered no replacement: the #0054 fair queue served every waiting writer round robin, so an urgent response shared the connection window equally with a large background one, and the `priority` field and PRIORITY_UPDATE (an unknown frame type) were ignored.

## Fix

- `HTTPCore/HTTPPriority.swift`: `HTTPPriority` (urgency 0–7, default 3; incremental, default false) with an allocation-free Structured Field Dictionary reader over the raw bytes (RFC 8941: keys, integers, decimals, strings, tokens, byte sequences, booleans, dates, inner lists, parameters). Invalid dictionaries are ignored whole; out-of-range `u` or non-boolean `i` are ignored; unknown keys and parameters are ignored; later members win. `apply(_:)` merges only the parameters a value carries; `schedulingKey(streamID:)` orders streams. Shared with HTTP/3 (#0107).
- `HTTP2FrameParser`: PRIORITY_UPDATE (0x10) is buffered and reported as `.priorityUpdate(prioritizedStreamID:field:)`. On a stream other than 0, or for Prioritized Stream ID 0: connection PROTOCOL_ERROR; shorter than 4 bytes: FRAME_SIZE_ERROR (RFC 9218 §7.1).
- `HTTP2ConnectionDriver.process`: PRIORITY_UPDATE passes the header-block gate, counts toward `maxControlFramesPerWindow` (a flood gets `GOAWAY(ENHANCE_YOUR_CALM)`, reusing #0056), then updates the shared state.
- `HTTP2SharedState`:
  - `priorities` per dispatched stream, set at dispatch from the `priority` request field (`openPriority`), removed when the stream task ends.
  - `earlyPriorities`: PRIORITY_UPDATEs for client streams above the highest opened, at most `maxConcurrentStreams`, applied (and winning over the request field) when the stream is dispatched; stale ones are dropped when a higher stream opens. Updates for closed streams, even (server) stream IDs and invalid values are ignored.
  - A handler's `priority` response field is merged in when HEADERS are encoded (RFC 9218 §5).
  - `grantNext` picks the proceedable waiter with the lowest key: urgency, then non-incremental before incremental, non-incremental in stream order (one at a time), incremental in queue order (a writer that sent rejoins at the back: round robin). A `lease` on the stream that just sent keeps the turn free for it while it outranks every waiter, until the writer takes a batch (so the transport always makes progress).
  - Starvation: one turn in `fairShareInterval` (16) goes to the oldest waiter regardless of priority.
- `H2OutboundFlowTests`: the #0054 round-robin tests now mark their streams incremental (`priority: i`): at the RFC default (non-incremental) streams go one at a time.

## Verification

- `swift test -j 2 --filter HTTPPriorityTests`: 6 tests (34 parser cases: valid, invalid, defaults, merge, fields, key order).
- `swift test -j 2 --filter H2PriorityTests`: 13 tests — urgent stream first; incremental interleaving; non-incremental one at a time; mixed urgency + incremental; low priority still progresses (1 in 16); PRIORITY_UPDATE after open reorders, before open is kept and wins, closed/even/invalid ignored, early buffer bounded; frame parser (split at every offset, stream ≠ 0, ID 0, short); end to end in memory: a `u=0` response requested second overtakes a `u=5` one on a contended connection window; PRIORITY_UPDATE before open, after open and after close over a connection; a PRIORITY_UPDATE flood gets `GOAWAY(ENHANCE_YOUR_CALM)`.
- `H2PriorityBenchmarkTests` (docs/benchmarks/M10-priorities.md): two 16 MiB downloads, low requested first: `u=0` finishes at ~75 ms, `u=7` at ~130 ms, the background stream getting 6–10% of bytes meanwhile; without a field they go first come first served; with `i` both finish together.
- Full `scripts/guarded.sh -t 900 -- swift test -j 2`: 1,479 tests in 20 runs passed (the 4 known issues are pre-existing curl/ngtcp2 observations).

## Gotchas

- Behaviour change: streams with no `priority` field are now served one at a time in stream order (RFC 9218 default `u=3`, non-incremental) instead of #0054's round robin; a large early response delays later default-priority ones, except for the 1-in-16 fair share. Browsers mark most subresources incremental or give them distinct urgencies, so this matches what they expect.
- Scheduling applies only while writers contend (the outbound queue is full or the connection window is closed). An uncontended connection sends in arrival order.
- `grantNext` now scans the fair queue computing a key per waiter (a dictionary lookup each): O(waiters) per grant, no allocation. The orchestrator's h2load gating run (M13-h2) should confirm no regression.
- The benchmark is a debug build on a loaded machine (load average ~6–8); the order is the result, not the milliseconds.
