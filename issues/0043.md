## Description

Implement the SETTINGS handshake (RFC 9113 §6.5).

## Scope

- The server sends its SETTINGS as the first frame, from config.
- Peer SETTINGS are validated: ENABLE_PUSH must be 0 or 1, INITIAL_WINDOW_SIZE at most 2³¹−1 (otherwise FLOW_CONTROL_ERROR), MAX_FRAME_SIZE between 16,384 and 16,777,215, and unknown identifiers are ignored. Valid settings are applied and ACKed.
- Local settings take effect only after the peer's ACK. A missing ACK within the timeout triggers `GOAWAY(SETTINGS_TIMEOUT)`.
- A SETTINGS ACK with a non-empty payload is a `FRAME_SIZE_ERROR`.
- Changes to the peer's INITIAL_WINDOW_SIZE and HEADER_TABLE_SIZE notify flow control (#0054) and the HPACK encoder (#0041).

## Acceptance criteria

- State machine tests cover every validation rule and the ACK-before-apply ordering.

## Root cause

Feature work: the frame parser (#0034) decoded and validated SETTINGS payloads, but nothing kept connection state. No code sent our SETTINGS, acknowledged the peer's, applied either side's values, or timed out a missing ACK.

## Fix

`HTTP2Connection` (`Sources/HTTP2/HTTP2Connection.swift`) is the connection-level state machine. It is a value type with `mutating func handle(_ event: Event) -> Action`. It returns exactly one action, does no I/O and never awaits.

- `.start` returns `.sendPreface(localSettings, windowIncrement:)`. That is our SETTINGS from `HTTP2Configuration.localSettings` (ENABLE_PUSH omitted), plus a connection WINDOW_UPDATE up to `connectionWindowSize` (1 MiB by default, docs/HTTP2.md).
- §3.4: any frame before the peer's first SETTINGS is a connection `PROTOCOL_ERROR`. This includes PING, a SETTINGS ACK, HEADERS, DATA, WINDOW_UPDATE, RST_STREAM, PRIORITY, unknown types and frame-level stream errors.
- Peer SETTINGS are validated by `HTTP2Settings(payload:)` and the frame parser:
  - ENABLE_PUSH must be 0 or 1 (`PROTOCOL_ERROR`);
  - INITIAL_WINDOW_SIZE must be at most 2³¹−1 (`FLOW_CONTROL_ERROR`);
  - MAX_FRAME_SIZE must be 2¹⁴…2²⁴−1 (`PROTOCOL_ERROR`);
  - an ACK with a payload, or a length that is not a multiple of 6, is `FRAME_SIZE_ERROR`;
  - SETTINGS on a stream is `PROTOCOL_ERROR`;
  - unknown identifiers are ignored.

  Valid settings are applied and answered with `.acknowledgeSettings(headerTableSize:)`. The runtime applies HEADER_TABLE_SIZE to the HPACK encoder and enqueues the ACK in the same critical section (#0044).
- INITIAL_WINDOW_SIZE moves every in-progress stream send window by the delta (§6.9.2). A window may go negative, which makes DATA wait. A window above 2³¹−1 is a connection `FLOW_CONTROL_ERROR`. MAX_FRAME_SIZE caps every DATA grant. MAX_HEADER_LIST_SIZE is recorded. ENABLE_PUSH is accepted and otherwise ignored, because the server never pushes.
- Our settings take effect only on the ACK. `.settingsAck` returns `.applyLocalSettings(settings)`, and the reader then raises the parser's MAX_FRAME_SIZE and sets the HPACK decoder's table limit. A second, unsolicited ACK changes nothing. `.settingsTimeout` before the ACK is `GOAWAY(SETTINGS_TIMEOUT)`; after it, nothing happens.
- A connection error produces exactly one `.goaway(lastStreamID:error)`. Afterwards every event is ignored and every local send returns `.drop`.
- The machine also holds the `HTTP2StreamTable`, the send windows and connection receive accounting. The frame loop drives those (#0044).

## Gotchas

- HPACK decoder capacity: until our SETTINGS are acknowledged the peer may use a 4,096-byte table. The runtime therefore creates the decoder with `max(headerTableSize, 4096)` and lowers the limit only on the ACK. A smaller advertised size then needs a size update from the peer, which RFC 7541 §4.2 requires anyway.
- The SETTINGS ACK must be queued in order with response HEADERS, not ahead of them. A block encoded before the table-size change must reach the peer before the ACK does, so the ACK goes in the ordered lane of the outbound queue (#0044).
