## Description

The legacy server is a singleton (#0002), ignores SIGINT/SIGTERM (#0003), swallows startup failures and hangs (#0004), has a double-resume `ExitHandler` (#0005), spawns an unstructured `Task` per connection (#0029) and parses `maxConnections` without using it (#0024). Replace all of it with an injectable `Server` whose lifetime is a task-group tree driven by a pure lifecycle state machine.

## Scope

- `ServerLifecycle` value type: idle, starting, running, draining(deadline), stopped, failed; `mutating func handle(_:) -> Action`; exhaustive transition tests.
- `Server(configuration:protocols:components:)`, no singleton; immutable `Sendable` `ServerConfiguration` captured at start (no per-request actor hop, ROADMAP §3).
- `run()` accepts in `withThrowingDiscardingTaskGroup` (server → listener → connection); startup errors (port in use, bad root) throw out of `run()`; `shutdown()` moves to draining and returns when the tree finishes.
- Connection limit (`maxConnections`): over the limit, new connections are refused or queued per configuration without spawning work (#0024 part).
- `@main` async CLI: `DispatchSource` signal sources for SIGINT/SIGTERM trigger graceful shutdown; exit code 0 after clean shutdown, 1 on configuration or startup error; no `exit()` from a signal handler and no `dispatchMain()`.
- Two `Server` instances can run in one process (port 0) for tests.

## Acceptance criteria

- `swift test` runs a test that starts two servers on port 0 concurrently and shuts both down.
- An integration test launches the built executable with `Process`, sends SIGTERM, and observes exit status 0; launching with a bad config file observes exit status 1 and a message on stderr, within 2 seconds (no hang).
- A test with `maxConnections = 2` opens three connections and observes the third refused while the first two are served.

## Root cause

The legacy server was a singleton (#0002) whose signal sources were released right after creation (#0003). Its `do/catch` wrapped a `Task {}` instead of the throwing work, so startup errors were swallowed and the process hung in `dispatchMain()` (#0004). `ExitHandler` resumed its continuation twice and dropped early exits (#0005). Every connection got a detached `Task` (#0029), and `maxConnections` was parsed but never enforced (#0024).

## Fix

- `ServerLifecycle` (HTTPServer) is a pure value type with `mutating func handle(_:) -> Action`. States are idle, starting, running, draining(deadline), stopped and failed. Events are start, listenerReady, listenerFailed, shutdownRequested(deadline), drainDeadlineReached and lastConnectionClosed. An event that does not apply leaves the state unchanged and returns `.none`. A shutdown from idle stops at once, and one from starting abandons startup, so an early shutdown is never lost. A second shutdown is a no-op that keeps the first deadline. `start` outside idle returns `.rejectStart`.
- `ServerConfiguration` is an immutable `Sendable` value captured at init: `maxConnections`, `connectionLimitPolicy` (`.backpressure` or `.refuse`) and `drainTimeout`. `validate()` throws `ServerError.invalidConfiguration`.
- `Server<Listener: TransportListener, Handler: HTTPHandler>` has no singleton, and several can run in one process.
  - `run()` validates the configuration and binds the listeners. A bind error, such as a port in use, closes the listeners already bound and is rethrown. Then `run()` serves in a `withDiscardingTaskGroup` with one child per listener. Each listener has its own discarding group with one child per connection. There is no unstructured `Task`.
  - Connection limit: `.backpressure` reserves a slot before calling `next()` on the listener's connections, so at the limit the server stops pulling and the listener's bounded queue applies. `.refuse` closes an over-limit connection at once and starts no task for it.
  - `requestShutdown()` is synchronous and never suspends, so it is safe to call from a signal handler. `shutdown()` requests a shutdown and returns when `run()` finishes. Draining closes the listeners, wakes accept loops waiting for a free slot, and triggers `ConnectionContext.shutdown` on every connection. The server then waits for the last connection or the deadline, whichever comes first. At the deadline it cancels the connection tasks. Cancelling the task that called `run()` stops the server with no grace period.
  - `waitUntilRunning()` returns the bound addresses. The server also counts open, accepted, refused and peak connections.
- `ProtocolRegistry` picks one protocol per connection. It tries the ALPN token first. With a single protocol it reads nothing ahead. Otherwise it sniffs the first bytes against each `matchesCleartextPreface` in order, up to `sniffLimit`, and replays the sniffed bytes through `PrefixedTransport`. A connection no protocol accepts is closed with `.protocolError`. The only protocols so far are test protocols; HTTP/1.1 comes in #0080.
- In HTTPCore: `ConnectionProtocol`, `SniffResult`, `ConnectionContext`, `ShutdownSignal` (a one-shot signal whose `trigger()` is idempotent) and `TransportListener`. They are in HTTPCore because HTTP1, HTTP2 and NetworkTransport depend only on HTTPCore. `TCPListener` conforms to `TransportListener` in NetworkTransport. HTTPTestSupport gains `InMemoryListener`.
- `sws-bench serve` is the new stack's entry point until #0086. It runs a `Server<TCPListener, _>` with an echo protocol, bound to 127.0.0.1:0 by default. It ignores SIGINT and SIGTERM, then routes them through `DispatchSource` signal sources that it keeps alive until the server stops. The sources call `requestShutdown()`. Nothing calls `exit()` from a handler or calls `dispatchMain()`. Exit status is 0 after a clean shutdown and 1 on a config-file, value or startup error, with a message on stderr. Once bound, it prints `listening HOST:PORT` on stdout.

## Gotchas

- `sws-bench` uses a top-level `main.swift`, so the entry point is a `serve` subcommand there, not a separate `@main` type. Package.swift is unchanged.
- The SIGTERM test needs `.build/debug/sws-bench`. `swift test` builds it because `SWSBenchTests` depends on `SWSBench`. The test looks next to the `.xctest` bundle first, then in `.build/debug`.
- The server and the CLI bind with `TCPConfiguration(allowLocalEndpointReuse: false)`. That way a second bind to a port in use fails with EADDRINUSE (`TransportError.failed(code: 48)`).
- The Server takes a single `handler:` for now. #0082 replaces it with the middleware/components builder from ROADMAP §5.2. `ServerComponent`/`ServerHandle` are not defined yet.
- With several protocols registered, a client that sends nothing holds its connection slot during sniffing until shutdown. The header and idle timeouts in #0083 bound this.
- `TransportListener.close()` must not run concurrently with `listen()`, because closing a `TCPListener` that never started can wait forever. So a shutdown during startup is handled by `run()` once binding returns; the listener is not closed from outside.
