# 0079 — Server runs a lifecycle state machine with task-group accept, a connection limit and CLI signal handling

| | |
|---|---|

## Description

The legacy server is a singleton (#0002), ignores SIGINT/SIGTERM (#0003), swallows startup failures and hangs (#0004), has a double-resume `ExitHandler` (#0005), spawns an unstructured `Task` per connection (#0029) and parses `maxConnections` without using it (#0024). Replace all of it with an injectable `Server` whose lifetime is a task-group tree driven by a pure lifecycle state machine.

## Scope

- `ServerLifecycle` value type: idle, starting, running, draining(deadline), stopped, failed; `mutating func handle(_:) -> Action`; exhaustive transition tests.
- `Server(configuration:protocols:components:)`, no singleton; immutable `Sendable` `ServerConfiguration` captured at start (no per-request actor hop, ROADMAP §3).
- `run()` accepts in `withThrowingDiscardingTaskGroup` (server → listener → connection); startup errors (port in use, bad root) throw out of `run()`; `shutdown()` moves to draining and returns when the tree finishes.
- Connection limit (`maxConnections`): over the limit, new connections are refused or queued per configuration without spawning work (#0024 part).
- `@main` async CLI: `DispatchSource` signal sources for SIGINT/SIGTERM trigger graceful shutdown; exit code 0 after clean shutdown, 1 on configuration or startup error; no `exit()` from a signal handler and no `dispatchMain()`.
- Two `Server` instances can run in one process (port 0) for tests.

## Acceptance criteria

- `swift test` runs a test that starts two servers on port 0 concurrently and shuts both down.
- An integration test launches the built executable with `Process`, sends SIGTERM, and observes exit status 0; launching with a bad config file observes exit status 1 and a message on stderr, within 2 seconds (no hang).
- A test with `maxConnections = 2` opens three connections and observes the third refused while the first two are served.
