## Description

Protocol code must be testable without sockets (ROADMAP §4). Define the I/O extension points from ROADMAP §5.2 and an in-memory implementation that every protocol test uses. This replaces the `AsyncSequence`-of-bytes transport proposed in #0027 with a demand-driven `receive(into:)` signature.

## Scope

- `ByteStreamTransport` (`receive(into:maxLength:)` returning 0 at EOF, `send(_:endOfStream:)`, `sendFile(_:)`, `close(_:)`, `info`), `FileRegion`, `CloseReason`, `ConnectionInfo` (local/remote address, TLS flag, negotiated ALPN).
- `MultiplexedTransport` and `StreamIdentified` declarations (implementations in #0098, #0099).
- `HTTPHandler`, `HTTPMiddleware`, `ConnectionProtocol` (with `SniffResult`) and `ServerComponent` declarations exactly as ROADMAP §5.2, so later items implement rather than redesign them.
- `InMemoryTransport` in `HTTPTestSupport`: scripted inbound chunks (including 1-byte splits), captured outbound bytes, half-close, injected errors, and a paired client/server mode; no `DispatchQueue`, no unbounded buffering (uses `BoundedAsyncQueue`).

## Acceptance criteria

- Tests drive `InMemoryTransport` through receive-to-EOF, send-after-close error, half-close, and a paired echo; a 1 MiB transfer through the pair holds at most the configured buffer bound (asserted).
- `swift build` shows `HTTPCore` still has no Network or Foundation import.

## Root cause

Protocol code had no I/O boundary to run over, so it could not be tested without sockets. The earlier `AsyncSequence`-of-bytes proposal (#0027) had no demand control.

## Fix

- `HTTPCore/Transport.swift`: `ByteStreamTransport` (one outstanding receive, `receive` returns 0 at sticky EOF, `send` resumes once bytes are accepted, cancellation throws `CancellationError` with no leaked continuation), `MultiplexedTransport` and `StreamIdentified` (declarations only), `CloseReason` (`normal`, `timeout`, `protocolError`, `shutdown`, `abort`), `ConnectionInfo` (local and remote `TransportAddress`, `isSecure`, `negotiatedALPN`) and a typed `TransportError`.
- `HTTPCore/FileRegion.swift`: `FileRegion` holds an `OwnedFileDescriptor`, which closes the descriptor on deinit, so a region can outlive its handler. The default `sendFile` is `sendFileByReading(_:chunkSize:)`, a `pread` loop over one reusable buffer (64 KiB by default). It checks for cancellation between chunks and throws `unexpectedEndOfFile` when the file is shorter than the region. It uses Darwin only, with no Foundation.
- `HTTPTestSupport/InMemoryTransport.swift`: `makePair(client:server:)` connects two endpoints with one `BoundedAsyncQueue` per direction. The reader's configuration sets the queue and segment size, so `bufferBound = (slots + 2) × segmentSize` holds no matter what the sender writes. `scripted(_:)` plays back fixed inbound `Event`s (`bytes`, `delay`, `endOfStream`, `error`). Receive chunking can be `unlimited`, `fixed(n)`, `bytewise` or a cycling `pattern`. The endpoint also provides `play(_:)` for in-order delays and errors sent to the peer, `failNextSend(with:)`, half-close, a graceful close that drains to EOF, an abortive close that resets the peer, capture of sent bytes, and high-water and suspended-sender counters.

## Gotchas

- **Deferred:** `HTTPHandler`, `HTTPMiddleware`, `ConnectionProtocol`/`SniffResult` and `ServerComponent` are not declared here. They depend on `HTTPRequest`/`HTTPResponse` (#0074, being written in parallel), `RequestContext` (#0083) and `ServerHandle`/`ConnectionContext` (#0080). They should be declared along with those types.
- `HTTPResponseBody.file` in #0074 should use this `FileRegion` and should not define its own.
- HTTPCore already had a `Foundation` import before this issue: `public import struct Foundation.Data` in `ByteBuffer+Data.swift` (#0073). The new files import only Darwin and Synchronization.
- Segment sends by the receiving pipe's `segmentSize`, not the sender's. Using the sender's broke the byte bound (4 KiB segments filled 1 KiB-sized slots) and was caught by the 1 MiB test.
- `BoundedAsyncQueue.next()` returns `nil` both when the queue finishes and when the task is cancelled. `receive` checks `Task.checkCancellation()` after a `nil` to tell the two apart.
- `close` empties a finished queue without suspending, which releases suspended peer senders. Because a finished queue never suspends `next()`, this cannot trip the queue's single-consumer precondition.
- A cancelled `send` may already have delivered a prefix of its segments, as a real socket can. The protocol documentation says to close the stream afterwards.
