## Description

Implement RFC 8441 so WebSockets (planned in `docs/TODO.md`) work over HTTP/2 streams as well as HTTP/1.1 Upgrade.

## Scope

- Advertise `SETTINGS_ENABLE_CONNECT_PROTOCOL = 1`.
- Accept `:method CONNECT` with `:protocol websocket`, `:scheme`, `:path`, and `:authority`, and respond with a 200 HEADERS frame that keeps the stream open.
- Expose the stream as a bidirectional byte AsyncSequence to the WebSocket layer, which is shared with the HTTP/1.1 Upgrade path.

## Acceptance criteria

- The Autobahn test suite scripts in the repo (`scripts/run-autobahn-*.sh`) pass over the HTTP/1.1 path, and a browser WebSocket connects over h2.

## Relation

- **Milestone:** M15 — WebSocket extensions (Track C), RFC 8441 over HTTP/2

- **Related:** #0111 (RFC 9220 over HTTP/3)

## Root cause

HTTP/2 answered every `.tunnel` response with `501` and dropped `:protocol`, so the WebSocket component (#0108/#0109, extended for RFC 9220 in #0111) could not run over h2 streams.

## Fix

- `HTTP2Configuration.enableConnectProtocol` puts `SETTINGS_ENABLE_CONNECT_PROTOCOL = 1` in our SETTINGS. `HTTP2.run` turns it on only when `MiddlewareChainInspector.extendedConnectProtocols(in:)` finds an `ExtendedConnectProvider` (`WebSocketUpgrade`), mirroring HTTP/3 (#0111).
- `HTTP2RequestFieldSink` keeps `:protocol` in `HTTPRequest.connectProtocol`, and treats it as malformed (`RST_STREAM(PROTOCOL_ERROR)`) when the setting was not advertised. `PseudoHeaderValidator` already requires `:scheme`, `:path` and `:authority` for extended CONNECT, rejects `:protocol` on any method but CONNECT, and rejects a CONNECT that has `:scheme`/`:path` but no `:protocol`. HTTP/2 requests now carry `version: .http2` (#0117 follow-up).
- An extended CONNECT's DATA is not bounded by `maxRequestBodySize`.
- `serve` sends a `2xx` `.tunnel` answer to an extended CONNECT as HEADERS without END_STREAM (`runTunnel`). It then runs the closure with `HTTP2TunnelTransport` and a `TunnelContext` carrying the drain signal.
- `HTTP2TunnelTransport` is a `ByteStreamTransport` over the stream:
  - receive pulls from the stream's `HTTP2BodyChannel`, so window credit returns only as the WebSocket reader consumes bytes.
  - send uses `driver.sendData`, waiting for stream and connection window.
  - END_STREAM in either direction is the end of stream; an abortive close (abort, timeout, protocolError) sends `RST_STREAM(CANCEL)`.
- `HTTP2SharedState.tunnels`: a peer or server reset of a tunnelling stream no longer cancels its task. The tunnel sees `connectionReset` in receive and send and ends itself, so the WebSocket handler observes 1006 instead of being cancelled. The drain deadline and connection teardown still cancel.
- `WebSocketUpgrade` / `WebSocketHandshake` needed no change: #0111 already answers an extended CONNECT with `200` and no `Sec-WebSocket-Accept`, and returns `400` (with `Sec-WebSocket-Version: 13` for a wrong version).

## Verification

- `scripts/guarded.sh -t 600 -- swift test -j 2 --filter H2WebSocketTests`: 14 new tests passed, run 4 times, all green:
  - SETTINGS advertised only with WebSockets in the chain.
  - Text, binary, fragmented message with an interleaved ping/pong, client close, then an ordinary request on the same connection.
  - Server close and the 1002 protocol-violation close.
  - Peer `RST_STREAM` gives 1006 and the stream task ends; END_STREAM without a Close frame also gives 1006.
  - Close timeout gives `RST_STREAM(CANCEL)`.
  - Outbound flow control: a 200 KB echo stalls at the client's 65,535-byte window until credited.
  - Inbound flow control: the client is stalled while the application does not read, then all 16 × 16 KB messages echo.
  - The tunnel is not bound by `maxRequestBodySize`.
  - Rejections: wrong or missing version gives 400; another `:protocol` gives 400; a missing `:scheme`/`:path`/`:authority` gives PROTOCOL_ERROR; `:protocol` on GET gives PROTOCOL_ERROR; CONNECT with `:path` and no `:protocol` gives PROTOCOL_ERROR; a plain CONNECT is passed on to the next handler.
  - `:protocol` without the setting gives PROTOCOL_ERROR; `connectProtocol` reaches handlers; shutdown gives 1001; `.tunnel` on an ordinary request gives 501.
  - A loopback TCP test on `127.0.0.1:0` runs a real `Server` with `HTTP2()`: 150 KB binary and text echo, then close.
- `scripts/guarded.sh -t 1200 -- swift test -j 2`: full suite passed (about 1,438 Swift Testing tests across 22 runs, 0 failures). `pgrep -fl "$PWD/.build"` printed nothing afterwards.

## Gotchas

- Inbound backpressure works at message granularity. `WSConnection` keeps reading until a message is complete, and the reader suspends only when the inbound queue (capacity 1) is full. The bound is the stream window, plus one chunk in the transport, plus about two messages.
- The tunnel receive takes the whole buffered chunk from the body channel (its credit goes back at once) and hands it out in `maxLength` slices. This keeps at most about two windows in memory per tunnel.
- A test client must keep answering PING and must not stop at the first GOAWAY. A graceful drain sends GOAWAY plus PING while the tunnel is still closing with 1001.
- Not covered: browser interop over h2 (#0062 territory) and Autobahn over h2. There is no curl or nghttp2 client support for RFC 8441, so the in-repo client is the only h2 WebSocket client used.
