## Description

Complete the MVP with orderly shutdown, consistent error mapping and resource limits (RFC 9114 §5.2, §8).

## Scope

- GOAWAY with the next unprocessed client stream ID on shutdown (from `ServerLifecycle.draining`); requests above it rejected with `H3_REQUEST_REJECTED`; connection closes when in-flight streams finish or the drain deadline passes.
- Error mapping table: stream errors reset the stream (`H3_REQUEST_CANCELLED`, `H3_MESSAGE_ERROR`, …); connection errors close QUIC with the application code.
- Limits: max concurrent bidi streams (QUIC transport parameter as exposed by NW), max field section size, max frame length, request body limit (413), header and idle timeouts reusing `Deadline`; defaults documented next to the HTTP/2 limits table.

## Acceptance criteria

- In-memory tests: GOAWAY on shutdown lets an in-flight request finish and rejects a new stream; each limit produces the documented response or error code.
- SIGTERM during an HTTP/3 download via Homebrew curl completes the download and the process exits 0.

## Root cause

The HTTP/3 MVP (#0100, #0101) closed the connection with `H3_NO_ERROR` as soon as the server drained, so in-flight requests were cut off. Error codes were chosen ad hoc at each call site, and apart from the field section size there were no limits: no concurrency limit beyond the transport's MAX_STREAMS, no body limit, no timeouts, and an unread request body was drained to FIN with no bound.

## Fix

- **GOAWAY and drain.** `H3Connection` gained `beginShutdown(final:)`, `requestStreamClosed(served:)`, and the `sendGoaway`, `grantStreamCredit` and `drained` actions. On `context.shutdown` (or after `H3Timeouts.idle`), the control task sends GOAWAY with the next unprocessed client bidirectional stream ID (largest seen + 4). With `goawayGrace` set, it first sends a provisional GOAWAY with 2^62-4. Streams at or above the ID are reset with `H3_REQUEST_REJECTED`, and requests below it finish. When the last one is done, or `timeouts.drain` passes, the server waits `closeLinger` (ended early when the peer closes) and closes with `H3_NO_ERROR`. Peer GOAWAY IDs that increase are still `H3_ID_ERROR`.
- **Error mapping.** `H3Failure` is the one table (stream vs connection, RESET_STREAM / STOP_SENDING / CONNECTION_CLOSE, code). Every runner failure goes through `fail(_:stream:)`.
- **Limits** (`H3Configuration`, `H3Timeouts`, defaults in `docs/HTTP2.md`):
  - `maxConcurrentRequestStreams`: QUIC credit is raised to the limit at the start and by one as each request stream finishes, through the new HTTPCore protocol `StreamCreditGranting`. `QUICConnection` and `InMemoryMultiplexedTransport` conform. A stream beyond the limit is rejected.
  - Field section size: `431` only when the pseudo-header fields decoded and validated before the overflow, otherwise `H3_MESSAGE_ERROR`. The 431 path now keeps reading the body. An oversized encoded HEADERS frame is still `H3_EXCESSIVE_LOAD`.
  - Request body size: `maxRequestBodySize` gives `413`.
  - Unread body: drained up to `maxUnreadBodySize` / `timeouts.unreadBody`, then STOP_SENDING `H3_NO_ERROR`.
  - Timeouts: `header` (`H3_REQUEST_REJECTED`), `body` (the handler waits for body bytes: `408`), and `idle` (GOAWAY + close). They are enforced by a per-stream `H3StreamWatch` watchdog task and a connection idle wait.
  - A response head larger than the peer's `SETTINGS_MAX_FIELD_SECTION_SIZE` becomes a bare `500` (#0101 follow-up).

## Gotchas

- CONNECTION_CLOSE discards whatever the peer has not read, including the GOAWAY itself. In memory, a client reading the control stream got `connectionReset` instead of the GOAWAY when the server closed right after sending it. The server therefore always waits `closeLinger` (1 s by default) after the drain, and a peer that closes first ends the wait. curl closes on its own once its transfer is done, so the curl test finishes in about the handler's time.
- The body timeout only runs while the handler waits in `HTTPRequestBody.next()`, not while the read-ahead pump waits on the stream. Otherwise a slow handler whose client simply has not sent more body yet would get a `408`. Because the body expires when the handler returns, `H3Failure.bodyTimeout` (after the response started) cannot happen today. It is kept for #0111 tunnels.
- Freeing a concurrency slot happens after the stream task closes the stream, which can be a moment after the client has read the response FIN. A test that reuses the slot at once must retry on `H3_REQUEST_REJECTED`.
- NW still has no STOP_SENDING on its own, so the unread-body STOP_SENDING (`H3_NO_ERROR`) resets the whole stream there. It is sent only after the response is complete and the drain bound has passed, so the response has normally been delivered by then. This is unverified against a slow NW peer.
- `Server` has no QUIC listener yet, so "SIGTERM during an HTTP/3 download, exit 0" is covered in-process: the test closes the listener, triggers the shutdown signal and checks that every task returns. The executable-level check needs QUIC in `Server` (follow-up).
- Each request stream now carries a watchdog task and a lock when any per-stream timeout is set. No benchmark was run (the load average was about 15 with other agents running). Measure it with the M10 load numbers (#0106).
