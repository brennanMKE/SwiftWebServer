## Description

Optional: RFC 7692 permessage-deflate reduces bandwidth for text-heavy WebSocket traffic.

## Scope

- Extension negotiation with `server_no_context_takeover`, `client_no_context_takeover` and `*_max_window_bits` parameters; RSV1 accepted only when negotiated.
- Raw deflate via Apple's Compression framework (shared primitive from #0091); trailing `00 00 ff ff` handling; context takeover per negotiated parameters.
- Decompression bomb protection: decompressed message size bounded by the max message size.

## Acceptance criteria

- `URLSessionWebSocketTask` (which offers permessage-deflate) echoes compressed text messages correctly; a compressed message that inflates beyond the limit closes with 1009.
- RFC 7692 §7.2.3 examples decode.

## Relation

- **Milestone:** M15 — WebSocket extensions (optional)
- **Blocked by:** #0091, #0109
- **Blocks:** none
- **Supersedes:** none

## Root cause

Not a defect: RFC 7692 was not implemented. The WebSocket session declined every extension,
so RSV1 was always a protocol error and every message went uncompressed.

## Fix

- `PerMessageDeflate` (`Sources/WebSockets/PerMessageDeflate.swift`):
  - `Configuration` (server terms; off unless `WebSocketConfiguration.compression` is set):
    context takeover on both sides, server window 2^15, level 6, memory level 8, messages under
    32 bytes sent uncompressed. `negotiate(offers:configuration:)` parses the
    `Sec-WebSocket-Extensions` list (RFC 6455 §9.1: tokens, quoted strings, empty elements) and
    takes the first acceptable `permessage-deflate` offer. Unknown or repeated parameters,
    values on the `*_no_context_takeover` flags, window bits outside 8–15 or with a leading
    zero decline that offer. `server_max_window_bits=8` is declined too: zlib's raw encoder
    cannot use a 256-byte window. The response states `server_no_context_takeover` (asked or
    configured), `client_no_context_takeover`, `server_max_window_bits` (when asked, or below
    15), and `client_max_window_bits` only when the client offered it and we limit it.
  - `Deflater`: raw deflate from #0091's `DeflateEncoder`, sync flush per message, the
    `00 00 ff ff` tail removed, reset after each message without context takeover. Without
    context takeover a message that does not shrink is sent uncompressed; with it the
    compressor has already consumed it, so it is always sent compressed.
  - `Inflater`: `DeflateDecoder` with a 2^15 window (it decodes any client window). It
    inflates into the message buffer with at most `limit - size + 1` bytes of room per step,
    so a message that inflates past `maxMessageSize` fails as soon as the excess appears.
    `finishMessage` appends the tail. It resets after each message without client context
    takeover, and after a block with BFINAL (RFC 7692 §7.2.3.4).
- `WSConnection`: with an inflater, the parser allows RSV1. RSV1 on a continuation or control
  frame is 1002. A message whose first frame has RSV1 is compressed: its payload goes to a
  side buffer and is inflated run by run, and the UTF-8 validator sees the inflated bytes.
  Inflated size over `maxMessageSize` is 1009. Data that will not inflate is 1007. Compressed
  input is bounded at `maxMessageSize` plus deflate's stored-block overhead.
- `WebSocket`: `run(over:...compression:...)` takes the agreed parameters and creates both
  codecs (if zlib cannot allocate, the session sends Close 1011 and ends). The writer task
  compresses text and binary messages and sets RSV1; control frames are never compressed.
  `socket.compression` exposes the agreement. Large message buffers are released after use.
- `WebSocketUpgrade` negotiates when `configuration.compression` is set and answers with
  `Sec-WebSocket-Extensions` (the same code runs for HTTP/3 extended CONNECT, #0111).
- `Package.swift`: `WebSockets` depends on `Compression` (one line).
- `sws-bench micro --filter WebSocket`: deflate and inflate per message on a 1,000-message
  JSON stream; results in `docs/benchmarks/M15-websockets.md`.

## Verification

- `PerMessageDeflateNegotiationTests` (5 tests + 14 invalid offers): defaults, the browser
  offer `client_max_window_bits`, server window and context-takeover combinations and the
  smaller-window rule, quoted values, the 2^8 window declined with fallback to the next offer,
  skipping other extensions.
- `PerMessageDeflateCodecTests`: `rfc7692Examples`. Every §7.2.3 example decodes, fed whole,
  byte by byte and in 2/3/5/7-byte chunks: "Hello" compressed, fragmented, the shared LZ77
  window, a stored block, BFINAL, two blocks, and the empty message. One uncompressed message
  sits between compressed ones. `roundTripWithAndWithoutContextTakeover`: repeats shrink
  below a third with takeover and stay the same size without it.
  `smallAndIncompressibleMessagesGoUncompressed`. `clientContextTakeoverAcrossManyMessages`
  covers both modes in 13-byte chunks. `decompressionBombFailsWith1009`: 4 MiB of zeros in
  under 8 KiB against a 64 KiB limit is 1009, exactly 64 KiB is accepted, and a fragmented
  bomb is also 1009. `reservedBitRules`: RSV1 on a continuation or ping, RSV2, and RSV1 when
  not negotiated are all 1002. `invalidDeflateDataAndInvalidUTF8Fail1007`.
- `PerMessageDeflateSessionTests` (through `HTTP1().run` with a hand-built client):
  `compressedEcho` with and without `server_no_context_takeover`, mixing compressed and
  plain client messages; `serverFramesCarryRSV1OnlyWhenCompressed`;
  `extensionIsDeclinedWhenNotConfiguredOrNotOffered` (RSV1 is then 1002);
  `bombThroughTheSessionClosesWith1009`.
- `URLSessionDeflateTests`: `URLSessionWebSocketTask` does offer the extension, a bare
  `permessage-deflate` on macOS 27, and compresses everything it sends once it is agreed. The
  server inflated 52 of 52 messages: 50 JSON quotes, about 1 MiB of text and 200 KB of
  binary, all echoed intact. `messageInflatingPastTheLimitClosesWith1009`: 1 MiB of one byte
  (about 1 KiB on the wire) against a 64 KiB limit; the client sees `.messageTooBig` and the
  server records failure 1009.
- Benchmarks (`docs/benchmarks/M15-websockets.md`, release, load about 4): the JSON stream
  compresses to 0.189 of its size at the default (level 6, takeover) at 2.5 µs per
  124-byte message; inflate takes 0.21 µs. Without context takeover the ratio is 0.861 at
  5.0 µs. No allocations per message.
- Full `scripts/guarded.sh -t 2400 -- swift test -j 2` on `55190a9`: 1424 tests in 20 runs
  passed. `pgrep -fl "$PWD/.build"` printed nothing.

## Gotchas

- The issue's scope says Apple's Compression framework, but #0091 built the shared primitive
  on the system zlib (`import zlib` inside our `Compression` target), so this uses that.
  `import Compression` in `WebSockets` and its tests resolves to our target, not Apple's.
- zlib cannot encode raw deflate with `windowBits` 8 (`Deflate.swift` clamps to 9). A
  server window of 2^9 used against a client that asked for 2^8 would produce invalid back
  references, so that offer has to be declined.
- Context takeover changes which uncompressed fallbacks are allowed. Once the compressor has
  consumed a message, the peer's decompressor must see it, so with takeover a message that
  did not shrink is still sent compressed.
- No context takeover is slower, not faster: `deflateReset` clears zlib's hash tables every
  message (5.0 µs against 2.5 µs per JSON message), and the state stays allocated either way.
- RFC 7692 §7.2.3.4 (BFINAL): after the stream end, the appended `00 00 ff ff` is not a
  valid start of a new stream (`00` is read as a block header). Drop the rest of that
  message's input and reset; do not feed the tail to a fresh stream.
- `Array.withUnsafeBytes` rethrows untyped errors; a typed-throws body inside it does not
  compile. Return a `Result` instead.
- `ByteBuffer` has no truncate; the writer sends `ByteView(offset:length:)` of the compressed
  buffer to drop the tail without a copy.
