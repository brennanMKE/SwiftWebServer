## Description

`parse.head` for a typical 10-header browser request takes 354 ns median with 0 allocations (release build, load average about 4.4). ROADMAP §7 targets under 150 ns. The parser agent profiled by removing one step at a time (`docs/benchmarks/M1.3-parser.md`):

- about 130 ns in the 10 `HTTPFieldName.lookup(hash:name:)` calls
- about 40 ns in `HTTPFieldIndex.append`
- about 110 ns floor for FNV-1a over the 116 name bytes: each byte's multiply depends on the previous one

## Scope

- Make well-known name lookup cheaper. Options: compare length plus the first 8 bytes as one integer before a full compare; build a perfect-hash table on (length, a few bytes) so most names need no full hash; or resolve names after the field section so the hash work for different fields can overlap.
- Replace FNV-1a's byte-serial dependency chain. Options: process 8 bytes per step (word-at-a-time multiply-xor), or hash only the length and selected bytes needed by the perfect-hash table. Lowercasing must stay fused into the scan.
- Make `HTTPFieldIndex.append` cheaper: unchecked appends into pre-reserved capacity, and fewer bounds checks in the hot path.
- Keep the differential test against the reference parser and the split-at-every-offset tests green.

## Acceptance criteria

- `parse.head` for the 10-header request is under 150 ns median on an idle machine, with 0 allocations.
- No regression above 10% in any other `micro` benchmark.
- Full `swift test` passes, including the differential and split tests.

## Root cause

The #0075 profile attributed about 110 ns to the byte-serial FNV-1a chain, but the
out-of-order core already overlapped most of it with the scan. The real costs were the
lookup itself (global accessor, calls, branches on name length, `canonicalName` compare),
three `Array` appends per field, an indirect-branch state dispatch between the five states
of every field line, bounds checks on every byte, and a byte-at-a-time request line.

## Fix

- `HTTPFieldName`: a 512-slot perfect-hash table keyed on the length and the SWAR-lowercased
  first and last 8 bytes. Four overlapping 8-byte words cover any well-known name (up to 32
  bytes), so confirming a match is one branchless compare; no per-byte hash is computed.
  New `lookup(_:from:to:)` (may read up to 8 bytes past a short name inside the span) and a
  public `HTTPFieldName.Table` the parser holds. `lookup(hash:name:)` keeps its signature and
  ignores the hash. `ASCII.lowercased(word:)` is an exact SWAR fold.
- `HTTPFieldIndex`: the three parallel arrays in one copy-on-write allocation addressed
  through one base pointer; one uniqueness check per append. `names`, `nameViews` and
  `valueViews` are bounds-checked `Column` collections (source compatible with the old
  array uses).
- `HTTP1Parser`: SWAR name scan, exact jump to the first flagged value byte, `fallthrough`
  through the field-line states with the LF checked inline, `GET ` and `HTTP/1.x` word
  compares, a SWAR target scan with the line limit hoisted, and `Span[unchecked:]` where
  `i < end <= count` is already established. Public API unchanged.

Result (release, load 3–5): `parse.head 10-header browser request` 387–450 ns → 132–133 ns
median, 0 allocations. Full table and the step-by-step measurements are in
`docs/benchmarks/M1.3-parser.md`.

## Gotchas

- The FNV-1a chain was not the bottleneck it looked like: removing it alone saved less than
  the A/B estimate. Per-state indirect-branch dispatch (~50 ns) and the request line (~25 ns)
  mattered more. Measure each change; several plausible ones (request-line fallthrough,
  early exit on an empty slot, short-circuit compares, dropping the uniqueness check) did
  nothing.
- `fields.lookupUnknown` is 1–2 ns slower (+10–20%): the old lookup returned at an empty slot
  given a hash the caller had already paid ~13 ns for; the new one ignores the hash and
  always builds its key. End to end, resolving an unknown name is cheaper.
- `x | 0x20` is not a safe lowercase for header bytes (`-` ↔ CR, digits ↔ controls); the
  SWAR fold only touches `A`–`Z`. The single-byte-change test catches a sloppy fold.
- Medians on this shared workstation swing 10–20% with other agents' builds; the first run
  after a build is often slow, so warm up and repeat.
- Another agent's script overwrote `bench.sh` in the shared session scratchpad; keep
  scratch scripts in a uniquely named subfolder.
