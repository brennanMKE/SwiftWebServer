## Root cause

The first h2spec 2.6.0 run against `sws-bench serve --h2` passed 145 of 146 cases over cleartext and 145 of 146 over TLS. Each mode failed a different case, and a third case failed intermittently over TLS:

- **3.5/2, "Sends invalid connection preface" (cleartext).** `--h2` registers HTTP/2 and HTTP/1.1 on one cleartext port. h2spec's bytes (`INVALID CONNECTION PREFACE…`) do not start with the preface, so the sniff sends them to HTTP/1.1, which answers `400`. h2spec then reads the HTTP/1.1 response as a frame header and reports "unexpected EOF". On a shared port that is the right answer. h2spec assumes the port speaks only HTTP/2.
- **5.4.1/1, "Sends an invalid PING frame for connection close" (TLS).** The server sent `GOAWAY(FRAME_SIZE_ERROR)` and started the lingering close (#0052). It half-closes, then waits up to `lingerTimeout` (2 s) for the client to close. Over BSD sockets the half-close is a FIN, the client sees end of stream, and the case passes. Network.framework TLS does not pass `.finalMessage` on to the peer (no close_notify and no FIN until the connection is cancelled), so the client saw no close until the 2 s linger timeout ended. That matches h2spec's own 2 s timeout. A Python client measured the close at 2.08 s over TLS and at 0 ms over cleartext.
- **6.9.1/3, "WINDOW_UPDATE … above 2^31-1 on a stream" (TLS, about 1 run in 3).** h2spec sends HEADERS without END_STREAM, then two WINDOW_UPDATEs of 2^31−1. Over TLS each frame tends to arrive in its own receive, so the hello handler could finish its response before the WINDOW_UPDATEs were read. `responseFinished` then reset the half-closed (local) stream with `RST_STREAM(NO_ERROR)` (§8.1). The WINDOW_UPDATEs then hit a closed stream, where they must be ignored, and h2spec saw the NO_ERROR reset instead of `FLOW_CONTROL_ERROR`. Separately, the send window was dropped as soon as the response ended, so a WINDOW_UPDATE overflow on a half-closed (local) stream was never checked. A Python client that waits 20 ms between the HEADERS and the WINDOW_UPDATEs reproduced it 20 times out of 20.

## Fix

Grouped by RFC 9113 section:

- **§3.4 (preface): `sws-bench serve --h2-only`.** It serves HTTP/2 without HTTP/1.1, so the registry has one protocol, nothing is sniffed, and a bad cleartext preface gets `GOAWAY(PROTOCOL_ERROR)` from `readPreface`. `--h2` keeps the shared port, and there 3.5/2 still gets an HTTP/1.1 `400`, by design. `scripts/h2spec.sh` uses `--h2-only`.
- **§5.4.1 (connection error handling): quiet lingering close.** New `HTTP2Configuration.lingerQuietTimeout` (default 500 ms; `nil` turns it off). The writer's `linger()` also stops waiting once a whole quiet period passes with no receive returning bytes (`HTTP2ConnectionDriver.receives`, one relaxed atomic add per receive, and `waitForQuietInput`). With no input in flight, closing cannot reset the connection over unread data, which is what the lingering close guards against. A peer that keeps sending is still read until it stops, closes, or `lingerTimeout` passes.
- **§6.9.1 and §8.1 (flow control; responses before the request ends): a later NO_ERROR reset.** When a response ends while the request is still open, the stream stays half-closed (local) in `HTTP2Connection.unfinishedRequests` and keeps its send window (`responseEnded`). A WINDOW_UPDATE that overflows the window is then `RST_STREAM(FLOW_CONTROL_ERROR)`. One that fits is accepted and wakes no writer. The §8.1 `RST_STREAM(NO_ERROR)` is sent when the peer's next DATA arrives, and that DATA is credited to the connection. DATA or trailers with END_STREAM close the stream with no reset. A RST_STREAM from the peer, a stream error, the final GOAWAY or a connection error clears the entry. `respondingStreams` excludes these streams. Such a stream holds a MAX_CONCURRENT_STREAMS slot until the client ends it, but no handler task, so drain and idle detection (which count tasks) are unchanged.
- **`scripts/h2spec.sh`.** It starts `sws-bench serve --h2-only` on 127.0.0.1 port 0 (`--tls` for ALPN h2 with the test identity), runs h2spec against the printed port, and stops the server. Options are `--bin`, `--h2spec`, `--report FILE`, and h2spec arguments after `--` (for example `-S` or `http2/6.9`). A watchdog subshell kills the server if the script itself is SIGKILLed, for example by a test timeout. Run it through `scripts/guarded.sh`.

There are no remaining h2spec failures, so no case needed a justification as an h2spec expectation that conflicts with RFC 9113. The 5.3 priority cases (RFC 7540 §5.3) pass because the server parses PRIORITY, validates it (a self-dependency is a stream error) and ignores it (#0050).

## Gotchas

- The script is `scripts/h2spec.sh`, not `scripts/run-h2spec.sh` as the Scope above says. The orchestrator's brief named it `h2spec.sh`, and one script covers both cleartext and `--tls`.
- On a port that serves HTTP/1.1 next to HTTP/2 (`--h2`, and the shipped server once HTTP/2 is registered there), 3.5/2 always fails: a cleartext client without the preface is an HTTP/1.1 client. Run h2spec against an HTTP/2-only port.
- `TCPTransport.send(_:endOfStream: true)` over TLS does not reach the peer as end of stream. The quiet period hides this for HTTP/2, but HTTP/1.1 or anything else that relies on half-close over Network.framework TLS has the same problem. That is a NetworkTransport follow-up, outside this issue.
- A client that sends HEADERS without END_STREAM, gets its response and then goes silent keeps the stream half-closed (local), using one MAX_CONCURRENT_STREAMS slot, until it ends the request or the connection closes. Before this change the server reset such a stream at once. Only that client is affected.
- `lingerQuietTimeout` samples the receive counter once per period. A peer that sends once just after a sample can keep the linger open for up to two periods, and never past `lingerTimeout`.
