## Description

ROADMAP §1.6 requires measurement before optimisation and blocks any milestone that regresses by more than 10%. There is no benchmark harness and no baseline for the legacy server, so there is nothing to regress against. Build the `sws-bench` executable and record the legacy numbers before any new code lands.

## Scope

- `swift run -c release sws-bench <suite>` with micro-benchmark suites (parse, serialize, header lookup, later HPACK/QPACK) that report ns per operation and allocations per operation (via `malloc_zone_statistics` deltas or an equivalent counter) over a fixed iteration count with warm-up, median of N runs.
- A load suite that starts the server on port 0 in-process (or the legacy binary for the baseline) and drives it with `oha` (installed by #0072) for keep-alive and new-connection-per-request runs at concurrency 1, 16 and 128 against a small file (`Root/Public/index.html`) and a large file (≥ 64 MiB generated into a temp root).
- Output as both a human table and JSON; results are committed under `docs/benchmarks/<milestone>-<date>.json` with machine, OS and toolchain recorded.
- A `--compare <old.json>` mode prints deltas and exits non-zero on a regression over 10% in any tracked metric.
- Record the legacy baseline: legacy parse cost per request, requests/s and p50/p99 latency for the small and large file, and peak RSS while serving the large file.

## Acceptance criteria

- `swift run -c release sws-bench --list` lists the suites; each suite runs and prints ns/op and allocs/op.
- `docs/benchmarks/m0-legacy-baseline.json` is committed and reproducible within ±10% on two consecutive runs.
- `--compare` against a deliberately slowed run exits non-zero.
