# M4.1: middleware builder, RequestContext and components (#0083)

What a middleware chain built by `@MiddlewareBuilder` costs per request, and whether the new
`RequestContext` costs anything when no component uses it.

## Cases

`sws-bench h1conn --requests 1000000` gained chain variants. Every handler answers with the
prebuilt `HelloHandler` response; the middlewares are no-ops.

| Case | Handler |
|---|---|
| `request` | `HelloHandler` (what `main` measured) |
| `empty` | `CompiledChain(hello)`: the builder's boundary with no middleware in it |
| `chain3` | `{ NoOp(); NoOp(); NoOp(); hello }` |
| `chain3inline` | the same with `@inline(__always)` no-ops |
| `disabledif` | `{ if disabled { NoOp() }; hello }`, `disabled` read from the environment at run time |
| `starttime` | `HelloHandler` with `RequestContext.startTime` stamped (a `RequestStartTimeConsumer` registered) |

The `h1conn.*` rows run the HTTP/1.1 connection loop over a transport that never suspends.
The `dispatch` rows call `handle` in a loop through `any HTTPHandler` (unspecialized, as the
protocol runners call it), with no connection, so they isolate the chain.

## Reading

- **The chain itself is free.** `chain3` equals `empty` (and `chain3inline`): the three no-op
  middlewares inline away. The symbol table confirms it: the specialized entry closures for
  `chain3`, `chain3inline` and `hello` are one merged function.
- **A disabled component costs about 2 ns** (`disabledif` − `empty`: +1.8 ns dispatch, +1.2 ns
  min / +2.7 ns median keep-alive, +2.4 ns min pipelined). That is about 1% of a request in this
  loop; the pipelined median (+12%) is noise, its min is +1.2%.
- **The boundary costs one async call.** `empty` − `request` is about 13 ns per direct call and
  about 30 ns inside the HTTP/1.1 loop. The runners are generic over the handler but are reached
  through `any ConnectionProtocol`, so they run unspecialized and call `handle` through a
  witness table. A chain called that way directly (no `CompiledChain`) pays two generic async
  calls per middleware plus value-witness copies: measured during development at +87 ns for
  `chain3` per direct call, +330 ns per request in the loop with a left-nested chain.
  `CompiledChain` (stored by the builder's inlinable `buildFinalResult`, so compiled where the
  chain is written with every type known) turns that into one indirect call into fully
  specialized code. The builder returns a lone handler unwrapped, so `Server { app }` pays
  nothing. Removing the last hop needs the runners specialized on the handler type (follow-up).
- **`RequestContext` costs nothing when unused.** The baseline comparison is within noise. A
  first version that copied the context per request and set the start time behind a branch cost
  +7 to +12 ns; the runner now stamps its stored context in place, and only when a registered
  component conforms to `RequestStartTimeConsumer`. Then the clock read
  (`mach_continuous_time`, about 4 ns alone) costs about 6–11 ns per request (`starttime`).
  `ContinuousClock.now` measured 33 ns in a loop, so `MonotonicInstant` keeps raw ticks.
- Development notes: a left fold (`buildPartialBlock`) built `MiddlewareChain(inner, next)` per
  request inside each `ComposedMiddleware`, copying the rest of the chain (two retains/releases
  per layer, about 40 ns for `chain3` once compiled). Fixed-arity `buildBlock` overloads (up to
  10 elements) nest to the right at build time instead, so the request path only borrows stored
  values. `ComposedMiddleware` remains for blocks of middlewares with no handler after them
  (an `if` body).
