## Against the target

The ROADMAP §7 provisional target is < 150 ns and 0 allocations. Allocations meet it
(0.00/op). Time does not: 354 ns median for the 10-header request.

Where the time goes (A/B builds during #0075, same machine, medians are noisy at ±15%):

| Removed from the parse | Median drop |
|---|---:|
| `HTTPFieldName.lookup(hash:name:)` for the 10 names | ~130 ns (≈13 ns per lookup, including waiting on the FNV-1a chain) |
| `HTTPFieldIndex.append` for the 10 fields | ~40 ns |
| Framing checks through `HTTPFieldCollection` when no `Content-Length`/`Transfer-Encoding` | ~40 ns (now a presence-bit fast path) |

The first working version measured 571 ns; the framing fast path plus an 8-byte SWAR scan of
field values brought it to ~355–390 ns.

The remaining ~180 ns is the scan itself, dominated by hashing the 116 name bytes: FNV-1a
is one dependent xor+multiply per byte (about 4 cycles), so the names alone are ~460 cycles
(~110 ns) unless the chains of successive fields overlap.

Reaching 150 ns needs work outside `HTTP1`: a cheaper well-known lookup in `HTTPCore`
(the table is reached through a global accessor and the confirming compare goes through
`canonicalName` and a closure), and either a faster name hash or deferring name
resolution until the field section is scanned so the hash chains overlap.

`parse.head` for the browser request is **132 ns median, 0 allocations**: under the 150 ns
target, at load 3–5 rather than on an idle machine. Other `fields` and `serialize`
benchmarks are unchanged or faster (serialize medians swing ±15% run to run at this load).

`fields.lookupUnknown` is 1–2 ns slower (about +10–20%). It resolves `X-Custom-Header` from
a precomputed FNV-1a hash: before, an unknown name hit an empty slot and returned at once,
but the caller had already paid for the byte-serial hash (about 13 ns for 15 bytes, not in
the benchmark). The new lookup ignores the hash and always builds its four-word key, so the
end-to-end cost of resolving an unknown name dropped; the benchmark only sees the lookup
half. An early return on an empty slot and short-circuit compares were both tried and were
no faster (12.1–12.7 ns at the time).

### What changed, in the order measured

Each row is the median after that step (`parse.head 10-header`), noted with the 1-minute
load average; only steps that measurably helped were kept.

| Step | median ns | load |
|---|---:|---:|
| `main` | 405 | 5.2 |
| 1. Perfect-hash name table keyed on length plus the first and last 8 bytes (SWAR-lowercased), so the scan carries no per-byte FNV-1a chain | 292 | 6.2 |
| 2. `HTTPFieldIndex`: the three parallel arrays in one copy-on-write allocation behind one base pointer, one uniqueness check per append instead of three | 264 | 4.3 |
| 3. SWAR name scan (8 bytes while all are letters, digits or `-`) and an exact jump to the first flagged byte in the value scan | 250 | 4.5 |
| 4. `fallthrough` from line start to name to OWS to value, and the LF checked inline: a field line no longer returns to the state dispatch (an indirect branch) between states | 201 | 2.7 |
| 5. Branchless key (four overlapping 8-byte words cover any name up to 32 bytes; one combined compare) and the table held in the parser, so the lookup skips the lazy global | 173 | 2.7 |
| 6. `Span[unchecked:]` / unchecked loads in the scan, where `i < end <= count` is already established | 163 | 2.5 |
| 7. Unchecked key loads after one range precondition | 159 | 2.4 |
| 8. Request line: `GET ` as one 4-byte compare, `HTTP/1.1`/`HTTP/1.0` + CR as one 8-byte compare, SWAR target scan with the line limit hoisted out of the loop | 133 | 2.3 |

Tried and dropped: `fallthrough` through the request-line states (202 vs 201 ns); removing
the uniqueness check from `append` entirely, as an experiment (no change, so the check
stays); an early return on an empty table slot and short-circuit word compares (no faster).

### Where the time went

The #0075 profile blamed the FNV-1a chain, but removing it alone (step 1) saved about 110 ns
mostly through the cheaper lookup: the out-of-order core already overlapped most of the
hash chain with the scan. The larger costs were branch mispredictions and per-call overhead:
the state dispatch between the five states of every field line (step 4, about 50 ns), the
three `Array` appends per field (step 2), the lookup's calls and length
branches (step 5), and the byte-at-a-time request line (step 8, about 25 ns, most of it the
fixed cost visible in `parse.head minimal request`).

Removing pieces as experiments: replacing the ten lookups with a constant after step 4 took
the parse from about 200 to 137 ns, which is what step 5 went after; skipping the ten
appends after step 6 made no measurable difference. What remains at 132 ns is the scan
itself (about 350 bytes, mostly in 8-byte words), ten lookups and appends, `finishHead`,
and per-head setup (`parse.head minimal request`, 28 ns).

### Correctness

The perfect hash is checked when the table is built (a collision traps) and by
`HTTPFieldNameTests`: every well-known name in three cases, inside larger spans with
different fillers (both key-load paths), every single-byte change of every name (including
each byte's `^ 0x20` partner, so the SWAR lowercase must be exact), unknown names that land
on occupied slots, and names that share length and first/last words with a well-known name.
`ASCII.lowercased(word:)` is checked against the byte fold for every byte in every lane.
`HTTP1FastPathTests` compares the parser with the reference at every request-line limit
across the new fast paths, whole and split at every offset; the existing differential,
every-prefix and 12,000-input mutation tests pass unchanged.
