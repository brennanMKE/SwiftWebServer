# M3.1: HTTP/1.1 connection loop (#0080)

The first record of the new stack serving HTTP/1.1: `sws-bench serve` (the `HTTP1` connection
protocol from #0080 over the #0078 TCP transport and the #0079 `Server`) with its built-in hello
handler, compared with the legacy baseline in [M0-baseline.md](M0-baseline.md).

- Date: 2026-11-11, 14:08–14:10 PST
- Branch: `m03-h1conn` (base `main` `2c8c38a`)
- Load average: 4.73 7.00 14.99 at start, 6.61 7.21 14.53 after the hello runs,
  6.78 7.19 14.31 at end (1, 5, 15 min). No other agent was building.

## Method

- Server: `.build/release/sws-bench serve --port 0` on 127.0.0.1, one process for the hello
  runs and a second with `--body-size 626` (the size of the legacy `/` page) for the
  like-for-like rows. Every response is `200 text/plain` with `date`, `content-length` and
  `connection`.
- Each run: 16 connections, client and server on the same machine over loopback.
  Hello keep-alive: `sws-bench load --keepalive` then `oha -c 16` against the same server,
  three times each, 10 s per run; the median run is reported, with the spread.
- Commands (through `scripts/guarded.sh`):
  - `sws-bench load --url http://127.0.0.1:PORT/ --connections 16 --duration 10 --keepalive --json`
  - `oha -z 10s -c 16 --no-tui --output-format json http://127.0.0.1:PORT/`
  - `oha -z 5s -c 16 --no-tui --output-format json --disable-keepalive http://127.0.0.1:PORT/`
- oha counts the requests in flight at the deadline as errors; they are listed as "cut at
  deadline" and are not failures.

### Connection loop alone: `sws-bench h1conn`

The loop over an in-process transport that never suspends (`Sources/sws-bench/H1ConnBench.swift`),
so the figure is our code per request: receive bookkeeping, parse, handler call, serialize,
send. Allocations are counted process-wide over the difference between a 200,000-request and
a 20,000-request connection, which cancels per-connection setup.

| Benchmark | ns/request | allocations/request |
|---|---:|---:|
| `h1conn.keepalive request` (one request per receive) | 311 | 0.000 |
| `h1conn.pipelined16 request` (16 requests per receive) | 224 | 0.000 |

## Comparison with M0

| Case | M0 legacy (oha) | M3.1 new (oha) | Change |
|---|---:|---:|---:|
| `/` 626 B, 16 connections, legacy's best mode (close) vs new keep-alive | 898 req/s | 67,351 req/s | +7,400% |
| `/` 626 B, 16 connections, close vs close | 898 req/s | 2,761 req/s | +207% |
| p50 latency, same rows as above | 10.597 ms / 10.597 ms | 0.227 ms / 5.494 ms | −98% / −48% |

The legacy server cannot keep a connection alive (it closes after every response, #0020), so
it has no keep-alive row; the first line compares each server in its best mode. The close vs
close line is the like-for-like one, and it is dominated by TCP connection setup on both sides.
For scale, M0 recorded Caddy keep-alive at 9,608 req/s with oha.

**Caveat:** M0 was recorded at a 1-minute load average of 206 (marked provisional there);
this record was taken at about 5–7. The ratio overstates the code change by an unknown factor.
Re-run `scripts/bench-baseline.sh` on an idle machine for a gating comparison.

## Notes

- `sws-bench load` (Network.framework client) reads about 11% below oha in keep-alive mode;
  that gap is the client, as in M0.
- Server RSS after the runs: 12.5 MiB after about 3.9 M hello keep-alive requests; 110 MiB after
  the 626 B runs, which include the 5 s close-mode run (about 14,000 connections). Memory
  after many short connections is worth a look in #0082/#0083 (Network.framework per-connection
  state, or allocator caching); keep-alive alone stays flat.
- The idle-connection drain (closing keep-alive connections waiting in `receive` as soon as
  shutdown starts) is #0082; today they are cancelled at the drain deadline.
