## Memory after close-mode runs (`oha --disable-keepalive`)

`sws-bench serve --port 0`, then three times `oha --no-tui --disable-keepalive -n 20000 -c 50`
with a 5 s pause after each, then `leaks`, `heap` and `vmmap --summary` on the server PID (own
process, no prompts). The new binary was sampled again after a further 90 s idle.

| Sample | Baseline RSS | #0082 RSS |
|---|---|---|
| start | 8.2 MiB | 8.2 MiB |
| after 20k connections | 129.6 MiB | 134.0 MiB |
| after 40k | 133.0 MiB | 137.5 MiB |
| after 60k | 132.9 MiB | 137.9 MiB |
| after 60k + 5 s | 132.6 MiB | 137.8 MiB |
| physical footprint (vmmap) | 110.4 MiB | 115.2 MiB |
| after a further 90 s idle: footprint | | 19.3 MiB |

- **Not a leak.** `leaks`: 0 leaks for 0 bytes in both binaries. RSS plateaus after the first
  20k connections instead of growing with the connection count.
- The live heap right after the runs (375k nodes, 62 MB in the baseline) is all
  Network.framework state, none of it ours: `Endpoint` (41k), `__NWPath` and
  `ProtocolOptions<TCP/IP>` (16k each), `NWConcrete_nw_association` (12.6k, with
  `deactivation_timer`s), path evaluators. No `TCPTransport`, task, or `ByteBuffer` storage is
  retained. Network.framework keeps an association per remote endpoint (every close-mode
  connection uses a new client port) and deactivates it on a timer.
- After 90 s idle the heap is 3,397 nodes (409 KB) and the physical footprint 19.3 MiB:
  the associations expired and malloc returned the pages (`MADV_FREE`). `ps` RSS still shows
  138 MiB because reusable pages stay counted until the system reclaims them; use the physical
  footprint, not RSS, to judge this.
- Right after the runs the small malloc zone was 58–65% fragmented (46 MB allocated in
  124 MB resident), which is the rest of the gap between live bytes and RSS.
- The new binary sits about 4.5 MiB higher during the burst: two more child tasks per
  connection (timer and shutdown waiter) while 50 connections are in flight, and allocator
  noise. It drops back the same way.

## Drain under load (manual check)

`sws-bench serve --port 0 --body-size 50000000 --drain-timeout 10`, `curl --limit-rate 20M`
of the 50 MB body, SIGTERM 1 s in: curl got all 50,000,000 bytes (`http=200`, exit 0, 2.38 s)
and the server exited 0 1.38 s after the signal, when the download finished.
