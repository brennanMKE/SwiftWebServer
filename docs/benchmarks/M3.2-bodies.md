## Method

- Server: `.build/release/sws-bench serve --port 0` on 127.0.0.1. `POST` reads the body with
  `HTTPRequestBody.collect(upTo:)` and answers `200 application/octet-stream` with it, so each
  request moves 1 KiB in and 1 KiB out. `GET /` answers the 14 B hello.
- Body: 1024 random bytes (`head -c 1024 /dev/urandom`), checked once with
  `curl --data-binary @body | cmp`.
- Client and server on the same machine over loopback, 16 connections, keep-alive, 10 s.
- Commands (through `scripts/guarded.sh`):
  - `oha -z 10s -c 16 --no-tui --output-format json -m POST -D body-1k.bin -H 'Content-Type: application/octet-stream' http://127.0.0.1:PORT/echo`
  - `oha -z 10s -c 16 --no-tui --output-format json http://127.0.0.1:PORT/`
- oha counts the requests in flight at the deadline as errors; they are listed as "cut at
  deadline" and are not failures.

## Results

| Case | req/s | p50 ms | p90 ms | p99 ms | errors |
|---|---:|---:|---:|---:|---|
| `POST /echo` 1 KiB body, keep-alive, 16 connections | **59,414** | 0.260 | 0.314 | 0.658 | 0 (594,280 × 200; +16 cut at deadline) |
| `GET /` hello (reference, same server process) | 60,174 | 0.257 | 0.313 | 0.683 | 0 (601,811 × 200; +15 cut at deadline) |

Reading and echoing a 1 KiB body costs about 1.3% of throughput against the hello `GET` in the
same session: the body arrives in the same receive as the head and is copied once into the
body chunk, then once into the collected response.

Server RSS after both runs (about 1.2 M requests): 12.7 MiB, the same as M3.1's hello runs.

## Comparison with M3.1

| Case | M3.1 (oha) | M3.2 (oha) | Change |
|---|---:|---:|---:|
| `GET /` hello, keep-alive, 16 connections (median of 3 in M3.1, 1 run here) | 67,809 req/s | 60,174 req/s | −11.3% |

This single run is below the M3.1 median by more than the 10% rule, but it is not a like-for-like
measurement: one run instead of the median of three, and M3.1's own runs spread 3.9%. The
`GET` path changed only by one `hasBody` branch per request (no body reader is created for a
request without content), and the in-process `h1conn` loop benchmark is unaffected by design.
The orchestrator's gating run at milestone end should repeat this case three times on an idle
machine before treating it as a regression.
