## Method

- Server: `.build/release/sws-bench serve --port 0` on 127.0.0.1. `POST` reads the body with
  `HTTPRequestBody.collect(upTo:)` and answers `200 application/octet-stream` with it, so each
  request moves 1 KiB in and 1 KiB out. `GET /` answers the 14 B hello.
- Body: 1024 random bytes (`head -c 1024 /dev/urandom`), checked once per run with
  `curl --data-binary @body | cmp`.
- Client and server on the same machine over loopback, 16 connections, keep-alive, 10 s.
- Commands (through `scripts/guarded.sh`):
  - `oha -z 10s -c 16 --no-tui --output-format json -m POST -D body-1k.bin -H 'Content-Type: application/octet-stream' http://127.0.0.1:PORT/echo`
  - `oha -z 10s -c 16 --no-tui --output-format json http://127.0.0.1:PORT/`
- Run 1 used the first commit's serve handler (POST/PUT/hello in one `HelloHandler`); run 2 the
  final code (`ServeHandler` in front of an unchanged `HelloHandler`). The request-body path is
  the same in both.
- oha counts the requests in flight at the deadline as errors; they are listed as "cut at
  deadline" and are not failures.

## Results

| Case | Run | req/s | p50 ms | p90 ms | p99 ms | errors |
|---|---|---:|---:|---:|---:|---|
| `POST /echo` 1 KiB body, keep-alive, 16 connections | 1 | 59,414 | 0.260 | 0.314 | 0.658 | 0 (594,280 × 200; +16 cut at deadline) |
| `POST /echo` 1 KiB body, keep-alive, 16 connections | 2 (final code) | **51,631** | 0.281 | 0.405 | 0.826 | 0 (516,414 × 200; +16 cut at deadline) |
| `GET /` hello (reference, same server process) | 1 | 60,174 | 0.257 | 0.313 | 0.683 | 0 (601,811 × 200; +15 cut at deadline) |
| `GET /` hello (reference, same server process) | 2 (final code) | 55,310 | 0.260 | 0.362 | 0.794 | 0 (553,210 × 200; +14 cut at deadline) |

The two runs differ by 13% (POST) and 8% (GET), more than the 10% rule allows, while the load
average rose from 3.6 to 6.2, so the absolute numbers measure the machine as much as the code.
Within each run, reading and echoing a 1 KiB body costs 1.3% (run 1) and 6.7% (run 2) of
throughput against the hello `GET`: the body arrives in the same receive as the head, is
copied once into the body chunk, then once into the collected response.

Server RSS after each pair of runs (about 1.1–1.2 M requests): 12.7 MiB and 13.1 MiB, the
same as M3.1's hello runs. The bounded body path is also covered by tests: a 4 MiB body keeps
the receive buffer and body chunk at one receive (`largeBodyKeepsMemoryFlat`).

## Connection loop alone: `sws-bench h1conn`

The in-process loop over a transport that never suspends, run three times on `main`
(`3241906`) and three times on this branch in the same session (load average 4.5–4.9), to
separate the code change from the machine:

| Benchmark | `main` runs (ns/req) | `main` median | M3.2 runs (ns/req) | M3.2 median | Change | allocations/req |
|---|---|---:|---|---:|---:|---:|
| `h1conn.keepalive request` | 306.4, 342.5, 325.9 | 325.9 | 331.7, 346.4, 322.2 | 331.7 | +1.8% | 0.000 |
| `h1conn.pipelined16 request` | 216.0, 255.0, 228.6 | 228.6 | 248.3, 248.6, 243.5 | 248.3 | +8.6% | 0.000 |

Per request without a body, the loop now summarizes `Expect`, carries the request version and
the body flags through the state machine, and builds a larger `HTTPRequest` (its body enum now
has a reader case). Still zero allocations, and within the 10% rule, but the pipelined case is
the one to watch at the milestone-end gating run.
